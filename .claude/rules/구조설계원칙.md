# 구조설계 원칙

무엇이든 — 프로젝트 폴더, 자료 모음, 링크 분류, 북마크 정리 — 구조를 설계하는 방법이다.


## 구조설계는 분류 문제다

폴더 구조를 만드는 건 mkdir이 아니라 분류 체계를 설계하는 일이다. 도서관 사서가 책을 꽂기 전에 분류 체계를 먼저 만드는 것과 같다.

분류 체계가 없으면 폴더는 쓰레기통이 된다. "misc", "temp", "stuff" 폴더가 생기고, 결국 검색에 의존하게 된다. 좋은 구조는 검색 없이도 원하는 것을 찾을 수 있게 한다.


## 본질 (Essence)

가장 중요한 질문은 "이것의 본질이 뭔가?"다. 항목의 유형을 분류하는 축이다.

코드 프로젝트라면 본질 유형이 이렇게 나뉜다:

```
소스 코드 · 설정/인프라 · 문서 · 참조/링크 · 재료(원본) · 산출물 · 도구/스크립트
```

자료 모음이라면 다르게 나뉜다:

```
글(텍스트) · 이미지 · 영상 · 데이터(CSV, JSON) · 링크/북마크 · 노트
```

본질 유형은 도메인마다 다르다. 위 예시를 기계적으로 대입하면 안 된다. "이 컬렉션에서 항목들은 어떤 유형으로 나뉘는가?"를 먼저 관찰한다.

### 본질은 고유하다

하나의 항목은 하나의 본질을 갖는다. `README.md`는 문서이면서 동시에 설정이 아니다. 두 유형에 걸치는 것처럼 보이면 주된 유형으로 분류한다. 모호하면 "이걸 수정할 때 어떤 관점으로 접근하는가?"로 판단한다.


## 경계 (Scope)

"어떤 기준으로 묶는가?" 항목들을 그룹핑하는 축이다.

```
도메인/기능별    계층/레이어별    생명주기별    대상 독자별    포맷별
```

도메인/기능별은 "이 항목이 어떤 기능에 속하는가"로 묶는다. 인증, 편집기, 결제 같은 것이다. 코드 프로젝트에서 가장 흔하다.

계층/레이어별은 "이 항목이 어떤 레이어에 속하는가"로 묶는다. 프론트엔드, 백엔드, 인프라 같은 것이다. 모노레포에서 자주 보인다.

생명주기별은 "이 항목이 어떤 단계에 속하는가"로 묶는다. 입력, 처리, 출력이나 초안, 진행, 완료 같은 것이다. 파이프라인이나 워크플로우에서 유용하다.

대상 독자별은 "이걸 누가 보는가"로 묶는다. 개발자용, 사용자용, 관리자용 같은 것이다. 문서 컬렉션에서 쓰인다.

포맷별은 "어떤 형태인가"로 묶는다. 이미지, 영상, 텍스트, 데이터 같은 것이다. 미디어 자산이나 자료 모음에서 쓰인다.

하나의 컬렉션에서 자연스러운 경계는 보통 1-2개다. 5개 모두 적용하려 하면 과도하게 복잡해진다.

### 균등성으로 검증한다

경계 축을 선택한 후 항목을 나눠본다. 한 그룹에 70% 이상이 몰리면 그 축은 부적절하다. 3-7개씩 고르게 나뉘면 적절한 축이다.

```
# 나쁨: auth(2개), editor(15개), other(1개) → 불균등
# 좋음: auth(5개), editor(6개), layout(4개), admin(3개) → 균등
```


## 우선축 (Primary Axis)

본질과 경계, 두 축이 있을 때 어느 것이 폴더의 첫 번째 깊이가 되는가.

```
# essence-first: 유형별로 먼저 나눈다
docs/
  auth/
  editor/
config/
  auth/
  editor/

# scope-first: 도메인별로 먼저 나눈다
auth/
  docs/
  config/
editor/
  docs/
  config/
```

같은 항목이지만 우선축에 따라 탐색 경험이 완전히 달라진다. essence-first는 "문서를 보고 싶다" → docs/로 간다. scope-first는 "인증 관련을 보고 싶다" → auth/로 간다.

### 우선축 결정: 세 가지 테스트

세 가지 테스트를 순서대로 적용한다. 첫 번째가 가장 결정적이다.

첫 질문 테스트가 핵심이다. "이걸 찾을 때 머릿속에 떠오르는 첫 번째 질문이 뭔가?" "어떤 기능이지?"가 먼저면 scope-first다. "어떤 유형이지?"가 먼저면 essence-first다. 편집기 관련 파일을 찾을 때 "editor 폴더 가자"가 먼저지 "components 폴더 가자"가 아니다.

동시 수정 테스트는 보조 판단이다. 한 번 수정할 때 같은 도메인의 다른 유형들을 함께 건드리면 scope-first다. 같은 유형의 다른 도메인들을 함께 건드리면 essence-first다. auth의 route + model + test를 한 번에 수정하면 scope-first, ko.json + en.json + vi.json을 한 번에 수정하면 essence-first다.

성장 방향 테스트는 미래를 본다. 새 도메인/기능이 주로 추가되면 scope-first가 확장에 유리하다. 새 유형/포맷이 주로 추가되면 essence-first가 유리하다.

세 테스트가 50:50이면 기본값을 적용한다:

```
코드 프로젝트  → scope-first
자료/참조 모음 → essence-first
문서 컬렉션   → 독자별(audience) > scope-first
혼합         → 사용자에게 묻는다
```

### 그룹핑 시점

평탄 구조에서 그룹 구조로 전환하는 시점이다. 항목 수만이 기준이 아니라 이름의 자기 서술성과 함께 판단한다.

7개 이하면 평탄을 유지한다. 항상 그렇다. 7개는 한눈에 스캔할 수 있는 양이다.

8-12개면 이름이 자기 서술적이고 스캔 가능하면 평탄을 유지한다. 이름만 보고 내용을 구분할 수 있으면 12개도 평탄으로 충분하다.

13개 이상이면 자연스러운 그룹이 있는지 본다. 각 그룹에 3개 이상 들어갈 때만 그룹핑한다. 2개짜리 그룹은 만들 가치가 없다.

```
# 나쁨: 2개짜리 그룹 생성
프로세스/          ← 2개뿐
  깃컨벤션/
  워크플로우/

# 좋음: 인접 그룹에 흡수
원칙/              ← 깃컨벤션, 워크플로우 포함
  깃컨벤션/
  워크플로우/
  이름짓기/
  디자인/
```

그룹핑 후에도 최상위 항목이 4-7개가 되어야 한다. 그룹을 만들었는데 최상위가 여전히 12개면 그룹핑이 실패한 것이다.


## 깊이 제한

깊이가 깊을수록 좋은 게 아니다. 깊이 4를 넘으면 경로를 기억하기 어렵다.

```
# 깊이 2: 대부분의 소규모 프로젝트에 충분
src/
  auth/
  editor/

# 깊이 3: 중규모 프로젝트
src/
  auth/
    routes/
    models/
  editor/
    components/
    hooks/

# 깊이 4: 대규모 프로젝트의 최대치
src/
  features/
    auth/
      routes/
      models/
```

규칙은 "flat until proven otherwise"다. 폴더에 항목이 많아지면 하위 폴더를 만든다. 구체적 시점은 위의 그룹핑 시점을 따른다. 넘지 않으면 평평하게 둔다. 미래를 예측해서 미리 깊이를 추가하지 않는다.


## 고아 방지

모든 항목은 명확한 자리가 있어야 한다. "여기 놓을 데가 없어서 루트에 둔다"는 구조 설계의 실패다.

고아가 생기면 두 가지 중 하나다. 새로운 그룹이 필요하거나, 기존 그룹의 경계가 너무 좁다. 고아를 misc/에 넣는 건 해결이 아니라 은폐다.


## 이름과 구조의 관계

폴더명은 그 자체로 분류 기준을 설명해야 한다. `components/`를 보면 "여기 컴포넌트가 있겠구나"가 바로 통한다. `group1/`은 아무것도 알려주지 않는다.

이름짓기 원칙이 여기서도 적용된다. 자기 서술성이 가장 중요하고, 발견 가능성이 그 다음이다. 구조 안에서 이름은 네비게이션이다.


## 설계안 파일

구조 설계의 결과물은 `_structure.md` 파일이다. 최종 산출물이 아니라 대화의 앵커다.

folder-planner가 설계를 마치면 대상 경로에 이 파일을 `draft` 상태로 생성한다. 사용자가 파일을 보면서 수정하고, 만족하면 `confirmed`로 전환한다. confirmed에서만 실제 폴더를 생성한다. Terraform의 plan → review → apply와 같은 패턴이다.

설계안 파일의 상세 형식은 folder-planner 에이전트 정의를 참조한다.


## 기본 연산과의 관계

이 원칙의 각 섹션은 에이전트 시스템의 기본 연산에 대응한다. 본질이 에센스("이것들이 뭔가?"), 경계가 스코프("어떻게 묶을까?"), 우선축·깊이·고아 방지가 구조("어디에 놓을까?"), 이름이 이름("뭐라 부를까?")이다. 설계안 파일의 리뷰가 대화("이게 맞아?")다. 여섯 번째 연산인 맥락 갱신("문서가 현실과 맞나?")은 설계가 아닌 유지의 문제이므로 이 원칙에서는 다루지 않는다.

folder-planner가 이 원칙을 가장 명시적으로 적용한다(Step 2 에센스, Step 3 스코프, Step 4-5 구조, Step 8 대화). project-init, scope-finder 등도 같은 원칙을 암묵적으로 사용한다. 기본 연산의 상세는 에이전트 가이드의 기본 연산 섹션 참조.


## 사례

### 코드 프로젝트 (scope-first)

기능별로 먼저 나누고, 기능 안에서 유형별로 나눈다.

```
src/
  auth/           ← 도메인: 인증
    routes.py
    models.py
    utils.py
  editor/         ← 도메인: 편집기
    components/
    hooks/
    types.ts
  shared/         ← 도메인 간 공유
    ui/
    lib/
```

근거: 기능을 추가하거나 수정할 때 한 폴더 안에서 작업이 완결된다. 파일 간 이동이 최소화된다.

### 자료 모음 (essence-first)

유형별로 먼저 나누고, 유형 안에서 주제별로 나눈다.

```
articles/         ← 본질: 글
  ai-agents/
  design-systems/
references/       ← 본질: 참조 링크
  tools.json
  libraries.json
raw/              ← 본질: 원본 재료
  client-docs/
  meeting-notes/
```

근거: "글을 찾는다", "링크를 찾는다"처럼 유형 단위로 접근하는 패턴이 지배적이다.

### 문서 모음 (audience-first)

독자별로 먼저 나누고, 독자 안에서 주제별로 나눈다.

```
docs/
  dev/            ← 독자: 개발자
    architecture/
    api/
  user/           ← 독자: 사용자
    guide/
    faq/
  ops/            ← 독자: 운영팀
    deploy/
    monitoring/
```

근거: 같은 주제라도 독자에 따라 내용과 깊이가 다르다. 독자가 자기 폴더만 보면 된다.


## 체크리스트

구조를 설계한 후 확인한다:

### 분류 기준
```
□ 각 항목의 본질(essence)을 파악했는가
□ 2개 이상 경계 축을 비교했는가
□ 균등하게 나뉘는 축을 선택했는가 (70% 쏠림 없음)
```

### 우선축
```
□ 접근 패턴에 맞는 우선축을 선택했는가
□ 근거를 명시했는가
```

### 그룹핑 시점
```
□ 7개 이하면 평탄을 유지했는가
□ 8-12개면 이름의 자기 서술성으로 판단했는가
□ 13개 이상이면 각 그룹 3개 이상으로 나뉘는가
□ 그룹핑 후 최상위가 4-7개인가
```

### 구조 품질
```
□ 깊이 4 이하
□ 폴더당 7±2 이하
□ 고아 항목 없음
□ 폴더명이 자기 서술적
```

### 검증
```
□ 새 항목이 추가될 때 자리가 명확한가
□ 기존 항목을 찾을 때 2번 이내에 도달하는가
□ 대안 구조와 비교하고 트레이드오프를 고려했는가
```
