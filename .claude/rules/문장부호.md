# 문장부호

쉼표, 따옴표, 하이픈, 쌍점 등의 문장부호 사용 기준을 정리한다. 스코프.md의 "표기/문장부호" 결정 항목을 구체화한다. 감정 온도와 시각적 밀도를 조절하는 층위에 해당한다.

근거는 두 종류다. 원칙은 국립국어원 한국어 어문 규범을 따른다. 증거는 BZCF와 AI 번역 코퍼스의 Level 4 비교 결과다.


## 원칙

**우선순위: 의미 정확성 > 맥락 보존 > 자연스러움 > 간결함.** 아래 금기와 대안은 이 우선순위 안에서만 적용한다. 부호 규칙을 따르되 원문의 논리 관계나 인용 경계가 모호해지면 원래 부호를 유지한다.

한국어의 문장부호 관습은 영어와 다르다. 영어는 쉼표로 절을 구분하고, 큰따옴표로 인용과 강조를 겸하며, 하이픈으로 복합어를 연결한다. 한국어는 그중 상당수가 불필요하거나 오히려 가독성을 떨어뜨린다.

쉼표는 "숨을 고르는 자리"에 쓴다. 영어의 문법적 의무 쉼표(관계절 앞, 삽입구 양쪽, 나열 끝)를 그대로 옮기면 한국어에서는 과잉이 된다. 한국어는 어미와 조사로 절 관계를 충분히 표현하므로 쉼표가 필요한 자리가 더 적다.

큰따옴표는 인용, 작은따옴표는 강조가 한국어 어문 규범이다. 영어식 `"quote"`를 강조에 쓰면 인용과 구분되지 않아 혼란을 준다.

쌍반점(;)과 쌍점(:)은 영어에만 있는 부호다. 한국어 어문 규범에 쌍반점의 용법은 아예 등재되어 있지 않고, 쌍점은 제한된 용법(시간 표기, 대화 인용)만 허용된다. 영문 전공서 번역에서 가장 흔하게 틀리는 곳이다.

하이픈은 한국어 단어 연결에 쓰지 않는다. 영어의 `not-so-intelligent` 같은 하이픈 복합어를 `그다지-지적이지-않은`으로 옮기면 어색하다. 강조가 필요하면 작은따옴표가 낫다.


## 증거

Level 4 코퍼스 비교에서 AI가 BZCF보다 문장부호를 훨씬 많이, 그리고 영어식으로 쓰는 경향이 드러났다.

```
큰따옴표 강조            AI 5.1배 (20.0 → 102.6 /1000줄)
느낌표                  AI 2.2배
말줄임표                AI ∞배 (BZCF 0회)
하이픈                  AI 2.7배
쌍점(:)                 BZCF 0.84, AI 0 (BZCF 약간 사용)
```

쉼표는 더 근본적인 차이를 보인다. KatFishNet 방식으로 측정한 comma features다.

```
쉼표 포함 문장 비율       BZCF 27.5%, AI 59.4%  (AI 2.2배)
평균 쉼표 밀도           BZCF 0.017, AI 0.022   (형태소 대비)
쉼표 상대 위치           BZCF 0.54, AI 0.46     (AI가 문장 앞쪽에 배치)
쉼표 주변 POS 다양성      BZCF 0.054, AI 0.134  (AI가 복잡 구조)
쉼표 사이 segment 길이    BZCF 11.7, AI 24.7    (AI의 segment 2배 길다)
```

AI가 쉼표를 많이 쓰는 이유는 두 가지다. 첫째, 영어식 쉼표 습관(관계절·삽입구·나열)을 그대로 전이한다. 둘째, AI의 문장이 평균 3배 길어서 쉼표로 호흡을 나눌 수밖에 없다. 두 요인이 겹쳐 AI의 segment가 24.7형태소로 BZCF(11.7형태소)의 2배가 된다.


## 금기

조건부 금기다. 각 항목 오른쪽의 "단, ~일 때는 유지"가 예외다.

### 쉼표

```
영어식 관계절 앞 쉼표           →  "내가 어제 만난, 친구가" 같은 쉼표 회피 (예외 없음)
영문식 삽입구 양쪽 쉼표          →  "나는, 사실, 그것을 알았다" 회피. 단, 삽입구가 앞뒤 문장과 어순이 명확히 달라 분리가 필요한 인용·설명이면 유지
나열 끝 Oxford comma           →  "A, B, 그리고 C" 회피. "A, B, C" 또는 "A, B 그리고 C"(쉼표 생략)로 대체. 단, 마지막 항목 자체가 "D와 E"처럼 접속사를 포함하면 앞에 쉼표 유지 ("A, B, 그리고 D와 E")
쉼표 뒤 공백 누락              →  "오늘은,정말" 같은 붙여쓰기 금지. 쉼표 뒤 한 칸 띄우기 (예외 없음)
한 문장 3개 이상 쉼표           →  문장 분리 고려. 단, 대등 나열(A, B, C, D, E)이거나 삽입구가 의미 경계로 필요하면 유지
```

### 따옴표

```
강조 목적 큰따옴표              →  강조는 작은따옴표(U+0027 ' 또는 U+2018/U+2019 ' ')로. 큰따옴표(U+0022 " 또는 U+201C/U+201D " ")는 인용 전용 (예외 없음)
영문식 굽은 따옴표 혼용           →  U+201C/U+201D("굽은 큰따옴표") 대신 U+0022(직선 큰따옴표)로 통일 권장. 편집 규정이 있으면 규정 따름
작은따옴표 인용                 →  인용은 큰따옴표. 단, 인용 안의 재인용은 작은따옴표 ("그는 '미안해'라고 말했다")
```

### 쌍반점·쌍점

```
쌍반점(;)                      →  한국어 용법 없음. 예외 없이 마침표·접속부사로 교체
쌍점(:) 뒤 내용 잇기            →  "다음과 같다: 첫째" → "다음과 같다. 첫째". 단, 시간(14:30)·비율(3:1)·인용·제목 구분은 유지
쌍점(:) 설명 도입               →  회피. 단, 목록의 머리말·용어 정의 같은 도식적 목적이면 유지 ("원칙: ..." 형태)
```

### 하이픈·대시

```
하이픈 복합어                   →  "그다지-지적이지-않은" 회피. 띄어쓰기 또는 작은따옴표로 대체
em dash 삽입                   →  "그는—물론—알고 있었다" 회피. 괄호나 쉼표로 대체
ASCII 대시                     →  범위 "3-5일"은 "3~5일"로. 단, 인명·약어("A-B 모델")는 유지
```

### 기타

```
느낌표 연속                    →  "정말이야!!" 회피. 단일 느낌표로 충분. 단, 캐릭터 대사의 격양 표현은 유지
말줄임표 남발                   →  "잘 모르겠어요…" 회피. 단, 실제 망설임·말끊김을 표현하면 유지
영문 apostrophe                →  한글에 ASCII ' 혼용 금지. 한국어 문장부호만 사용
```


## 대안

### 쉼표 대신

```
(영어) I, however, disagree.
(직역) 나는, 하지만, 동의하지 않는다.
(대안) 하지만 나는 동의하지 않는다.

(영어) The man, who was tall, walked in.
(직역) 그 남자는, 키가 컸는데, 들어왔다.
(대안) 키가 큰 그 남자가 들어왔다.

(영어) A, B, and C
(직역) A, B, 그리고 C
(대안) A, B, C / A와 B, C / A, B, C 세 가지
```

### 따옴표 대신

```
(잘못) 이것이 "진짜" 문제다.
(올바름) 이것이 '진짜' 문제다.

(잘못) 그는 이렇게 말했다. '미안해요'
(올바름) 그는 이렇게 말했다. "미안해요"
```

### 쌍점·쌍반점 대신

```
(영문식) 핵심은 다음과 같다: 속도와 비용.
(한국어) 핵심은 속도와 비용이다. / 핵심은 둘이다. 속도와 비용.

(영문식) 속도가 빠르다; 비용이 싸다.
(한국어) 속도가 빠르고 비용이 싸다. / 속도가 빠르다. 비용도 싸다.
```

### 하이픈 대신

```
(영문식) 그다지-지적이지-않은 답변
(한국어) 그다지 지적이지 않은 답변 / '지적이지 않은' 답변

(영문식) 3-5일 소요
(한국어) 3~5일 소요 / 3일에서 5일 소요
```


## 과교정 경계

부호 규칙을 기계적으로 적용하면 오히려 의미 경계가 무너진다.

### 쉼표 과잉 제거로 경계 상실

```
(원문) 그는 지난 20년간, 특히 2010년 이후의 업적으로, 업계 전설이 되었다.
(과교정) 지난 20년간 특히 2010년 이후의 업적으로 업계 전설이 되었다  ← 삽입구 경계가 사라져 수식 구조 모호
(적절) 그는 지난 20년간, 특히 2010년 이후의 업적으로 업계 전설이 되었다  ← 첫 쉼표는 유지
```

"3개 이상이면 분리"는 평가 문장이 꼬여있을 때만. 삽입구가 명확히 분리되어야 읽히는 자리에는 쉼표를 유지한다.

### 쌍점 일괄 제거로 도식 구조 붕괴

```
(원문 도식)
  우선순위:
    1. 정확성
    2. 맥락
    3. 간결함
(과교정) "우선순위는 정확성, 맥락, 간결함이다"로 한 줄화  ← 목록의 순위·독립성이 사라져 나열로 변형
(적절) 원 도식 구조 유지 (쌍점 + 번호 목록)
```

쌍점은 영어식 "설명 잇기"만 회피. 머리말·정의·번호 목록·용어 정의("원칙: ...") 같은 도식 구조에는 쌍점을 유지한다.

### 하이픈 제거로 복합어 분리

```
(원문) end-to-end 암호화
(과교정) 종단 종단 암호화  ← 의미 파편화
(적절) 종단 간 암호화 / end-to-end 암호화  ← 원어 유지 또는 조사로 재구성
```

하이픈 복합어는 띄어쓰기로 단순 교체하지 않는다. 의미 관계(~간, ~에서 ~까지)를 복원하거나 원어를 유지한다.

### 인용 경계 모호화

```
(원문) 그는 "이것이 정답이다"라고 말했다
(과교정) 그는 이것이 정답이라고 말했다  ← 직접 인용이 간접 인용으로 변형됨
(적절) 그는 "이것이 정답이다"라고 말했다  ← 직접 인용 따옴표 유지
```

따옴표는 인용 경계를 분명히 한다. 직접 인용의 따옴표를 "강조 회피"로 간주해 제거하지 않는다.


## 체크리스트

### 1단계: 부호 규칙 준수

```
□ 쉼표가 숨을 고르는 자리 외에 습관적으로 들어가지 않았는가
□ 한 문장에 쉼표가 3개 이상이면 문장 분리를 고려했는가 (삽입구 명확 분리 제외)
□ 강조에 큰따옴표 대신 작은따옴표를 썼는가
□ 인용은 큰따옴표로 구분되는가
□ 쌍반점(;)이 없는가
□ 쌍점(:) 뒤에 영어식 설명 잇기가 없는가 (목록·정의·제목 제외)
□ 하이픈 복합어가 없는가 (복합어는 띄어쓰기 또는 작은따옴표)
□ 느낌표와 말줄임표가 감정을 강요하지 않는가
□ 범위 표기에 ASCII 대시 대신 물결표(~) 또는 "에서"가 쓰였는가
```

### 2단계: 과교정 역검사

```
□ 쉼표 제거로 삽입구·수식 경계가 무너지지 않았는가
□ 쌍점 제거로 도식·목록 구조가 산문으로 뭉개지지 않았는가
□ 하이픈 제거로 복합어의 의미 관계가 사라지지 않았는가
□ 직접 인용의 따옴표가 "강조 회피" 규칙에 오인되어 제거되지 않았는가
□ 숫자 범위·시간 표기처럼 쌍점·하이픈이 규범상 허용되는 자리는 유지됐는가
```
