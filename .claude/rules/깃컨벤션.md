## 원자적 커밋

하나의 논리적 변경 = 하나의 커밋. revert, cherry-pick, bisect 모두 이 원칙 위에서 동작한다.

나쁜 예:
```bash
git commit -m "여러 작업 완료"
# 인증 + 결제 + 이메일 기능이 한 커밋에
```

좋은 예:
```bash
git commit -m "feat: 사용자 인증 추가"
git commit -m "feat: 결제 시스템 연동"
git commit -m "feat: 이메일 알림 추가"
```

각 커밋은 독립적으로 revert/cherry-pick 가능하다. 관련 파일은 함께 커밋한다. 심볼릭 링크와 실제 파일, 서로 의존하는 파일들은 같은 커밋에 넣어서 관계를 명확하게 한다.


## 커밋 메시지 형식

Conventional Commits 기반이다. 프로젝트에 `.gitmessage.txt`가 있으면 해당 형식을 우선 따른다.

```
<type>(<scope>): <summary>

<키워드 · 키워드>

<body>

<footer>
```

### Type

| type | 용도 |
|------|------|
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 리팩토링 (기능 변경 없음) |
| docs | 문서 |
| test | 테스트 |
| chore | 빌드, 설정 |
| perf | 성능 개선 |
| style | 포맷팅 (코드 변경 없음) |
| ci | CI/CD 설정 |

### Scope (optional)

단일 모듈 변경이면 사용, 여러 영역이면 생략.

### Summary

문제 또는 결과를 쓴다. 구현 방법은 Body에. 50자 이내, 마침표 없음.

### 키워드

이 커밋이 다루는 내용을 · 로 나열한다.

### Body

"왜" 변경했는지 설명. 한국어는 연결어(반면, 그래서, 하지만)로 문장 관계를 명시한다. 72자 줄바꿈.

### Footer

- `Review: passed/skipped/manual` - code-reviewer 상태
- `Closes #123` - 이슈 닫기
- `BREAKING CHANGE: 설명` - 호환성 깨는 변경
- `Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>` - AI 협업 명시

### 실전 예시

```
fix(editor): 머신 텍스트 개행이 선택 전후로 달라지는 문제 수정

border · outline · MachineItem · 텍스트 레이아웃

border는 콘텐츠 영역을 줄여 작은 머신에서 텍스트 줄바꿈이
선택 전후로 달라지는 문제가 있었다. 반면 outline은 레이아웃에
영향을 주지 않으므로 일관된 텍스트 렌더링을 보장한다.

Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
```


## 브랜치 전략

1인/소규모 (GitHub Flow):
```
main ─────────────────────────
       ↑
feature/기능명 ────→
```

대규모 (Git Flow):
```
main ─────────────────────────
       ↑
develop ──────────────────────
       ↑
feature/기능명 ────→
```


## PR/리뷰

PR 제목은 70자 이내로 쓴다. 본문에 변경 사항 요약과 테스트 계획을 포함한다.

리뷰 정책:
- 리뷰어 수: 팀 규모에 따라 결정 (1인이면 AI 리뷰)
- 승인 조건: code-reviewer 통과 + 팀원 승인
- 자동 리뷰: code-reviewer 에이전트 활용

```markdown
## Summary
- {변경 내용 요약}

## Test plan
- [ ] {테스트 항목}
```


## 머지 전략

브랜치 전략이 "어떤 브랜치를 만드는가"라면, 머지 전략은 "브랜치를 어떻게 합치는가"다.

| 전략 | 용도 |
|------|------|
| Merge commit | 히스토리 보존, 대규모 팀 |
| Squash merge | 깔끔한 히스토리, 기능 단위 |
| Rebase | 선형 히스토리, 소규모 팀 |

1인 프로젝트는 squash merge가 간결하다. 팀 프로젝트는 merge commit으로 컨텍스트를 보존한다.


## 태그/버저닝

Semantic Versioning 기반:
```
v{MAJOR}.{MINOR}.{PATCH}
```

| 변경 | 올림 |
|------|------|
| 호환성 깨짐 | MAJOR (v1 → v2) |
| 새 기능 | MINOR (v1.0 → v1.1) |
| 버그 수정 | PATCH (v1.0.0 → v1.0.1) |

태그 생성:
```bash
git tag -a v1.0.0 -m "첫 릴리스"
git push origin v1.0.0
```


## Hooks/자동화

컨벤션을 코드로 강제한다. 규칙을 정해도 강제하지 않으면 지켜지지 않는다.

| 도구 | 용도 |
|------|------|
| commitlint | 커밋 메시지 형식 검증 |
| husky | Git hooks 관리 |
| lint-staged | 스테이징된 파일만 린트 |

1인이면 `.gitmessage.txt` 템플릿으로 충분하다. 팀이면 husky + commitlint로 강제한다.

설정 예시:
```bash
npx husky init
echo "npx commitlint --edit \$1" > .husky/commit-msg
```


## .gitmessage.txt

project-init 에이전트가 이 템플릿을 프로젝트 루트에 `.gitmessage.txt`로 복사한다. 복사 후 글로벌 또는 프로젝트 단위로 적용한다.

```bash
# 프로젝트 단위 (권장)
git config commit.template .gitmessage.txt

# 글로벌 (모든 프로젝트에 적용)
git config --global commit.template ~/.gitmessage.txt
```

```
<type>(<scope>): <summary>
# │       │         │
# │       │         └─ 문제/결과 (구현 방법은 Body에). 50자 이내
# │       └─ 영향 범위 (auth, editor, api 등)
# └─ feat, fix, refactor, docs, test, chore, perf, style

# 키워드: 이 커밋이 다루는 내용을 · 로 나열

# Body: "왜" 변경했는지
# - 한국어는 연결어로 문장 관계 명시
# - 72자 줄바꿈

# Footer:
# - Review: passed
# - Closes: #123
# - BREAKING CHANGE: 호환성 깨짐
```
