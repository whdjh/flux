# 문서 작성 가이드

내부 문서 작성 원칙이다.

메모, 설계 노트, 가이드 문서를 쓸 때 사용한다. 규칙이 충돌하면 명확성 > 흐름 > 형식 순서로 판단한다. 빠르게 참조하려면 맨 아래 체크리스트를 보면 된다.


## 철학

문서는 달랑 필요한 것만 담는다. 설명을 위한 설명, 형식을 위한 형식은 배제한다. 읽는 사람이 5초 안에 핵심을 파악할 수 있어야 한다.

불필요한 것은 세 수준에서 자란다. 문장 안에서는 넣어도 빠져도 그만인 단어를 제거한다. 문단 안에서는 같은 말을 반복하는 문장을 제거한다. 문서 안에서는 독자가 이미 아는 정보를 과감히 생략한다.

단일 책임 원칙이 문서에도 적용된다. 한 문서는 하나의 명확한 목적만 갖는다. 여러 주제를 섞으면 집중력이 흐려진다.

복사-붙여넣기가 가능해야 한다. 템플릿과 코드 블록은 즉시 사용할 수 있게 만든다.


## 계층적 문서화

실무용 문서와 학습용 문서를 분리한다.

실무용 문서는 즉시 사용 가능하게 만든다. 명령어, 템플릿, 체크리스트만 담는다. 배경은 최소화하고 "어떻게"에 집중한다.

학습용 문서는 깊이 있게 만든다. 개념, 원리, 예시를 상세히 다루고 "왜"를 설명한다. 실무 문서와 링크로 연결한다.

이 문서는 학습용이다. 실무에서는 체크리스트만 보면 된다.


## 구조

빠른 참조가 우선이다. 스캔 가능한 구조가 긴 설명보다 낫다.

필수 마크업만 쓴다:
- 제목 (`##`)
- 코드블록 (` ``` `)
- 리스트 (`-`)
- 링크 (`[text](url)`)

불필요한 것들은 제거한다:
- Bold labels (`**레이블**:`)
- 과도한 강조 (`**중요**`, `*강조*`)
- 장식용 구분선 (`---`)
- 복잡한 테이블

예외가 있다. 나쁜/좋은 예 라벨은 사용 가능하다. 구조를 잡는 데 필요하다.


## 문체

서술형 중심으로 쓴다. 리스트는 항목 나열이 불가피할 때만 사용한다.

레이블 없이 흐름 있게 쓴다. "핵심:", "왜:", "문제:", "해결:" 같은 레이블을 제거하고 문장으로 자연스럽게 이어간다. 참조용 항목 분류는 예외다.

문체는 문체.md를 따른다. 내부 문서는 서술체(~한다, ~이다)가 기본이다. 사용자 대면 문서는 해요체나 합니다체를 쓴다.

대화하듯 설명한다. 독자에게 직접 말하는 것처럼 쓰고 형식적인 문어체를 피한다. 소리 내어 읽었을 때 어색하면 고친다.

논리적 흐름을 유지한다. 배경(왜) → 개념(뭔지) → 방법(어떻게) 순서로 쓴다. 독자가 자연스럽게 따라올 수 있게 한다.

문단은 2-3문장으로 짧게 쓴다. 긴 문단은 집중력을 떨어뜨린다. 한 문단 = 하나의 생각.

개념을 정의할 때는 본질만 설명한다. 효과나 이유는 다음 문단에서 분리해서 쓴다.

예시는 실제 사용 사례로 만든다. 추상적인 예시보다 구체적인 나쁜 예/좋은 예가 규칙을 명확하게 보여준다.

### 연결어 활용

연결어가 흐름을 만든다. 문장 사이의 관계를 명확하게 한다.

인과관계: 그래서, 때문에, 덕분에
```
컨텍스트가 너무 크다. 그래서 Agent를 분리한다.
```

대조: 하지만, 반면에, 그러나
```
리스트는 간결하다. 하지만 서술형이 이해하기 쉽다.
```

순서: 먼저, 다음에, 마지막으로
```
먼저 문제를 파악한다. 다음에 해결책을 찾는다. 마지막으로 검증한다.
```

추가: 또한, 게다가, 특히
```
Agent 분리가 효과적이다. 특히 큰 프로젝트에서 더 그렇다.
```

### 리스트 vs 서술형

리스트를 써야 할 때:
- 여러 파일이나 항목을 나열할 때
- 단계별 실행 방법이나 명령어
- 체크리스트
- 옵션이나 선택지

서술형을 써야 할 때:
- 개념 설명, 가이드, 튜토리얼
- 아키텍처 설명
- "왜"와 "어떻게" 설명
- 흐름이나 프로세스 설명
- 문제와 해결책 제시

설명이 필요하면 서술형으로 쓴다. 단순 나열이 필요한 경우만 리스트를 쓴다.

### 쉬운 언어

약어와 전문 용어를 피한다. 써야 하면 첫 등장 시 풀어쓴다. 설명이 필요한 단어는 커뮤니케이션을 방해한다.

새 독자가 용어집 없이 읽을 수 있어야 한다. 모르면서 물어보기 꺼려하는 상황이 최악이다.


## 이름짓기

이름은 그 자체로 완전한 지시문이어야 한다. "{이름}을 적어라"를 말했을 때 올바른 내용이 나오면 좋은 이름이다. "결정을 적어라"는 근거 없이 결론만 나오지만, "근거를 적어라"는 왜, 대안, 추론 과정이 나온다.

파일명, 섹션 제목, 템플릿 빈 칸 모두 이 원칙이 적용된다.

### 파일명

파일명은 한글로 짓는다. 접근성과 명확성이 높아진다.

좋은 예: `배포.md`, `개요.md`, `구조.md`, `흐름.md`

나쁜 예: `deployment.md`, `overview.md`, `project-structure.md`


## 범용성 우선

하드코딩된 경로를 쓰지 않는다. 독자가 자기 환경에 적용할 수 있게 만든다.

나쁜 예:
```bash
cd ~/8_August/electron
npm start
```

좋은 예:
```bash
npm start
```

"메인 프로젝트로 돌아가서 npm start를 실행한다"라고 쓰면 독자가 자기 환경에 맞게 이동한다.

범용 문서는 프로젝트 특화 예시를 쓰지 않는다. 추상적 예시만 쓴다.


## 예시

### 항목 나열

항목을 나열해야 할 때는 짧은 서술 + 리스트를 섞는다.

나쁜 예 (레이블 과다):
```
제외 항목:
목적: 토큰 절약
중요도: 필수

항목 목록:
- node_modules (500K 절약)
- dist/, out/ (50K 절약)
- .cache/, *.log (10K 절약)
```

좋은 예 (서술 + 간결한 리스트):
```
.gitignore는 컨텍스트 관리의 첫 번째 방어선이다.

제외 항목:
- node_modules: 500K 절약 (필수!)
- dist/, out/: 50K 절약
- .cache/, *.log: 10K 절약
```

서술로 맥락을 잡고, 리스트로 항목을 나열한다. 레이블을 줄이고 정보 밀도를 높인다.

### 문제와 해결책

문제와 해결책을 제시할 때도 서술형을 유지한다.

나쁜 예 (레이블 중심):
```
문제: 컨텍스트 사용량 증가
원인: 전체 프로젝트 로드
영향: 성능 저하, 비용 증가

해결책: Agent 분리
방법: 단계별 agent 사용
효과: 70% 토큰 절약
```

좋은 예 (서술형):
```
전체 프로젝트를 한 번에 로드하면 컨텍스트가 너무 커진다. 80K를 넘어가면
성능이 떨어지고 비용이 급증한다. 특히 간단한 작업에도 전체 구조가 필요하지
않은데 모두 로드하는 건 낭비다.

Agent를 단계별로 분리하면 이 문제를 해결할 수 있다. Demo 작업에는 demo-developer만
쓰고, Feature 통합에는 feature-integrator만 쓴다. 이렇게 하면 70% 토큰을 절약하면서도
작업 품질은 유지된다.
```

문제의 맥락과 해결책의 근거가 명확하다.

### 문단 구성

문단은 짧게 쓴다. 하나의 생각 = 하나의 문단.

나쁜 예 (긴 문단):
```
Agent 시스템은 컨텍스트를 효율적으로 관리하는 방법이다. 전체 프로젝트를 한 번에
로드하면 80K를 넘어가서 성능이 떨어진다. 비용도 많이 든다. 간단한 작업에도
전체 구조가 로드되는 건 낭비다. 그래서 Agent를 단계별로 분리한다. Demo 작업에는
demo-developer만 쓰고, Feature 통합에는 feature-integrator만 쓴다.
```

좋은 예 (짧은 문단):
```
Agent 시스템은 컨텍스트를 효율적으로 관리하는 방법이다.

전체 프로젝트를 한 번에 로드하면 80K를 넘어가서 성능이 떨어진다. 비용도 많이 든다.
간단한 작업에도 전체 구조가 로드되는 건 낭비다.

Agent를 단계별로 분리하면 이 문제를 해결할 수 있다. Demo 작업에는 demo-developer만
쓰고, Feature 통합에는 feature-integrator만 쓴다.
```

문단이 짧으면 읽기 편하다. 호흡이 자연스럽다.


## 예외: 공개 문서

README, API 문서, 블로그는 다르다. 완전한 마크다운을 쓴다.

존댓말을 쓸 수도 있다. 대상 독자가 일반 사용자라면 격식을 차리는 게 나을 수 있다.

구조가 더 체계적이어야 한다. 목차, 섹션 구분, 예제가 명확해야 한다.

하지만 기본 원칙은 같다. 서술형 중심, 자연스러운 흐름, 짧은 문단은 여전히 유효하다.


## 체크리스트

문서를 쓴 후 확인한다:

### 철학
```
□ 한 문서 = 하나의 목적
□ 5초 안에 핵심 파악 가능
□ 복사 가능한 코드/템플릿
□ 실무용/학습용 구분 명확
□ 내부/공개 문서 구분 명확
□ 잡초 제거 (단어 → 문장 → 정보)
```

### 구조
```
□ 최소 마크업 (##, ```, -, link만)
□ 강조 표시 최소화 (bold, italic)
□ 하드코딩된 경로 금지
□ 범용 문서는 추상적 예시만
```

### 문체
```
□ 서술형 중심 (리스트 최소화)
□ 레이블 제거 (참조 분류는 예외)
□ 반말 사용 (~한다, ~이다)
□ 대화하듯 설명 (소리 내어 읽어도 자연스러움)
□ 쉬운 언어 (약어/전문 용어 피하기, 쓰면 풀어쓰기)
□ 연결어로 흐름 연결
□ 논리적 흐름 — 배경(왜) → 개념(뭔지) → 방법(어떻게)
□ 문단 2-3문장
□ 개념 정의는 본질만 (효과 분리)
□ 실제 사용 사례 예시
```

### 이름짓기
```
□ 이름이 그 자체로 완전한 지시문
□ 한글 파일명 사용
```
