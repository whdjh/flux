- `reference/병렬작업.md` — worktree로 feature 병렬 개발하는 방법


## 만드는 법

### 두 레이어

이 워크플로우에는 두 레이어가 있다. 혼동하면 에이전트를 잘못 쓴다.

보일러플레이트 레이어는 레시피 자체를 만드는 흐름이다. 1회성이다. scope-finder로 스코프를 검증하고, recipe-builder로 골격을 만들고, 필요하면 folder-planner로 폴더 구조를 설계하고, recipe-checker로 완성도를 확인한다. 이 레이어는 agentic-boilerplate 저장소 안에서만 일어난다.

프로젝트 레이어는 레시피를 써서 실제 프로젝트 문서를 만드는 흐름이다. 프로젝트마다 반복한다. folder-planner로 구조를 설계하고, project-init으로 초기화하고, guide-filler로 문서를 채우고, recipe-checker로 검증한다. 기능이 많으면 feature-decomposer로 쪼개고 prompt-builder로 프롬프트를 만든다.

```
보일러플레이트 레이어 (1회성):
  scope-finder → recipe-builder → [folder-planner] → recipe-checker
  naming-advisor (수시)

프로젝트 레이어 (프로젝트마다):
  [folder-planner] → project-init → (에센스 수집) → guide-filler → recipe-checker
  feature-decomposer → prompt-builder (병렬 구현 시)
  context-writer (매 세션)
  planner, tdd-guide, code-reviewer (개발 중)
```


### 프로젝트 파이프라인

새 프로젝트를 시작하면 이 순서를 따른다.

```
 1. [folder-planner]        → 프로젝트 폴더/파일 구조 설계
 2. project-init          → 프로젝트 초기화 (CLAUDE.md, context/, .gitmessage.txt)
 3. 에센스 수집 (수동)      → guides/{topic}/에센스/에 넣기
 4. guide-filler          → 레시피 + 에센스 → 문서 생성
 5. recipe-checker        → 문서 완성도 검증
 6. 요구사항 정리         → 요구사항/레시피로 기능명세 작성
        ↓ (기능이 많으면)
 7. feature-decomposer   → work units 분해
 8. prompt-builder        → 프롬프트 + worktree/merge 명령어
 9. tmux + worktree       → 병렬 실행
        ↓ (각 세션에서)
10. planner → tdd-guide → code-reviewer → 커밋
        ↓ (세션 종료)
11. context-writer        → context/MMDD.md 기록
```

1단계에서 folder-planner가 프로젝트 폴더/파일 구조를 설계한다. 구조 설계(어떤 폴더와 파일이 필요한가)와 구조 생성(실제로 만들기)을 분리해서 설계를 먼저 검토할 수 있게 한다.

2단계에서 project-init이 CLAUDE.md {TODO} 골격, context/, .gitmessage.txt를 만든다. folder-planner가 설계한 구조는 folder-planner 자체가 confirmed 후 생성한다. 4단계에서 guide-filler가 에센스로 {TODO}를 채운다.

3단계는 사람이 한다. 클라이언트 요청서, 회의록, 레퍼런스, 브랜드 가이드라인 등 AI가 읽을 에센스를 수집한다. 각 레시피의 "필요한 에센스" 체크리스트가 뭘 모아야 하는지 안내한다.

4단계에서 guide-filler가 레시피를 읽고 에센스를 적용해서 실제 문서를 만든다. 5단계에서 recipe-checker가 빠진 에센스나 미완성 섹션이 없는지 검증한다.

7-9단계는 기능이 많아서 병렬 작업이 필요할 때만 탄다. 단일 기능이면 6단계 후 10단계로 바로 간다.

판단 기준:
- 기능 1-2개, 파일 7개 이하 → 단일 세션 (7-9단계 스킵)
- 기능 3개 이상 또는 파일 8개 이상 → 병렬 (7-9단계)
- 파일 수정 없는 분석/리뷰 → Agent Teams


### 기능 개발 흐름

단일 기능은 한 세션에서 처리한다.

```
요구사항 확인
    ↓
feature-map 노드 생성 (복잡한 경우)
    ↓
planner 에이전트로 계획
    ↓
TDD로 구현 (테스트 먼저)
    ↓
code-reviewer로 리뷰 → (선택) codex_review로 교차 리뷰
    ↓
커밋 + PR
```

codex_review는 다른 모델의 관점으로 리뷰한다. Claude가 리뷰할 코드를 직접 전달하므로 맥락 손실이 없다. code-reviewer 후 보안이나 성능에 대한 second opinion이 필요할 때 쓴다.

병렬 개발이 필요하면 worktree를 활용한다. 아래 '병렬 작업' 섹션 참조.


### 에이전트 활용

에이전트 출처가 두 가지다. 호출 방식이 다르다.

everything-claude-code 에이전트 (플러그인 제공, `everything-claude-code:` 접두사):

| 상황 | 에이전트 |
|------|----------|
| 복잡한 기능 시작 | planner |
| 코드 작성 후 | code-reviewer |
| 새 기능/버그 수정 | tdd-guide |
| 아키텍처 결정 | architect |
| 보안 관련 코드 | security-reviewer |
| 빌드 실패 | build-error-resolver |

커스텀 에이전트 (`~/.claude/agents/`, 이름으로 직접 호출):

| 상황 | 에이전트 |
|------|----------|
| 프로젝트 초기 구조 | project-init |
| 폴더/파일 구조 설계 | folder-planner |
| 레시피 + 에센스 → 문서 생성 | guide-filler |
| 스코프 정의 | scope-finder |
| 가이드 골격 생성 | recipe-builder |
| 가이드 완성도 검증 | recipe-checker |
| 기능 분해 (병렬 작업) | feature-decomposer |
| 세션 프롬프트 생성 | prompt-builder |
| 이름 검토 | naming-advisor |
| 맥락 축적 (세션 종료) | context-writer |

에이전트는 병렬 실행이 가능하다. 독립적인 분석은 동시에 돌린다.


#### 체이닝 패턴

에이전트를 단독으로 쓰기보다 체이닝으로 쓰는 경우가 많다.

프로젝트 시작:
```
[folder-planner] → project-init → (에센스 수집) → guide-filler → recipe-checker
```

가이드 작성 (보일러플레이트 레이어):
```
scope-finder → recipe-builder → [folder-planner] → recipe-checker
```

가이드 신규 작성 (레시피 없을 때, docs 브랜치):
```
scope-finder → recipe-builder → [folder-planner] → (에센스 수집) → guide-filler → recipe-checker
```

단일 기능 개발:
```
planner → tdd-guide → code-reviewer → 커밋 → context-writer
```

병렬 기능 개발:
```
feature-decomposer → prompt-builder → (worktree + tmux)
```

읽기 중심 분석 (Agent Teams):
```
Lead → security-reviewer + code-reviewer + architect (동시)
```


### 병렬 작업

하나의 Claude Code 세션이 모든 기능을 순서대로 처리하면 컨텍스트가 쌓이고 품질이 떨어진다. git worktree + tmux로 기능별 독립 세션을 병렬 실행하면 각 세션의 컨텍스트를 작게 유지할 수 있다.

전체 흐름:

```
(선택) docs 분리 — orphan branch + worktree (reference/컨텍스트-분리.md)
    ↓
기능 목록
  ↓ feature-decomposer
work units + 페이즈 순서
  ↓ prompt-builder (각 unit)
프롬프트 + worktree 명령어
  ↓ 사람
ghostty + tmux로 병렬 실행
  ↓
Phase 순서로 merge
```

docs 분리는 1회성 사전 준비다. 문서(context/, feature-map/)를 orphan branch로 분리하면 코드 세션의 컨텍스트가 줄어든다. 프로젝트가 작으면 생략해도 된다.


#### 페이즈 구조

기능을 쪼갤 때 "무엇을 병렬로 돌릴 수 있는가"보다 "무엇이 공유 의존성인가"를 먼저 파악한다.

여러 기능이 같은 파일(types, stores, API)을 건드리면 머지 충돌이 생긴다. 공유 의존성을 Phase 1에서 먼저 처리하면 Phase 2에서 각 기능이 독립적으로 작업할 수 있다.

```
Phase 1 (순차): 공유 인프라
  → types, API 계약, store 인터페이스
  → 여러 기능이 함께 쓸 기반

Phase 2 (병렬): 독립 구현
  → Phase 1 위에서 각 feature 작업
  → worktree별 독립 세션

Phase 3 (순차): 통합
  → merge, 충돌 해결, 통합 테스트
```


#### Work Unit 포맷

feature-decomposer가 출력하고 prompt-builder가 입력으로 받는 형식이다. 두 에이전트의 인터페이스.

```markdown
# Decomposition: {제목}

project: {프로젝트 디렉토리명}
base-branch: {워크트리 기준 브랜치}

## Phase 1: 공유 인프라 (순차)
### unit-0: {제목}
- branch: phase1/{name}
- files_modify: [수정할 파일]
- files_create: [생성할 파일]
- files_readonly: [참고만 — 건드리지 마]
- depends_on: []
- description: {2-3줄}
- pattern_ref: {참고할 기존 코드 경로}
- open_questions: [미확인 사항 — 작업 전 확인 필요]
- size: ~{N}파일, ~{N}줄

## Phase 2: 독립 구현 (병렬)
### unit-1: {제목}
- branch: feature/{name}
- depends_on: [unit-0]
- ...

## Phase 3: 통합 (순차)
### unit-N: 통합 테스트
- depends_on: [unit-1, unit-2, ...]

## Dependency Graph
unit-0 → unit-1, unit-2
unit-1, unit-2 → unit-N
```

files_modify / files_create / files_readonly 분리가 핵심이다. prompt-builder가 이걸 보고 "이 파일은 수정해라, 이 파일은 참고만 해라, 이 파일은 절대 건드리지 마라"를 프롬프트에 명시한다.


#### 유닛 사이징

Claude Code가 일관된 품질을 유지하는 작업 단위 기준이다. 초기값이며, 실제 사용 후 조정한다.

```
기본:           3-8 파일, 200-500줄
패턴 참조 가능:  상한 완화 (~10 파일, ~700줄)
패턴 없음:      하한 강화 (3-5 파일, 200-300줄)
```

"패턴 참조 가능"은 비슷한 코드가 이미 존재하는 경우다. 다른 Admin 탭을 보고 새 탭을 만드는 상황이면 파일 수가 많아도 품질이 유지된다. 패턴 없이 새로 만드는 경우는 더 작게 쪼갠다.

첫 unit이 패턴을 만들면 후속 unit은 "패턴 있음"으로 전환된다.


#### Worktree + tmux 명령어

```bash
# Phase 1: 공유 인프라
git worktree add -b phase1/shared ../{project}-shared dev
tmux new-session -d -s shared -c ../{project}-shared
tmux send-keys -t shared 'claude' Enter

# Phase 2: 독립 구현 (Phase 1 완료 후)
tmux kill-session -t shared 2>/dev/null
git merge phase1/shared  # dev에 Phase 1 반영
git worktree remove ../{project}-shared  # Phase 1 워크트리 정리
git worktree add -b feature/unit-1 ../{project}-unit-1 dev
git worktree add -b feature/unit-2 ../{project}-unit-2 dev
tmux new-session -d -s unit-1 -c ../{project}-unit-1
tmux new-session -d -s unit-2 -c ../{project}-unit-2
tmux send-keys -t unit-1 'claude' Enter
tmux send-keys -t unit-2 'claude' Enter

# 모니터링
tmux list-sessions
tmux attach -t unit-1

# Phase 3: 통합 (모든 Phase 2 완료 후)
cd {project}
git merge feature/unit-1
git merge feature/unit-2
# 충돌 해결 후 통합 테스트

# 정리 (tmux 세션 + worktree)
tmux kill-session -t unit-1 2>/dev/null
tmux kill-session -t unit-2 2>/dev/null
git worktree remove ../{project}-unit-1
git worktree remove ../{project}-unit-2
git worktree prune
```


#### Agent Teams (대안)

Claude Code의 Agent Teams 기능은 세션 오케스트레이션을 자동화한다. Lead 세션이 Teammate를 생성하고 공유 task list + 메시지로 조율한다.

worktree가 **파일 격리**(같은 파일을 동시 수정 방지)를 해결한다면, Agent Teams는 **세션 조율**(프롬프트 붙여넣기, 모니터링, merge 지시)을 해결한다.

```
worktree + tmux:     파일 격리 ✓  세션 조율 수동
Agent Teams:         파일 격리 ✗  세션 조율 자동
```

사용 시점:
- 리서치/리뷰 (파일 수정 없음) → Agent Teams
- 구현 (파일 수정 있음) → worktree + tmux
- 읽기 중심 탐색 (코드 분석, 버그 조사) → Agent Teams

설정: `settings.json`에 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` 추가. experimental 기능이다.

```
Create an agent team to review this codebase from different angles:
- One focused on security
- One checking performance
- One validating test coverage
```

Lead가 자동으로 teammate를 생성하고 task를 배정한다. `Shift+Up/Down`으로 teammate 전환, `Shift+Tab`으로 delegate 모드(Lead가 코드를 직접 건드리지 않음).


#### 공유 의존성 관리

공유 의존성은 여러 기능이 동시에 수정해야 하는 파일이다. 프론트엔드에서 흔한 예:

```
stores/     → 여러 페이지가 같은 store 사용
types/      → 여러 컴포넌트가 같은 타입 참조
services/   → API 클라이언트를 여러 기능이 호출
App.tsx     → 라우트 추가
```

관리 전략:
- feature-decomposer가 import 그래프를 분석해서 공유 파일을 식별한다
- 공유 파일 수정은 Phase 1에 몰아넣는다
- Phase 2의 각 unit은 Phase 1에서 만든 타입/API를 사용만 한다 (수정하지 않음)
- 불가피하게 공유 파일을 건드려야 하면 files_modify에 명시하고, 다른 unit의 files_readonly에도 넣어서 충돌 위험을 표시한다


### 맥락 관리

AI와 협업할 때 맥락 유실이 가장 큰 비용이다. 네 가지를 결정한다.

어디에 저장하는가:
- `CLAUDE.md` — 프로젝트 상시 맥락 (빌드, 아키텍처, 컨벤션)
- `context/MMDD.md` — 날짜별 맥락 (한 것/근거/할 것)
- `context/메모.md` — 미분류 신호 (비구조, 임시 버퍼)
- `feature-map/nodes/` — 기능별 설계 근거

언제 기록하는가:
- 세션 시작: 이전 context/ 확인, 메모.md 분류
- 세션 중: 중요 결정은 즉시 기록
- 세션 종료: context-writer 에이전트로 context/MMDD.md 생성 (한 것/근거/할 것)


#### 맥락 라우팅

"이 맥락을 어디에 넣을까?"는 기본 연산(에센스, 스코프, 구조, 이름, 대화)의 적용이다. 북마크 폴더를 정리하는 것과 같다. 고정된 분류표가 아니라, 현재 문서 구조가 라우팅을 결정한다. 여섯 번째 연산(맥락 갱신)이 이 흐름을 반복적으로 트리거한다.

```
맥락 입력
  ↓ 에센스: 이 맥락이 뭔가?
  ↓ 스코프: 어떤 범위에 속하나?
  ↓ 구조:   기존 문서에 맞는 곳이 있나?
  │   ├── 있다 → 해당 섹션에 삽입
  │   └── 없다 → 새 섹션/파일 생성 (이름: naming-advisor)
  ↓ 대화:   사용자 컨펌
  └── 루프:  수정 후 반복
```

목적지는 고정이 아니다. CLAUDE.md에 아키텍처 섹션이 있으니까 아키텍처 맥락이 거기로 가는 거지, "아키텍처"라는 분류가 먼저 있는 게 아니다. 문서 구조가 잘 잡혀 있을수록 라우팅 정확도가 올라가는 자기강화 루프다.

확신이 없으면 메모.md에 넣는다. 다음 세션 시작 시 분류한다.

어떻게 분리하는가:
- 코드와 문서가 커지면 orphan branch + worktree로 분리한다 (reference/컨텍스트-분리.md 참조)
- 컨텍스트가 길어지면 AI가 중간 정보를 놓친다
- 코드 세션과 문서 세션을 다른 창에서 연다
- 병렬 작업 시 docs 분리를 먼저 하면 각 worktree 세션의 컨텍스트가 더 작아진다

모델 간 맥락 전달 (Codex MCP 사용 시):

Codex에 위임하면 CLAUDE.md, rules/, 세션 히스토리가 전달되지 않는다. 네 번째 종류의 맥락 분리다.

```
세션 간 맥락 (context/MMDD.md)        ← 시간축 분리
문서-코드 맥락 (orphan branch)        ← 관심사 분리
병렬 세션 맥락 (Phase 1 공유)         ← 공간 분리
모델 간 맥락 (context 필드)           ← 도구 분리
```

위임 시 판별 기준: "프로젝트 컨벤션 없이도 그대로 쓸 수 있는 코드인가?" Yes면 위임, No면 직접 처리. 회색지대에서 context 필드로 맥락을 보완하려는 시도는 비용 대비 효과가 낮다 — 직접 하는 게 낫다.

codex_review는 예외다. Claude가 코드를 전달하므로 맥락 손실이 없고, 다른 모델의 관점이라는 고유한 가치가 있다.


### 팀 협업

```
스프린트 시작: 요구사항 → 기능명세 분리
              ↓
개발: 각자 feature 브랜치 (worktree 활용 가능)
      ↓
PR: code-reviewer → 팀원 리뷰
      ↓
머지: main 브랜치
      ↓
스프린트 종료: 진행현황.md 업데이트
```

충돌 방지: 백엔드는 기능별 라우터 파일, 프론트엔드는 기능별 pages/ 하위 폴더로 분리한다.
