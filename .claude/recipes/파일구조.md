# 레시피

조직 원칙 · 프로젝트 트리 · 주요 경로 · 네이밍 규칙 · 깊이 제한 · 특수 파일 · 모노레포 구조

## 필요한 에센스

- [ ] 프로젝트 유형 (웹, 모바일, CLI, API, 라이브러리, 모노레포)
- [ ] 기술 스택 결정사항 (프론트엔드/백엔드/인프라 — 스택 가이드 참조)
- [ ] 아키텍처 스타일 (모놀리식/모듈러 모놀리스/마이크로서비스 — 아키텍처 가이드 참조)
- [ ] 기존 폴더 구조 (이미 프로젝트가 있으면 현재 트리)
- [ ] 팀 규모와 협업 방식 (1인/소규모/대규모, 코드 오너십 범위)
- [ ] 도메인 목록 (주요 기능 영역: 인증, 편집기, 결제 등)
- [ ] 특수 파일 목록 (설정 파일, 환경변수, CI/CD, Docker 등)
- [ ] 배포 환경 (프론트/백 분리 여부, 모노레포 여부)
- [ ] 네이밍 관습 (기존 프로젝트가 따르는 케이스, 언어/프레임워크 컨벤션) - 선택
- [ ] 디자인 시스템 구조 (컴포넌트 조직 방식 — 디자인 가이드 참조) - 선택


## 만드는 법

파일구조는 mkdir이 아니라 분류 체계를 설계하는 일이다. 구조설계원칙의 본질(이것들이 뭔가) → 경계(어떻게 묶는가) → 우선축(어느 것이 첫 번째 깊이인가) 순서를 따른다. 기술 스택과 아키텍처가 결정된 후에 파일구조를 정한다. 스택이 벽돌이고 아키텍처가 설계도라면, 파일구조는 벽돌을 놓을 선반이다.


### 1. 에센스 → 조직 원칙

입력: 에센스의 "프로젝트 유형", "아키텍처 스타일", "팀 규모".

본질과 경계를 먼저 결정한다. 프로젝트에 담길 항목의 유형(소스 코드, 설정, 문서, 자산, 테스트)을 나열하고, 어떤 축으로 묶을지 정한다.

| 프로젝트 유형 | 권장 우선축 | 이유 |
|--------------|-----------|------|
| 웹 앱 (SPA/SSR) | scope-first (기능/도메인별) | 기능 추가·수정 시 한 폴더 안에서 완결 |
| API 서버 | scope-first (도메인별) | 도메인 경계가 곧 모듈 경계 |
| CLI 도구 | essence-first (유형별) | 명령어/유틸/설정이 자연스럽게 분리 |
| 라이브러리 | essence-first (유형별) | src/tests/docs가 명확히 분리 |
| 모노레포 | layer-first (패키지별) | apps/packages가 첫 번째 깊이 |
| 모바일 앱 | scope-first (기능별) | 화면 단위가 작업 단위 |

경계 축을 선택한 후 균등성을 검증한다. 항목을 나눠봤을 때 한 그룹에 70% 이상 몰리면 그 축은 부적절하다. 3-7개씩 고르게 나뉘면 적절한 축이다.

팀 규모도 조직 원칙에 영향을 준다. 1인이면 단순한 구조가 생산성을 높이고, 대규모 팀이면 코드 오너십 경계와 폴더 경계를 일치시켜야 충돌이 줄어든다.

조직 원칙을 2-3 문장으로 요약한다. "이 프로젝트는 {우선축}으로 조직한다. 이유는 {근거}. {보조 결정}."


### 2. 조직 원칙 → 프로젝트 트리

입력: 1단계의 조직 원칙, 에센스의 "기술 스택", "도메인 목록".

조직 원칙에 따라 실제 폴더 트리를 그린다. 루트부터 깊이 2-3까지만 명시하고, 그 아래는 패턴으로 설명한다.

프레임워크가 정해져 있으면 프레임워크의 관례를 존중한다. Next.js는 `app/`, Nuxt는 `pages/`, NestJS는 모듈 기반이다. 관례를 무시하면 프레임워크의 자동 기능(파일 기반 라우팅 등)이 깨진다.

| 스택 | 관례적 구조 | 주의점 |
|------|------------|--------|
| Next.js (App Router) | `app/` 라우팅, `components/`, `lib/` | `app/`은 라우팅 전용, 비즈니스 로직 분리 |
| Nuxt | `pages/`, `composables/`, `server/` | 자동 임포트 규칙 준수 |
| NestJS | 모듈별 폴더 (auth/, editor/) | 모듈당 controller+service+module |
| FastAPI | `app/` 하위 라우터별 분리 | 의존성 주입 구조 반영 |
| Go | 패키지 = 폴더 | `internal/`로 외부 노출 제한 |

프레임워크 관례 위에 도메인 경계를 입힌다. scope-first라면 도메인별 폴더가 먼저 오고 그 안에 유형이 들어간다.

```
# scope-first 예시
src/
  {도메인1}/
    components/
    hooks/
    utils/
  {도메인2}/
    components/
    hooks/
    utils/
  shared/
    ui/
    lib/
```

```
# essence-first 예시
src/
  components/
    {도메인1}/
    {도메인2}/
  hooks/
  utils/
  types/
```

트리를 그린 후 "새 도메인이 추가되면 어디에 놓는가"를 테스트한다. 자리가 명확하지 않으면 구조가 불완전하다.


### 3. 트리 → 주요 경로

입력: 2단계의 프로젝트 트리, 에센스의 "기술 스택".

프로젝트에서 자주 접근하는 경로를 테이블로 정리한다. AI와 새 팀원이 "이 파일 어디 있지?"를 즉시 해결할 수 있게 한다.

| 분류 | 정리 대상 |
|------|----------|
| 진입점 | 앱 진입, 서버 진입, 메인 설정 |
| 핵심 비즈니스 | 도메인 로직이 모이는 경로 |
| 공유 자원 | 공통 컴포넌트, 유틸, 타입 |
| 설정 | 빌드, 린트, 테스트, 환경변수 |
| 인프라 | Docker, CI/CD, IaC |
| 문서 | 가이드, ADR, 컨텍스트 |

경로 테이블은 간결하게 유지한다. 10-15개가 적당하다. 모든 파일을 나열하면 트리와 중복되고 유지보수 부담만 커진다.

각 경로에 "이 경로가 없으면 무엇이 안 되는가"를 붙여 역할을 명확히 한다. 역할이 모호한 경로는 구조 재검토 신호다.


### 4. 프레임워크 + 팀 → 네이밍 규칙

입력: 에센스의 "기술 스택", "네이밍 관습", "팀 규모".

파일명과 폴더명의 케이스를 결정한다. 프레임워크/언어마다 관례가 다르다.

| 대상 | 권장 케이스 | 근거 |
|------|-----------|------|
| React 컴포넌트 | PascalCase (`UserProfile.tsx`) | React 관례, JSX와 구분 |
| 일반 TS/JS 파일 | kebab-case (`user-profile.ts`) | URL 안전, OS 호환 |
| Python 모듈 | snake_case (`user_profile.py`) | PEP 8 |
| Go 패키지 | lowercase (`userprofile/`) | Go 관례, 접근 제어와 연동 |
| CSS/스타일 | kebab-case (`user-profile.module.css`) | CSS 관례 |
| 테스트 파일 | 원본 + suffix (`user-profile.test.ts`) | 원본과 1:1 대응 |
| 폴더명 | kebab-case 또는 프레임워크 관례 | 일관성 |

한국어 파일명은 가이드/문서 파일에만 허용한다. 소스 코드와 설정 파일에는 영문을 쓴다. 빌드 도구와 OS 호환성 문제가 있기 때문이다.

네이밍 규칙에서 가장 중요한 건 일관성이다. PascalCase와 camelCase를 섞거나, 같은 유형의 파일을 다른 케이스로 쓰면 혼란이 커진다. 한 가지 패턴을 정하고 예외를 최소화한다.

index 파일 정책도 정한다. barrel export(`index.ts`)를 쓸지, 명시적 파일명을 쓸지 결정한다.

| 전략 | 장점 | 단점 |
|------|------|------|
| barrel export (index.ts) | 임포트 경로 짧음 | 트리 셰이킹 방해, 순환 참조 위험 |
| 명시적 파일명 | 파일 검색 명확, 번들 최적화 | 임포트 경로 길어짐 |

대규모 프로젝트에서는 barrel export가 빌드 성능을 떨어뜨릴 수 있다. 소규모면 편의를 위해 써도 무방하다.


### 5. 프로젝트 규모 → 깊이 제한

입력: 에센스의 "도메인 목록", "팀 규모", 2단계의 프로젝트 트리.

구조설계원칙의 깊이 제한과 그룹핑 시점을 적용한다.

| 프로젝트 규모 | 권장 깊이 | 기준 |
|-------------|----------|------|
| 소규모 (도메인 3개 이하) | 2 | src/{도메인}/ |
| 중규모 (도메인 4-8개) | 3 | src/{도메인}/{유형}/ |
| 대규모 (도메인 9개 이상) | 4 (최대) | src/features/{도메인}/{유형}/ |

깊이 4를 넘으면 경로를 기억하기 어렵다. `src/features/auth/components/forms/LoginForm.tsx`는 깊이 5인데, 이미 탐색이 불편하다.

"flat until proven otherwise" 원칙을 적용한다. 폴더 안에 항목이 7개 이하면 평탄하게 둔다. 8-12개면 이름이 자기 서술적이면 평탄을 유지한다. 13개 이상이면 자연스러운 그룹이 있는지 보고, 각 그룹에 3개 이상 들어갈 때만 하위 폴더를 만든다.

고아 방지도 검증한다. "여기 놓을 데가 없어서 루트에 둔다"는 구조 설계의 실패다. 고아가 생기면 새 그룹이 필요하거나 기존 그룹의 경계가 너무 좁은 것이다.

2단계에서 그린 트리의 각 폴더에 대해 예상 항목 수를 적어보고, 깊이가 적절한지 검증한다.


### 6. 프로젝트 요건 → 특수 파일

입력: 에센스의 "특수 파일 목록", "배포 환경", "기술 스택".

소스 코드 외에 프로젝트 루트나 특정 위치에 놓이는 파일을 정리한다. 이 파일들은 프레임워크나 도구가 특정 위치를 기대하므로 위치를 바꿀 수 없는 경우가 많다.

| 분류 | 파일 예시 | 위치 결정 기준 |
|------|----------|--------------|
| 패키지 매니저 | package.json, pnpm-workspace.yaml | 루트 고정 |
| 빌드 도구 | vite.config.ts, next.config.js, tsconfig.json | 프레임워크가 기대하는 위치 |
| 린트/포맷 | .eslintrc, .prettierrc, biome.json | 루트 또는 패키지별 |
| 환경변수 | .env, .env.local, .env.production | 루트 또는 앱별 |
| Git | .gitignore, .gitmessage.txt | 루트 고정 |
| CI/CD | .github/workflows/, .gitlab-ci.yml | 플랫폼이 기대하는 위치 |
| Docker | Dockerfile, docker-compose.yml | 루트 또는 앱별 |
| 에디터 | .editorconfig, .vscode/ | 루트 고정 |
| AI 컨텍스트 | CLAUDE.md, .claude/ | 루트 고정 |
| 문서 | docs/, guides/ | 프로젝트 관례 |

특수 파일은 "이 파일이 없으면 무엇이 깨지는가"로 필수/선택을 구분한다. 불필요한 설정 파일은 루트를 어지럽힌다.

`.gitignore`에 포함할 패턴도 여기서 정리한다. node_modules, dist, .env.local 같은 기본 패턴은 프레임워크 보일러플레이트가 제공하지만, 프로젝트 특화 패턴(생성된 파일, 캐시 등)은 직접 추가한다.


### 7. 배포 환경 → 모노레포 구조

입력: 에센스의 "배포 환경", "프로젝트 유형", "기술 스택".

모노레포가 아니면 이 섹션은 "해당 없음"으로 남긴다.

모노레포를 쓰는 경우, 패키지 분리 전략을 결정한다.

| 분리 패턴 | 구조 | 적합한 상황 |
|----------|------|------------|
| apps + packages | `apps/{앱}`, `packages/{라이브러리}` | 여러 앱이 공통 패키지를 공유 |
| apps만 | `apps/{앱}` | 앱 간 공유 코드가 적음 |
| packages만 | `packages/{패키지}` | 라이브러리 모음 |

```
# 일반적인 모노레포 구조
{루트}/
  apps/
    {앱1}/           # 프론트엔드
    {앱2}/           # 백엔드
  packages/
    {공유-ui}/       # 공유 컴포넌트
    {공유-config}/   # 공유 설정
    {공유-types}/    # 공유 타입
  turbo.json         # 또는 nx.json
  pnpm-workspace.yaml
```

워크스페이스 도구 선택:

| 도구 | 특징 |
|------|------|
| pnpm workspace | 간단한 의존성 관리, 별도 빌드 오케스트레이션 필요 |
| Turborepo | 빌드 캐싱, 태스크 파이프라인, 증분 빌드 |
| Nx | 의존성 그래프, 영향 분석, 코드 생성기 |

패키지 분리 기준은 "독립적으로 버저닝/배포할 필요가 있는가"다. 공유 코드라도 항상 함께 배포된다면 별도 패키지로 분리할 이유가 없다.

모노레포에서 CI/CD는 변경 감지(affected)를 활용한다. 전체 빌드 대신 변경된 패키지와 그 의존자만 빌드하면 파이프라인 시간이 줄어든다.

## 체크리스트

### 필수
- [ ] 7개 섹션이 모두 다뤄졌는가 (모노레포가 아니면 "해당 없음"으로 명시)
