## 필요한 에센스

- [ ] 클라이언트 요청 (메일, 회의록, PPT)
- [ ] AS-IS 시스템 정보 (있으면)
- [ ] 레퍼런스 (경쟁사, 유사 서비스)
- [ ] 이해관계자 목록 (의사결정자, 사용자, 운영자)
- [ ] 기술적 제약 (인프라, 예산, 일정)
- [ ] 품질 요구사항 (성능, 보안, 접근성 기준)


## 만드는 법

요구사항은 한 번에 확정되지 않는다. 대략적인 것 → 제안 → 컨펌 → 상세 순서로 구체화된다. 컨펌 없이 상세부터 쓰면 뒤집어질 때 전부 다시 써야 한다. 각 단계를 건너뛰지 않는 게 핵심이다.

### 1. 원본 자료 → 분석 문서

클라이언트가 준 자료를 먼저 분석한다. 요약이 아니라 분석이다. 명시적 요구("로그인 기능 필요")와 암묵적 기대("당연히 모바일도 되겠지?")를 구분한다.

```
요구사항/_analysis/
├── 01_원본분석.md      # 클라이언트 자료 요약
├── 02_AS-IS분석.md     # 현재 시스템 분석
└── 03_Gap분석.md       # 요구사항 vs 현재
```


### 2. 비기능 요구사항

기능 외 품질 속성을 정의한다. 기능명세가 "무엇을 하는가"라면, 비기능 요구사항은 "얼마나 잘 하는가"다. 측정 가능해야 한다. "빠르게"가 아니라 "페이지 로드 2초 이내". 측정할 수 없으면 검증할 수 없고, 완료 기준이 없다.

| 영역 | 결정 사항 |
|------|-----------|
| 성능 | 응답 시간, 동시 사용자, 처리량 |
| 보안 | 인증 방식, 데이터 암호화, 접근 제어 |
| 사용성 | 대상 사용자, 접근성 등급, 다국어 |
| 가용성 | 가동 시간, 백업, 복구 시간 |
| 확장성 | 데이터 증가율, 사용자 증가 대응 |


### 3. 우선순위

요구사항 간 중요도와 긴급도를 분류한다. 모든 것이 "상"이면 우선순위가 없는 것과 같다.

분류 기준:
| 등급 | 기준 |
|------|------|
| 필수 | 없으면 서비스 불가 |
| 중요 | 없으면 사용성 저하 |
| 선택 | 있으면 좋음, 후순위 가능 |

Gap분석의 우선순위 컬럼과 연결한다. 기준을 먼저 정의하고, 각 요구사항에 일관되게 적용한다.


### 4. 이해관계자

요구사항의 출처와 승인 주체를 정의한다. 누가 요구했는지, 누가 승인하는지가 명확해야 분쟁이 없다.

| 역할 | 관여 |
|------|------|
| 의사결정자 | 최종 승인, 우선순위 조정 |
| 사용자 | 요구사항 제공, 사용성 검증 |
| 개발자 | 기술 검토, 구현 가능성 판단 |
| 운영자 | 운영 요구사항, 모니터링 기준 |


### 5. 제약사항

예산, 일정, 기술적 제한을 명시한다. 제약사항을 먼저 정리하면 실현 불가능한 요구사항을 조기에 걸러낼 수 있다.

| 분류 | 예시 |
|------|------|
| 일정 | 출시 기한, 마일스톤 |
| 기술 | 기존 시스템 호환, 특정 프레임워크 |
| 인프라 | 서버 사양, 네트워크 환경 |
| 예산 | 개발 비용, 라이선스 |
| 규제 | 법적 요구사항, 인증 |
