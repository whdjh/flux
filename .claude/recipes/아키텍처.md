# 레시피

목표·품질 속성 · 제약 · 컨텍스트·경계 · 컴포넌트 구조 · 런타임 흐름 · 데이터 아키텍처 · 배포 토폴로지 · 횡단 관심사 · 확장 전략 · 아키텍처 결정

## 필요한 에센스

- [ ] 요구사항 문서 (기능 + 비기능 요구사항)
- [ ] 비즈니스 목표 (성공 지표, 핵심 KPI)
- [ ] 품질 속성 우선순위 (성능, 가용성, 보안, 유지보수성 중 상위 3개)
- [ ] 제약 조건 (기술, 조직, 규제, 예산, 일정)
- [ ] 외부 시스템 연동 대상 및 경계 (결제, 인증, 메시지, 데이터 소스)
- [ ] 사용자 그룹과 접근 경로 (웹, 모바일, 관리자, API 클라이언트)
- [ ] 규모 예상 (동시 사용자, 초당 요청, 데이터 양, 성장률)
- [ ] 데이터 특성 (일관성 요구, 트랜잭션 범위, 실시간성)
- [ ] 가용성 요구사항 (목표 SLO, RTO/RPO)
- [ ] 기술 스택 결정사항 (스택 가이드 참조)
- [ ] 기존 시스템 자료 (있다면 현재 구성도, API 명세) - 선택
- [ ] 규제/컴플라이언스 요구 (개인정보, 감사, 데이터 주권) - 선택


## 만드는 법

아키텍처는 "무엇을 만들 것인가"가 아니라 "어떻게 구성할 것인가"의 문제다. 기술 스택이 벽돌이라면 아키텍처는 벽돌을 쌓는 방식이다. 스택 가이드가 개별 기술을 결정한다면, 아키텍처는 그 기술들이 어떻게 연결되고 분리되는지를 결정한다.

arc42와 C4 모델의 관점을 섞어서 쓴다. arc42는 문서의 뼈대(목표 → 제약 → 컨텍스트 → 구조 → 런타임 → 배포 → 횡단 → 결정)를 제공하고, C4는 각 레벨의 시각화(컨텍스트 → 컨테이너 → 컴포넌트 → 코드)를 제공한다.

순서를 지킨다. 목표와 품질 속성을 먼저 확정하지 않으면 이후 모든 결정이 흔들린다. 아키텍처 결정은 마지막에 모인다.


### 1. 요구사항 → 목표·품질 속성

입력: 에센스의 "비즈니스 목표", "요구사항 문서", "품질 속성 우선순위".

비즈니스 목표를 2-3 문장으로 요약한다. "이 시스템이 없으면 무엇이 안 되는가"를 기준으로 쓴다. 기술 언어가 아니라 비즈니스 언어로 쓴다.

품질 속성은 ISO/IEC 25010 기준으로 고른다. 모든 속성을 높일 수는 없으므로 상위 3개만 선택한다. 나머지는 "수용 가능한 수준"으로 남긴다.

| 품질 속성 | 측정 가능한 형태 |
|----------|-----------------|
| 성능 | p95 응답 시간 {n}ms 이하, 처리량 {n} RPS |
| 가용성 | 월간 가동률 {n}%, 장애 복구 시간 {n}분 |
| 확장성 | 동시 접속 {n}명까지 선형 확장 |
| 보안 | OWASP Top 10 대응, 규제 준수 |
| 유지보수성 | 신규 기능 추가 시 평균 {n}일 |
| 관측 가능성 | 장애 원인 식별 평균 {n}분 |

"빠르게", "안정적으로" 같은 모호한 표현은 아키텍처 결정의 근거가 되지 못한다. 반드시 숫자로 바꾼다. 숫자를 모르면 에센스 단계에서 다시 묻는다.

품질 속성 간 트레이드오프도 명시한다. 강한 일관성을 택하면 지연시간이 늘어나고, 높은 가용성을 위해 결과적 일관성을 수용하는 식이다.


### 2. 에센스 → 제약 조건

입력: 에센스의 "제약 조건", "규제/컴플라이언스 요구".

제약은 설계 공간을 줄인다. 제약을 먼저 명시해야 불가능한 대안을 논의하느라 시간을 낭비하지 않는다. 네 가지 유형으로 나눠 기록한다.

| 제약 유형 | 예시 |
|----------|------|
| 기술 | 기존 DB 유지, 특정 언어 고정, 사내 표준 준수 |
| 조직 | 팀 규모, 운영 권한, 외부 호스팅 불가 |
| 규제 | 개인정보보호법, GDPR, 데이터 국내 보관 |
| 예산/일정 | 월 인프라 비용 상한, 런칭 마감일 |

제약은 "바꿀 수 없는 것"이다. "바꿀 수 있지만 비싸다"는 제약이 아니라 트레이드오프다. 둘을 혼동하면 논의가 막힌다.


### 3. 사용자·외부 시스템 → 컨텍스트·경계

입력: 에센스의 "사용자 그룹과 접근 경로", "외부 시스템 연동 대상".

C4 모델의 컨텍스트 다이어그램을 그린다. 시스템을 블랙박스로 두고, 어떤 사용자가 어떻게 접근하며 어떤 외부 시스템과 연결되는지 보여준다.

```
[모바일 사용자]  →
[웹 사용자]      →   {시스템}   →  [결제 게이트웨이]
[관리자]         →                →  [이메일 서비스]
[API 클라이언트] →                →  [외부 데이터 소스]
```

외부 관계마다 방향(인바운드/아웃바운드), 프로토콜(HTTPS, gRPC, 메시지), 인증 방식을 기록한다.

시스템 경계를 명확히 한다. "우리가 만드는 것"과 "외부에 의존하는 것"을 선으로 가른다. 경계 안쪽이 이후 설계 대상이다. 경계 바깥쪽은 의존성으로만 다룬다.


### 4. 경계 → 컴포넌트 구조

입력: 3단계의 컨텍스트, 에센스의 "기술 스택 결정사항".

C4 모델의 컨테이너/컴포넌트 레벨이다. 시스템 내부를 배포 단위(컨테이너)와 그 내부의 논리 단위(컴포넌트)로 나눈다.

먼저 아키텍처 스타일을 결정한다. 스타일은 컴포넌트를 나누고 연결하는 기본 규칙이다.

| 스타일 | 적합한 상황 |
|--------|------------|
| 모놀리식 | 팀 소규모, 단일 배포 단위, 도메인 경계 미성숙 |
| 모듈러 모놀리스 | 모놀리식의 단순함 + 내부 모듈 경계 분리 |
| 마이크로서비스 | 팀 여러 개, 독립 배포 필요, 명확한 도메인 경계 |
| 서버리스/함수 | 트래픽 변동 심함, 이벤트 기반, 무상태 |
| 이벤트 주도 | 비동기 처리, 서비스 간 느슨한 결합 |
| 계층형(Layered) | CRUD 중심, 요청-응답 위주 |
| 헥사고날/포트·어댑터 | 도메인 로직 순수성 유지, 외부 변경 흡수 |

기본 권장은 "모듈러 모놀리스에서 시작해서 필요할 때 분리"다. 처음부터 마이크로서비스로 가는 것은 팀과 운영 역량이 충분할 때만 정당화된다.

스타일이 정해지면 컨테이너와 컴포넌트를 나열한다.

```
컨테이너:
  웹 앱 (브라우저)        - 사용자 UI
  API 서버 (컨테이너)     - 비즈니스 로직
  워커 (컨테이너)         - 비동기 작업
  주 DB (관리형 서비스)   - 영속 저장소
  캐시 (관리형 서비스)    - 세션·핫 데이터

API 서버 내부 컴포넌트:
  HTTP 라우터 → 애플리케이션 서비스 → 도메인 모델 → 저장소 어댑터
```

컨테이너마다 책임, 입출력, 상태 보유 여부를 기록한다. "이 컨테이너가 없어지면 무엇이 안 되는가"로 책임을 검증한다.

컴포넌트 경계는 도메인 경계와 일치시킨다. 폴더 구조, 소스 코드 조직은 구조설계원칙을 따른다.


### 5. 기능 → 런타임 흐름

입력: 에센스의 "요구사항 문서"에서 핵심 시나리오 3-5개, 4단계의 컴포넌트.

핵심 시나리오를 골라 시퀀스 다이어그램이나 흐름 서술로 표현한다. 모든 기능을 그릴 필요는 없다. 품질 속성이 걸리는 경로(성능 중요 경로, 장애 복구 경로)를 우선한다.

시나리오 선정 기준:

| 유형 | 예시 |
|------|------|
| 행복 경로 | 로그인 → 주요 작업 → 저장 |
| 장애 경로 | 외부 API 장애 시 폴백 |
| 비동기 경로 | 이벤트 발행 → 워커 처리 → 결과 반영 |
| 보안 경로 | 인증 실패 → 차단 → 감사 로그 |
| 고부하 경로 | 피크 트래픽 → 캐시 → DB |

시나리오마다 동기/비동기, 타임아웃, 재시도 정책, 실패 시 동작을 명시한다. 타임아웃 없는 외부 호출이 있으면 아키텍처 결함이다.

```
사용자 로그인 시나리오:
  1. 브라우저 → API 서버: POST /login (150ms 타임아웃)
  2. API 서버 → 인증 저장소: 자격 검증
  3. 실패 시: 429면 재시도, 401이면 즉시 반환
  4. 성공 시: 세션 토큰 발급 → 캐시 저장 (TTL {n})
  5. API 서버 → 브라우저: 토큰 반환
```


### 6. 데이터 특성 → 데이터 아키텍처

입력: 에센스의 "데이터 특성", "규모 예상", "가용성 요구사항".

데이터는 아키텍처에서 가장 바꾸기 어려운 부분이다. 컴퓨팅은 쉽게 재배치되지만, 데이터는 마이그레이션 비용이 크다. 처음에 잘 결정한다.

결정할 항목:

| 영역 | 결정 사항 |
|------|-----------|
| 저장소 소유권 | 각 데이터는 하나의 컴포넌트가 소유 (공유 DB 안티패턴 회피) |
| 일관성 모델 | 강한 일관성 / 결과적 일관성 / 세션 일관성 |
| 트랜잭션 경계 | 단일 서비스 트랜잭션 / Saga / 보상 트랜잭션 |
| 읽기/쓰기 분리 | 단일 / 리플리카 읽기 / CQRS |
| 이벤트 소싱 | 상태 저장 / 이벤트 저장 (감사 요구 시) |
| 데이터 파티셔닝 | 수직 분할(도메인) / 수평 분할(샤딩) |
| 캐싱 전략 | Cache-aside / Read-through / Write-through |
| 백업·복구 | 빈도, 보관 기간, RTO/RPO 달성 방법 |
| 데이터 보존 | 기간, 삭제 정책, 아카이빙 |

마이크로서비스를 선택했다면 서비스당 DB가 기본이다. 같은 DB를 여러 서비스가 공유하면 경계가 무너진다.

규모가 커질 때의 경로도 미리 정한다. "수직 확장 → 읽기 리플리카 → 샤딩" 같은 단계별 전략을 기록한다. 지금 당장 샤딩할 필요는 없지만, 샤딩이 가능한 키 설계는 지금 해둔다.


### 7. 제약·품질 → 배포 토폴로지

입력: 1단계의 품질 속성, 2단계의 제약, 4단계의 컨테이너.

컨테이너를 어디에 어떻게 배치할지 결정한다. 스택 가이드가 "어떤 호스팅을 쓰는가"를 결정했다면, 여기서는 "몇 개를, 어느 리전에, 어떻게 격리할지"를 결정한다.

| 영역 | 결정 사항 |
|------|-----------|
| 환경 분리 | 로컬 / 개발 / 스테이징 / 프로덕션 |
| 리전 전략 | 단일 리전 / 다중 리전 / 엣지 |
| 가용 영역 | 단일 AZ / 다중 AZ |
| 네트워크 경계 | 퍼블릭 / 프라이빗 서브넷, VPC 피어링 |
| 로드 밸런싱 | L4 / L7, 헬스체크 정책 |
| 트래픽 관리 | CDN, WAF, 속도 제한 게이트웨이 |
| 인증 경계 | API 게이트웨이 / BFF / 서비스 메시 |
| 비밀 관리 | 시크릿 매니저, 환경변수 주입 경로 |
| 구성 관리 | 환경별 설정 파일 / 원격 설정 서비스 |

배포 단위 구성도를 그린다. 컨테이너 다이어그램에 "어느 노드에서 어느 프로세스가 몇 개 돌아가는지"를 덧붙인 형태다.

```
CDN (글로벌 엣지)
  ↓
WAF / API 게이트웨이 (리전 A)
  ↓
웹 앱 (ECS, 2 AZ × 2 태스크)
  ↓
API 서버 (ECS, 2 AZ × 3 태스크)
  ↓
주 DB (Aurora, Multi-AZ)
캐시 (ElastiCache, Multi-AZ)
```

가용성 목표(1단계)와 실제 토폴로지가 일치하는지 역검증한다. 99.9%를 목표하는데 단일 AZ로 구성하면 숫자가 맞지 않는다.


### 8. 공통 필요 → 횡단 관심사

입력: 1단계의 품질 속성, 4단계의 컴포넌트, 에센스의 "규제/컴플라이언스 요구".

횡단 관심사는 여러 컴포넌트에 공통으로 적용되는 정책이다. 컴포넌트마다 다르게 구현하면 일관성이 깨지고 보안 사고가 난다. 아키텍처 레벨에서 "어디서 책임질지"를 결정한다. 아래 10개 항목은 최소 다뤄야 할 관심사다.

인증은 누가 누구인지 확인하는 관문이다. API 게이트웨이에서 중앙 처리할지, 각 서비스에서 토큰 검증할지, 세션 기반인지 토큰 기반인지 정한다.

로깅은 관측의 기반이다. 구조화 로그 포맷, 필수 필드(요청 ID, 사용자 ID, 레이어), 수집 파이프라인, 보존 기간을 결정한다. 민감 정보 마스킹 규칙이 빠지면 사고로 이어진다.

모니터링은 지표 수집과 알림이다. 골든 시그널(지연, 트래픽, 에러, 포화도)을 어떻게 수집하고, 어떤 임계값에서 누구에게 알리는지 정한다. SLO 기반 경보가 임계값 기반보다 오경보가 적다.

분산 추적은 요청이 여러 컴포넌트를 지나는 경로를 재구성한다. OpenTelemetry 같은 표준을 쓸지, 어느 수집기로 보낼지, 샘플링 비율을 얼마로 할지 정한다. 마이크로서비스에서는 선택이 아니라 필수다.

설정 관리는 환경변수, 기능 플래그, 원격 설정이다. 재시작 없이 바꿀 수 있어야 하는 값이 무엇인지, 설정 변경이 감사 가능한지 정한다. 비밀과 일반 설정을 분리한다.

에러 처리는 어디서 포착하고 어디서 전파하는지의 규칙이다. 도메인 에러와 인프라 에러를 구분하고, 사용자에게 노출할 메시지와 내부 로그만 남길 메시지를 나눈다. 재시도 가능한 에러와 불가능한 에러도 구분한다.

API 버저닝은 외부 계약의 진화 전략이다. URL 버저닝(/v1/), 헤더 버저닝, 미디어 타입 버저닝 중 하나를 고르고, 폐기(Deprecation) 정책과 지원 기간을 정한다.

국제화는 언어와 로케일 처리다. 메시지 카탈로그 위치, 로케일 협상 방식(Accept-Language, URL 경로, 사용자 설정), 시간대와 통화 처리 규칙을 정한다. 한국어만 지원해도 시간대와 통화는 결정해야 한다.

감사는 "누가 언제 무엇을 했는가"를 추적할 수 있게 한다. 감사 로그를 일반 로그와 분리할지, 변조 방지가 필요한지, 보관 기간이 규제로 정해져 있는지 확인한다.

속도 제한은 악용과 과부하를 막는다. 어느 레벨에서(게이트웨이, 서비스), 어떤 키로(IP, 사용자, API 키), 어떤 알고리즘으로(토큰 버킷, 고정 윈도우) 제한할지 정한다. 초과 시 반환 코드와 재시도 헤더도 함께 정한다.


### 9. 규모 예상 → 확장 전략

입력: 에센스의 "규모 예상", 1단계의 품질 속성, 6-7단계의 데이터/배포 결정.

"지금 필요한 것"과 "나중에 필요할 것"을 구분한다. 지금 오버 엔지니어링하지 않되, 나중에 막히지 않는 경로를 남긴다.

| 축 | 전략 |
|----|------|
| 수직 확장 | 인스턴스 크기 상향 (한계 있음, 단순) |
| 수평 확장 | 인스턴스 수 증가 (무상태 컴포넌트 필요) |
| 읽기 확장 | 읽기 리플리카, CDN, 캐시 |
| 쓰기 확장 | 샤딩, 이벤트 소싱, CQRS |
| 기능 분리 | 모놀리스 → 모듈러 → 서비스 분리 |
| 지리적 확장 | 다중 리전, 엣지 컴퓨팅 |

단계별 성장 경로를 기록한다. "현재 규모에서는 X, 10배 규모에서는 Y, 100배에서는 Z" 형태로 쓴다. 이렇게 써두면 언제 다음 단계로 넘어갈지 판단 기준이 생긴다.

```
현재 ({n} DAU):
  모듈러 모놀리스, 단일 DB, Multi-AZ

10배 ({n} DAU):
  읽기 리플리카 추가, 캐시 확장, 인기 모듈 서비스 분리

100배 ({n} DAU):
  샤딩 또는 파티셔닝, 다중 리전, 전용 검색/큐 인프라
```

병목 예상 지점과 모니터링 트리거도 함께 적는다. "DB CPU 70% 지속 시 리플리카 추가" 같은 구체적 조건이 필요하다.


### 10. 주요 선택 → 아키텍처 결정

입력: 1-9단계의 모든 주요 선택.

ADR(Architecture Decision Record) 형식으로 핵심 결정을 기록한다. 아키텍처 문서의 나머지는 시간이 지나면 재생성되지만, ADR은 "왜 이 길을 택했는가"를 보존한다.

ADR 한 개의 구조:

```
제목: {결정 내용을 한 줄로}
상태: 제안 / 수용 / 폐기 / 대체됨
맥락: {이 결정이 필요한 배경과 제약}
결정: {택한 방향}
근거: {왜 이 방향인지, 다른 대안은 왜 안 됐는지}
결과: {따라오는 긍정적/부정적 결과}
```

최소 다뤄야 할 결정 주제:

| 주제 | 예시 |
|------|------|
| 아키텍처 스타일 | 모듈러 모놀리스 선택 이유 |
| 데이터 일관성 모델 | 결과적 일관성 수용 범위 |
| 인증 경계 | 게이트웨이 중앙 인증 vs 서비스별 검증 |
| 통신 방식 | REST vs gRPC vs 메시지 |
| 동기 vs 비동기 | 어떤 작업이 비동기인가 |
| 상태 vs 무상태 | 어디에 상태를 두는가 |
| 트랜잭션 범위 | 경계를 넘는 트랜잭션 처리 방식 |
| 배포 단위 분리 | 언제 서비스를 나누는가 |

"폐기"된 결정도 남긴다. 나중에 같은 논의가 반복될 때 참조가 된다. 결정이 바뀌면 이전 ADR을 "대체됨"으로 표기하고 새 ADR을 추가한다.

- [ ] 핵심 시나리오 3개 이상이 런타임 흐름으로 표현됐는가
