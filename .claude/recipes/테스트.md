# 레시피

테스트 레벨/피라미드 · 테스트 유형 · 커버리지/메트릭 · 테스트 대역 전략 · 테스트 데이터 · 자동화 범위 · 진입/종료 기준 · 리스크 기반 우선순위

이 레시피는 테스트 전략과 방법론을 다룬다. 테스트 도구 선정(Jest, Vitest, Playwright 등)은 스택 레시피의 테스트 섹션에서 결정한다.

## 필요한 에센스

- [ ] 요구사항 문서 (기능 + 비기능 요구사항)
- [ ] 기술 스택 가이드 (스택 레시피 산출물, 테스트 도구 결정)
- [ ] 아키텍처 가이드 (컴포넌트 구조, 런타임 흐름, 외부 의존성)
- [ ] 프로젝트 유형 (웹, 모바일, CLI, API, 데스크톱)
- [ ] 팀 규모와 테스트 경험 (TDD 경험, 자동화 경험)
- [ ] 배포 주기 (일간/주간/월간, CI/CD 파이프라인 유무)
- [ ] 비기능 요구사항 (성능 목표, 가용성 SLO, 보안 등급)
- [ ] 외부 의존성 목록 (결제, 인증, 메시지, DB)
- [ ] 기존 테스트 현황 (있으면 커버리지, 테스트 수, 실패 현황) - 선택
- [ ] 규제/컴플라이언스 요구 (감사 로그, 개인정보, 결제) - 선택


## 만드는 법

테스트 전략은 "무엇을 얼마나 테스트할 것인가"의 문제다. 스택 가이드가 도구를 결정한다면, 이 가이드는 그 도구로 어떤 비율과 기준으로 테스트를 구성할지를 결정한다.

순서를 지킨다. 리스크 분석이 가장 먼저다. 리스크 없이 테스트 비율을 정하면 중요하지 않은 코드에 테스트를 몰아쓰게 된다. 리스크 기반 우선순위가 다른 모든 결정의 토대가 된다.


### 1. 리스크 분석 → 리스크 기반 우선순위

입력: 에센스의 "요구사항 문서", "아키텍처 가이드", "규제/컴플라이언스 요구".

모든 기능을 같은 강도로 테스트하는 건 낭비다. 리스크가 높은 영역에 테스트를 집중하고, 리스크가 낮은 영역은 최소한으로 검증한다.

리스크를 두 축으로 평가한다. 장애 발생 확률(변경 빈도, 복잡도, 외부 의존성)과 장애 영향(사용자 수, 매출 영향, 데이터 손실 가능성)을 곱해서 리스크 점수를 매긴다.

| 리스크 등급 | 기준 | 테스트 강도 |
|------------|------|------------|
| P0 (치명) | 장애 시 서비스 중단 또는 데이터 손실 | 단위 + 통합 + E2E, 커버리지 90%+ |
| P1 (높음) | 핵심 기능 장애, 매출 영향 | 단위 + 통합, 커버리지 80%+ |
| P2 (보통) | 보조 기능 장애, 우회 가능 | 단위, 커버리지 60%+ |
| P3 (낮음) | 시각적/편의 기능, 영향 미미 | 스모크 테스트 또는 수동 |

리스크 매핑 예시:

```
P0: 결제 처리, 인증/인가, 데이터 마이그레이션
P1: 핵심 비즈니스 로직, API 엔드포인트, 상태 관리
P2: UI 인터랙션, 관리자 도구, 보고서
P3: 정적 페이지, 소개 화면, 도움말
```

규제 대상 기능(결제, 개인정보 처리)은 리스크 등급과 무관하게 P0으로 올린다. 감사 추적이 필요한 기능도 마찬가지다.


### 2. 리스크 등급 → 테스트 레벨/피라미드

입력: 1단계의 리스크 매핑, 에센스의 "프로젝트 유형"과 "아키텍처 가이드".

테스트 피라미드는 비용과 속도의 균형이다. 아래층일수록 빠르고 싸고, 위층일수록 느리고 비싸다. 프로젝트 유형에 따라 피라미드 모양이 달라진다.

| 프로젝트 유형 | 권장 비율 (단위:통합:E2E) | 근거 |
|-------------|--------------------------|------|
| API 서버 | 60:30:10 | 비즈니스 로직 중심, UI 없음 |
| 웹 앱 (SPA) | 50:30:20 | 사용자 흐름 검증 비중 높음 |
| 웹 앱 (SSR) | 50:25:25 | 서버/클라이언트 양쪽 검증 |
| 모바일 앱 | 40:30:30 | 디바이스 파편화, E2E 비중 높음 |
| CLI 도구 | 70:20:10 | 함수 단위 테스트 효율 높음 |
| 라이브러리/패키지 | 80:15:5 | 공개 API 계약 중심 |
| 데이터 파이프라인 | 40:40:20 | 시스템 간 통합 비중 높음 |

비율은 출발점이다. 1단계의 리스크 매핑으로 조정한다. P0 영역에 외부 연동이 많으면 통합 테스트 비율을 높이고, P0 영역이 순수 계산 로직이면 단위 테스트 비율을 높인다.

레벨별 범위:

단위 테스트는 하나의 함수, 하나의 클래스를 격리 상태에서 검증한다. 외부 의존성은 모두 테스트 대역으로 교체한다. 실행 시간은 개별 테스트 10ms 이하가 목표다.

통합 테스트는 두 개 이상의 컴포넌트가 함께 동작하는지 검증한다. DB, 캐시, 메시지 큐 같은 인프라를 실제로 띄우거나 테스트용 인스턴스를 사용한다. API 엔드포인트 테스트가 대표적이다.

E2E 테스트는 사용자 관점에서 전체 시스템을 검증한다. 브라우저 자동화(웹), 디바이스 시뮬레이터(모바일), CLI 실행(도구)으로 수행한다. P0 시나리오만 커버한다.


### 3. 시나리오 → 테스트 유형

입력: 에센스의 "요구사항 문서", "비기능 요구사항", 1단계의 리스크 매핑.

테스트 레벨(어디서)과 테스트 유형(무엇을)은 다른 축이다. 레벨이 수직 깊이라면 유형은 수평 관심사다.

| 유형 | 검증 대상 | 적용 시점 |
|------|----------|----------|
| 기능 테스트 | 요구사항 충족 여부 | 모든 프로젝트 |
| 회귀 테스트 | 기존 기능이 변경 후에도 동작 | 모든 프로젝트 |
| 스모크 테스트 | 핵심 경로가 기본적으로 동작 | 배포 직후 |
| 성능 테스트 | 응답 시간, 처리량, 자원 사용 | 비기능 요구사항에 성능 목표 있을 때 |
| 부하 테스트 | 예상 최대 부하에서의 동작 | 동시 사용자 목표가 있을 때 |
| 보안 테스트 | 취약점, 인증 우회, 인젝션 | 사용자 입력/인증/결제 있을 때 |
| 접근성 테스트 | WCAG 준수, 키보드/스크린리더 | 웹 앱, 사용자 대면 |
| 호환성 테스트 | 브라우저/디바이스/OS 간 동작 | 웹/모바일, 다중 환경 |
| 계약 테스트 | 서비스 간 API 계약 유지 | 마이크로서비스, 외부 API 연동 |
| 스냅샷 테스트 | UI 렌더링 결과 변경 감지 | 컴포넌트 라이브러리 |

프로젝트별 필수 유형:

| 상황 | 필수 유형 |
|------|----------|
| 모든 프로젝트 | 기능, 회귀, 스모크 |
| 성능 SLO가 있으면 | + 성능, 부하 |
| 사용자 인증이 있으면 | + 보안 |
| 사용자 대면 웹이면 | + 접근성, 호환성 |
| 마이크로서비스면 | + 계약 |
| UI 컴포넌트 라이브러리면 | + 스냅샷 |


### 4. 요구사항 → 커버리지/메트릭

입력: 1단계의 리스크 등급, 에센스의 "배포 주기", "팀 규모".

커버리지는 수단이지 목적이 아니다. 100% 커버리지여도 잘못된 어설션이면 버그를 못 잡는다. 의미 있는 커버리지를 추적한다.

전체 프로젝트 커버리지 목표:

| 상황 | 목표 | 근거 |
|------|------|------|
| 신규 프로젝트, 팀 TDD 경험 있음 | 80% | 높은 기준으로 시작 |
| 신규 프로젝트, 팀 TDD 경험 없음 | 60% → 점진 증가 | 무리하면 형식적 테스트만 늘어남 |
| 레거시 프로젝트 | {현재}% → +5%/스프린트 | 점진적 개선, 새 코드는 80% |
| 라이브러리/공개 패키지 | 90% | 외부 사용자 신뢰 |

커버리지 유형별 우선순위:

라인 커버리지(line coverage)가 기본이다. 측정이 쉽고 CI에 통합하기 좋다. 하지만 라인 커버리지만으로는 분기 누락을 잡지 못한다.

브랜치 커버리지(branch coverage)가 실질적이다. if/else, switch, 삼항 연산의 모든 분기를 커버하는지 확인한다. P0 영역에는 브랜치 커버리지를 추적한다.

추적할 메트릭:

| 메트릭 | 측정 방법 | 목표 |
|--------|----------|------|
| 라인 커버리지 | CI 리포트 | {목표}% |
| 브랜치 커버리지 | CI 리포트 (P0 영역) | {목표}% |
| 테스트 실행 시간 | CI 파이프라인 | 단위 {n}분, 전체 {n}분 |
| 불안정 테스트(flaky) 비율 | 실패 로그 분석 | 0% 목표 |
| 테스트 대 코드 비율 | LOC 비교 | 참고용 (강제하지 않음) |

커버리지 게이트를 CI에 설정한다. PR이 커버리지 목표를 충족하지 못하면 머지를 차단한다. 단, 전체 커버리지가 아닌 변경된 코드의 커버리지를 게이트로 사용하면 레거시 코드가 발목을 잡지 않는다.


### 5. 아키텍처 → 테스트 대역 전략

입력: 에센스의 "아키텍처 가이드" (컴포넌트 구조, 외부 의존성), "외부 의존성 목록".

테스트 대역(test double)은 실제 의존성을 대체하는 객체다. 어떤 의존성에 어떤 대역을 쓸지 아키텍처 수준에서 결정한다.

| 대역 종류 | 용도 | 적합한 상황 |
|----------|------|------------|
| Stub | 정해진 값을 반환 | 외부 API 응답, 설정값 |
| Mock | 호출 여부와 인자를 검증 | 이벤트 발행, 알림 전송 |
| Fake | 단순화된 실제 구현 | 인메모리 DB, 로컬 파일 시스템 |
| Spy | 실제 구현 + 호출 기록 | 로깅, 메트릭 수집 검증 |
| Fixture | 고정 테스트 데이터 | DB 시드, API 응답 파일 |

의존성별 대역 전략:

| 의존성 | 단위 테스트 | 통합 테스트 | E2E 테스트 |
|--------|-----------|-----------|-----------|
| 데이터베이스 | Fake (인메모리) | 테스트 DB (Docker) | 실제 DB (스테이징) |
| 외부 API | Stub | Mock 서버 (MSW, WireMock) | 실제 또는 Sandbox |
| 메시지 큐 | Mock | 테스트 인스턴스 | 실제 인스턴스 |
| 파일 시스템 | Fake (인메모리) | 임시 디렉토리 | 실제 |
| 시간/날짜 | Stub (고정 시간) | Stub (고정 시간) | 실제 |
| 인증 | Stub (토큰 하드코딩) | Mock 인증 서버 | 실제 인증 |

대역 사용 원칙:

테스트 대역은 격리를 위해 쓴다. "테스트가 느려서"가 아니라 "이 의존성의 동작이 테스트 결과를 비결정적으로 만들어서" 대역을 쓴다.

대역의 계약을 유지한다. 실제 API가 바뀌었는데 Stub은 옛날 응답을 반환하면 거짓 양성이다. 계약 테스트(3단계)로 대역과 실제의 괴리를 잡는다.

Mock 남발을 경계한다. Mock이 많아지면 "테스트는 통과하는데 프로덕션에서 터지는" 상황이 온다. 통합 테스트에서 실제 인프라를 쓰는 이유가 여기에 있다.


### 6. 시나리오 → 테스트 데이터

입력: 에센스의 "요구사항 문서", "규제/컴플라이언스 요구", 5단계의 대역 전략.

테스트 데이터는 세 가지 전략으로 관리한다. 프로젝트 규모와 데이터 민감도에 따라 선택한다.

| 전략 | 설명 | 적합한 상황 |
|------|------|------------|
| 정적 시드 | 고정 데이터셋을 SQL/JSON으로 관리 | 소규모, 단순 스키마 |
| 팩토리 패턴 | 코드로 테스트 데이터를 생성 | 중규모, 복잡한 관계 |
| 프로덕션 복제 | 프로덕션 데이터를 익명화해서 복제 | 대규모, 현실적 시나리오 필요 |

팩토리 패턴이 가장 범용적이다. 테스트마다 필요한 데이터를 최소한으로 생성하고, 테스트 간 데이터 의존을 없앤다.

```
// 팩토리 패턴 예시 (의사 코드)
createUser({ name: "테스트", role: "admin" })
createOrder({ user: user, items: 3 })
```

데이터 격리 규칙:

각 테스트는 자기 데이터를 만들고 자기가 정리한다. 다른 테스트의 데이터에 의존하면 실행 순서에 따라 결과가 달라진다. 트랜잭션 롤백(단위), 테스트 DB 초기화(통합), 전용 계정(E2E)으로 격리한다.

민감 데이터 처리:

| 데이터 유형 | 테스트 환경 전략 |
|------------|----------------|
| 개인정보 (이름, 연락처) | 가짜 데이터 생성 (Faker) |
| 결제 정보 | Sandbox API 전용 테스트 카드 |
| 인증 토큰 | 테스트 전용 토큰, 환경변수 관리 |
| 비즈니스 데이터 | 익명화 후 사용, 또는 합성 데이터 |

규제 대상 프로젝트에서는 프로덕션 데이터를 테스트에 사용하면 안 된다. 합성 데이터나 익명화 파이프라인을 구축한다.


### 7. 배포 주기 → 자동화 범위

입력: 에센스의 "배포 주기", "팀 규모", 에센스의 "기술 스택 가이드" (CI/CD 파이프라인).

자동화 범위는 "무엇을 CI에서 돌리고 무엇을 수동으로 하는가"의 결정이다. 전부 자동화하는 게 이상적이지만 비용이 든다. 리스크와 비용의 균형을 잡는다.

| 테스트 유형 | 자동화 여부 | 실행 시점 |
|-----------|-----------|----------|
| 단위 테스트 | 필수 자동화 | PR마다 |
| 통합 테스트 | 필수 자동화 | PR마다 |
| E2E 테스트 (P0) | 필수 자동화 | main 머지 시 |
| E2E 테스트 (P1-P2) | 권장 자동화 | 야간/주간 스케줄 |
| 성능 테스트 | 자동화 권장 | 릴리스 전, 주간 |
| 보안 테스트 | 의존성 스캔 자동화, 침투 테스트 수동 | PR마다(스캔), 분기마다(침투) |
| 접근성 테스트 | 자동화 도구 + 수동 검증 | PR마다(자동), 릴리스 전(수동) |
| 호환성 테스트 | 매트릭스 자동화 | 릴리스 전 |

CI 파이프라인 구성:

```
PR 생성 시 (빠른 피드백, {n}분 이내):
  린트 → 타입 체크 → 단위 테스트 → 통합 테스트 → 커버리지 게이트

main 머지 시 (전체 검증):
  린트 → 타입 체크 → 단위 테스트 → 통합 테스트 → E2E (P0) → 빌드 → 배포

야간/주간 (확장 검증):
  E2E (전체) → 성능 테스트 → 보안 스캔 → 호환성 매트릭스
```

PR 파이프라인은 {n}분 이내를 목표로 한다. 10분을 넘으면 개발자가 피드백을 기다리지 않고 다른 작업으로 넘어가서 컨텍스트 스위칭이 발생한다. 느린 테스트는 야간 스케줄로 분리한다.

불안정 테스트(flaky test) 관리:

불안정 테스트가 있으면 CI를 믿지 않게 되고, 결국 실패를 무시하게 된다. 불안정 테스트는 발견 즉시 격리하고(skip + 이슈 생성), 원인을 분석해서 수정한다. 일주일 안에 수정되지 않으면 삭제한다.


### 8. 리스크 등급 → 진입/종료 기준

입력: 1단계의 리스크 등급, 4단계의 커버리지 목표, 7단계의 자동화 범위.

진입 기준은 "테스트를 시작해도 되는가"의 조건이다. 종료 기준은 "테스트를 끝내도 되는가"의 조건이다. 기준이 없으면 "대충 돌려보고 됐다"가 된다.

진입 기준:

| 테스트 레벨 | 진입 조건 |
|-----------|----------|
| 단위 테스트 | 코드 컴파일/빌드 성공, 린트 통과 |
| 통합 테스트 | 단위 테스트 전체 통과, 테스트 DB 가용 |
| E2E 테스트 | 통합 테스트 전체 통과, 스테이징 환경 배포 완료 |
| 성능 테스트 | E2E P0 통과, 성능 환경 격리 확인 |
| 보안 테스트 | 기능 테스트 완료, 보안 체크리스트 준비 |

종료 기준:

| 기준 | P0 영역 | P1 영역 | P2-P3 영역 |
|------|---------|---------|-----------|
| 커버리지 | 90%+ | 80%+ | 60%+ |
| 미해결 결함 | 0개 | 0개 (P0 결함) | {에센스에서 결정} |
| 불안정 테스트 | 0개 | 0개 | 0개 |
| 성능 기준 충족 | 필수 | 필수 | 해당 시 |
| 보안 스캔 통과 | 필수 | 필수 | 권장 |

릴리스 종료 기준 (전체):

```
필수:
- 모든 자동화 테스트 통과
- P0 영역 커버리지 {목표}% 이상
- P0 결함 0개, P1 결함 0개
- 불안정 테스트 0개

권장:
- 전체 커버리지 {목표}% 이상
- P2 결함 {n}개 이하
- 성능 회귀 없음 (이전 릴리스 대비)
```

기준은 프로젝트 초기에 정하고, 팀 역량과 프로젝트 성숙도에 따라 점진적으로 강화한다. 처음부터 P0 90%를 강제하면 형식적 테스트만 양산된다.
