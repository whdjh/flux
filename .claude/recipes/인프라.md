# 레시피

환경 구분 · 환경변수 · 시크릿 관리 · 배포 절차 · 도메인/DNS/인증서 · 모니터링/알림 · 장애 대응 · 백업/복구 · 비용/쿼터

스택 가이드가 "어떤 도구를 쓸지" 결정하고, 아키텍처가 "어떻게 배치할지" 결정한다면, 이 레시피는 "실제 운영에 필요한 설정값"을 채운다. URL, 변수명, 채널명, 임계값 같은 구체적 구성값이 대상이다.


## 필요한 에센스

- [ ] 환경 목록과 각 환경의 URL (로컬, 개발, 스테이징, 프로덕션)
- [ ] 환경변수 목록 (.env 파일 또는 설정 매트릭스)
- [ ] 시크릿 저장소 정보 (Vault 주소, AWS Secrets Manager ARN, 1Password 볼트명 등)
- [ ] 배포 파이프라인 현황 (CI/CD 도구, 트리거 조건, 배포 대상)
- [ ] 도메인/DNS 현황 (도메인명, 레지스트라, 네임서버, 인증서 발급 방식)
- [ ] 모니터링 현황 (사용 중인 도구, 대시보드 URL, 알림 채널)
- [ ] 장애 대응 체계 (온콜 담당, 에스컬레이션 경로, 커뮤니케이션 채널)
- [ ] 백업 현황 (대상, 주기, 보관 위치, 복구 테스트 이력)
- [ ] 비용 현황 (월 인프라 비용, 주요 과금 항목, 쿼터 제한)
- [ ] 스택 가이드 (도구 선정 결과 참조) - 선택
- [ ] 아키텍처 가이드 (배포 토폴로지 참조) - 선택


## 만드는 법

인프라 가이드는 "이 프로젝트를 운영하려면 무엇이 어디에 어떤 값으로 설정돼 있는가"를 답한다. 새 팀원이 합류했을 때, 장애가 터졌을 때, 환경을 하나 더 만들어야 할 때 이 문서만 보고 행동할 수 있어야 한다.

순서는 안쪽에서 바깥쪽으로 진행한다. 환경 구분과 환경변수가 가장 안쪽이고, 비용/쿼터가 가장 바깥이다. 앞 단계의 결정이 뒤 단계의 입력이 된다.


### 1. 환경 구분

입력: 에센스의 "환경 목록과 각 환경의 URL", 아키텍처 가이드의 배포 토폴로지.

환경별 목적과 접근 범위를 정의한다. 환경이 몇 개인지, 각 환경이 어떤 역할인지, 누가 접근할 수 있는지를 기록한다.

| 상황 | 권장 구성 |
|------|----------|
| 1인/소규모 | 로컬 + 프로덕션 (2개) |
| 일반 팀 | 로컬 + 스테이징 + 프로덕션 (3개) |
| 규제/대규모 | 로컬 + 개발 + 스테이징 + 프로덕션 (4개) |

각 환경에 대해 다음을 기록한다.

```
{환경명}:
  URL: {서비스 URL}
  용도: {이 환경에서 하는 일}
  접근: {접근 가능한 사람/시스템}
  데이터: {실 데이터/시드 데이터/목 데이터}
  배포: {자동/수동, 트리거 조건}
```

환경 간 차이를 명시한다. "스테이징은 프로덕션과 동일"이라고 쓰면 안 된다. 실제로는 인스턴스 크기, 데이터 양, 외부 연동(샌드박스 vs 라이브)이 다르다. 다른 점만 기록한다.

환경별 외부 서비스 모드도 여기서 정리한다. 결제 API의 테스트 모드, OAuth의 개발용 앱, 이메일 서비스의 샌드박스 같은 것이다.


### 2. 환경변수

입력: 에센스의 "환경변수 목록", 1단계의 환경 구분.

환경변수는 세 층으로 분류한다.

앱 설정은 애플리케이션 동작을 결정하는 변수다. `NODE_ENV`, `LOG_LEVEL`, `API_BASE_URL` 같은 것이다. 코드에 하드코딩하면 안 되지만 노출돼도 보안 문제는 없다.

연결 정보는 외부 서비스의 접속 주소다. `DATABASE_URL`, `REDIS_URL`, `S3_BUCKET` 같은 것이다. 환경마다 다른 값을 가진다.

시크릿은 3단계에서 별도로 다룬다. 여기서는 변수명만 기록하고 값은 절대 적지 않는다.

환경변수 매트릭스를 만든다. 모든 환경에서 어떤 변수가 어떤 값을 갖는지 한눈에 보여야 한다.

```
| 변수명 | 로컬 | 스테이징 | 프로덕션 | 필수 | 분류 |
|--------|------|---------|---------|:---:|------|
| NODE_ENV | development | staging | production | O | 앱 설정 |
| DATABASE_URL | {로컬 DB} | {스테이징 DB} | {시크릿} | O | 연결 정보 |
| API_KEY | {테스트키} | {테스트키} | {시크릿} | O | 시크릿 |
```

시크릿 열에는 `{시크릿}` 플레이스홀더만 남긴다. 실제 값은 시크릿 저장소에서만 관리한다.

`.env.example` 파일을 프로젝트 루트에 둔다. 모든 변수명과 설명을 포함하되 실제 값은 비워둔다. 새 환경변수가 추가될 때마다 이 파일도 함께 업데이트하는 동기화 규칙을 명시한다.

유효성 검증도 기록한다. 앱이 시작될 때 필수 환경변수가 있는지 확인하는 코드가 어디 있는지, 없으면 어떻게 실패하는지 적는다.


### 3. 시크릿 관리

입력: 에센스의 "시크릿 저장소 정보", 2단계의 환경변수 중 시크릿 분류.

시크릿은 환경변수와 별도로 관리한다. "어디에 저장하고, 어떻게 주입하고, 어떻게 교체하는가"를 기록한다.

| 상황 | 권장 방식 |
|------|----------|
| 1인/소규모 | .env 파일 (gitignore) + CI/CD 시크릿 |
| 일반 팀 | CI/CD 시크릿 + 클라우드 시크릿 매니저 |
| 규제/대규모 | Vault/AWS Secrets Manager + 자동 로테이션 |

각 시크릿에 대해 다음을 기록한다.

```
| 시크릿명 | 저장소 | 주입 방법 | 로테이션 주기 | 담당 |
|---------|--------|----------|-------------|------|
| {DB 비밀번호} | {저장소} | {환경변수/파일/API} | {주기} | {담당자} |
| {API 키} | {저장소} | {환경변수} | {주기} | {담당자} |
```

시크릿 로테이션 절차가 핵심이다. "교체할 때 어떤 순서로 무엇을 하는가"를 단계별로 적는다. 새 시크릿 생성 → 새 값으로 서비스 업데이트 → 이전 값 폐기 순서가 일반적이다. 동시에 두 값이 유효한 기간(grace period)도 명시한다.

시크릿이 유출됐을 때의 긴급 대응 절차도 적는다. 7단계 장애 대응과 연결된다.


### 4. 배포 절차

입력: 에센스의 "배포 파이프라인 현황", 1단계의 환경 구분.

"코드가 머지된 후 프로덕션에 도달하기까지의 모든 단계"를 기록한다. 스택 가이드가 CI/CD 도구를 결정했다면, 여기서는 실제 파이프라인의 단계와 설정값을 채운다.

환경별 배포 트리거를 정의한다.

```
| 환경 | 트리거 | 방법 | 승인 |
|------|--------|------|------|
| {스테이징} | {main 머지} | {자동} | {불필요} |
| {프로덕션} | {태그 푸시/수동} | {자동+승인} | {필요, 담당자} |
```

배포 단계를 상세하게 적는다.

```
1. {빌드 단계}: {무엇을 하는가}
2. {테스트 단계}: {어떤 테스트를 돌리는가}
3. {아티팩트 생성}: {이미지 빌드, 번들링 등}
4. {배포}: {대상 환경, 전략}
5. {검증}: {헬스체크, 스모크 테스트}
6. {롤백 조건}: {어떤 상황에서 자동/수동 롤백}
```

롤백 절차는 배포만큼 중요하다. 롤백 명령어, 롤백 시 DB 마이그레이션 처리, 롤백 후 확인 사항을 명시한다. "롤백이 가능한가"를 확인하지 않은 배포는 불완전하다.

배포 중 다운타임 여부도 기록한다. 다운타임이 있으면 공지 절차와 유지보수 페이지 전환 방법을 함께 적는다.


### 5. 도메인/DNS/인증서

입력: 에센스의 "도메인/DNS 현황".

도메인 관련 설정은 바꾸기 어렵고 실수하면 서비스가 중단된다. "어디서 관리하고, 어떤 레코드가 있고, 인증서는 어떻게 갱신되는가"를 기록한다.

도메인 등록 정보:

```
| 도메인 | 레지스트라 | 만료일 | 자동 갱신 | 관리 계정 |
|--------|----------|--------|:-------:|----------|
| {도메인} | {업체} | {날짜} | {O/X} | {계정/담당} |
```

DNS 레코드 현황:

```
| 호스트 | 유형 | 값 | TTL | 용도 |
|--------|------|-----|-----|------|
| @ | A | {IP} | {값} | {프로덕션} |
| www | CNAME | {값} | {값} | {리다이렉트} |
| staging | CNAME | {값} | {값} | {스테이징} |
| _acme-challenge | TXT | {값} | {값} | {인증서 검증} |
```

인증서 관리:

| 상황 | 권장 방식 |
|------|----------|
| CDN 사용 | CDN 제공 자동 인증서 (Cloudflare, Vercel) |
| 서버 직접 운영 | Let's Encrypt + certbot 자동 갱신 |
| 와일드카드 필요 | DNS-01 챌린지 + 자동 갱신 |
| 규제 환경 | 유료 인증서 (OV/EV) |

인증서 만료 알림을 모니터링(6단계)에 포함한다. 인증서 만료는 가장 흔하면서도 예방 가능한 장애 원인이다.


### 6. 모니터링/알림

입력: 에센스의 "모니터링 현황", 아키텍처 가이드의 횡단 관심사.

스택 가이드가 모니터링 도구를 결정했다면, 여기서는 "무엇을 감시하고, 임계값은 얼마이고, 누구에게 어떻게 알리는가"를 채운다.

감시 대상과 임계값:

```
| 지표 | 정상 범위 | 경고 임계값 | 심각 임계값 | 대시보드 |
|------|----------|-----------|-----------|---------|
| {API 응답시간} | {p95 < Nms} | {> Nms} | {> Nms} | {URL} |
| {에러율} | {< N%} | {> N%} | {> N%} | {URL} |
| {CPU 사용률} | {< N%} | {> N%} | {> N%} | {URL} |
| {디스크 사용률} | {< N%} | {> N%} | {> N%} | {URL} |
| {DB 커넥션 수} | {< N} | {> N} | {> N} | {URL} |
```

알림 라우팅:

```
| 심각도 | 채널 | 대상 | 응답 시간 |
|--------|------|------|----------|
| 심각 (P1) | {전화/PagerDuty} | {온콜 담당} | {N분 이내} |
| 경고 (P2) | {Slack 채널} | {팀} | {N시간 이내} |
| 정보 (P3) | {Slack 채널/이메일} | {팀} | {다음 근무일} |
```

알림 피로를 방지하는 규칙도 적는다. 같은 알림이 N분 내 반복되면 묶기, 비근무 시간에는 P1만 전달하기 같은 정책이다.

대시보드 목록과 URL을 기록한다. 대시보드가 어디 있는지 모르면 장애 시 시간을 낭비한다.


### 7. 장애 대응

입력: 에센스의 "장애 대응 체계", 6단계의 알림 라우팅.

장애 발생 시 "누가 무엇을 어떤 순서로 하는가"를 기록한다. 장애 중에 절차를 만들면 늦는다.

장애 등급 정의:

```
| 등급 | 정의 | 예시 | 목표 복구 시간 |
|------|------|------|--------------|
| P1 | {서비스 전체 중단} | {DB 다운, DNS 장애} | {N분} |
| P2 | {핵심 기능 장애} | {결제 불가, 로그인 불가} | {N시간} |
| P3 | {일부 기능 장애} | {검색 느림, 알림 지연} | {N시간} |
| P4 | {사소한 이슈} | {UI 깨짐, 오타} | {다음 스프린트} |
```

장애 대응 절차:

```
1. 감지: {알림 수신 또는 사용자 보고}
2. 확인: {대시보드/로그로 영향 범위 파악}
3. 공지: {상태 페이지 업데이트, 내부 채널 공유}
4. 분류: {등급 부여, 담당 배정}
5. 완화: {임시 조치 — 트래픽 우회, 롤백, 스케일 업}
6. 해결: {근본 원인 수정}
7. 사후: {포스트모템 작성, 재발 방지책}
```

온콜 체계:

```
| 역할 | 담당 | 연락처 | 교대 주기 |
|------|------|--------|----------|
| 1차 대응 | {담당자} | {전화/Slack} | {주기} |
| 2차 에스컬레이션 | {담당자} | {전화} | {조건} |
```

1인 프로젝트라면 온콜 체계 대신 "장애 인지 경로"를 적는다. 업타임 모니터링 → 이메일/SMS 알림 → 확인 순서다.

포스트모템 템플릿 위치도 명시한다. 장애가 끝난 뒤 기록하지 않으면 같은 장애가 반복된다.


### 8. 백업/복구

입력: 에센스의 "백업 현황", 아키텍처 가이드의 데이터 아키텍처.

"무엇을 얼마나 자주 어디에 백업하고, 복구에 얼마나 걸리는가"를 기록한다.

백업 대상과 정책:

```
| 대상 | 방법 | 주기 | 보관 기간 | 보관 위치 | RTO | RPO |
|------|------|------|----------|----------|-----|-----|
| {DB} | {스냅샷/덤프} | {매일/매시간} | {N일} | {S3/별도 리전} | {N분} | {N시간} |
| {파일 저장소} | {증분/전체} | {매일} | {N일} | {위치} | {N시간} | {N시간} |
| {설정 파일} | {Git/스냅샷} | {변경 시} | {무기한} | {Git} | {즉시} | {즉시} |
```

RTO(Recovery Time Objective)는 "복구까지 허용되는 최대 시간"이고, RPO(Recovery Point Objective)는 "유실을 허용하는 최대 데이터 양(시간)"이다. 아키텍처 가이드에서 목표를 정했다면 여기서 실제 달성 가능한 수치를 기록한다.

복구 절차를 단계별로 적는다.

```
{대상} 복구 절차:
1. {백업 확인}: {어디서 최신 백업을 찾는가}
2. {환경 준비}: {복구 대상 환경 상태 확인}
3. {복구 실행}: {구체적 명령어 또는 콘솔 조작}
4. {검증}: {데이터 정합성 확인 방법}
5. {서비스 재개}: {트래픽 복구, 공지}
```

복구 테스트 주기를 정한다. 백업은 복구 테스트를 하기 전까지는 "있다고 믿는 것"일 뿐이다.

| 상황 | 권장 주기 |
|------|----------|
| 소규모 | 분기 1회 |
| 일반 | 월 1회 |
| 규제/대규모 | 주 1회 + 자동 검증 |


### 9. 비용/쿼터

입력: 에센스의 "비용 현황".

"지금 얼마 쓰고 있고, 어디서 많이 나가고, 한도는 얼마인가"를 기록한다.

비용 현황:

```
| 항목 | 서비스 | 월 비용 | 비율 | 비고 |
|------|--------|--------|------|------|
| {컴퓨팅} | {서비스명} | {금액} | {%} | {인스턴스 타입} |
| {DB} | {서비스명} | {금액} | {%} | {티어} |
| {스토리지} | {서비스명} | {금액} | {%} | {용량} |
| {네트워크} | {서비스명} | {금액} | {%} | {전송량} |
| {기타} | {서비스명} | {금액} | {%} | |
```

쿼터와 한도:

```
| 서비스 | 쿼터 항목 | 현재 한도 | 현재 사용 | 사용률 |
|--------|----------|----------|----------|--------|
| {서비스} | {API 호출} | {N/월} | {N/월} | {%} |
| {서비스} | {스토리지} | {N GB} | {N GB} | {%} |
| {서비스} | {동시 접속} | {N} | {N} | {%} |
```

비용 알림을 설정한다. 월 예산의 80%에 도달하면 경고, 100%에 도달하면 심각 알림을 보낸다. 클라우드 서비스 대부분이 비용 알림을 지원하지만, 기본 설정으로는 안 켜져 있다.

비용 최적화 여지도 기록한다. Reserved Instance, Savings Plan, 사용하지 않는 리소스, 오버 프로비저닝된 인스턴스 같은 것이다. 당장 최적화하지 않더라도 기회를 기록해두면 나중에 참조할 수 있다.
