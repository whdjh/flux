# 레시피

프론트엔드 · 백엔드 · 데이터베이스 · 인프라/배포 · DevOps/CI·CD · 모니터링 · 보안 · API/외부연동 · 테스트 · 개발 도구 · 선택 근거

## 필요한 에센스

- [ ] 요구사항 문서 (기능 + 비기능 요구사항)
- [ ] 프로젝트 유형 (웹, 모바일, CLI, API, 데스크톱)
- [ ] 대상 사용자 (일반 사용자, 개발자, 내부 직원)
- [ ] 팀 역량 (경험 있는 기술, 학습 가능 시간, 팀 규모)
- [ ] 배포 환경 (로컬, 클라우드, 온프레미스, 하이브리드)
- [ ] 규모 예상 (사용자 수, 데이터 양, 트래픽 패턴)
- [ ] 데이터 특성 (관계형/문서형/시계열, 스키마 유연성 요구)
- [ ] 기존 제약 (이미 정해진 기술, 회사 표준, 라이선스 제한)
- [ ] 보안 요구사항 (인증 방식, 규제, 데이터 등급)
- [ ] 외부 시스템 연동 대상 (결제, 인증, 메시지, 데이터 소스)
- [ ] 예산 범위 (인프라 비용, 유료 서비스 허용 여부) - 선택
- [ ] 기존 시스템 API 명세 (연동 대상이 있으면) - 선택


## 만드는 법

기술 스택은 한 번에 결정되지 않는다. 요구사항에서 기술 요건을 추출하고, 레이어별로 결정하되, 각 레이어의 결정이 다른 레이어에 영향을 준다. 프론트엔드 → 백엔드 → 데이터베이스 → 인프라 순서로 결정하되, 보안이나 규모 요건이 앞선 결정을 뒤집을 수 있다.

### 1. 요구사항 → 기술 요건 추출

입력: 에센스의 "요구사항 문서"와 "프로젝트 유형".

요구사항에서 기술적 결정이 필요한 부분을 뽑는다. 기능 요구사항("실시간 알림" → WebSocket)과 비기능 요구사항("동시 접속 1만 명" → 수평 확장 가능한 서버)을 모두 본다.

| 요구사항 패턴 | 시사하는 기술 |
|-------------|-------------|
| 실시간 알림/채팅 | WebSocket, SSE |
| 오프라인 지원 | PWA, localStorage, IndexedDB |
| 대용량 파일 업로드 | 스트리밍, 청크 업로드 |
| SEO 필수 | SSR (Next.js, Nuxt) |
| SPA (관리자 도구 등) | CSR (Vite + React/Vue) |
| 서버 없이 동작 | 정적 사이트, localStorage |
| 높은 동시성 | Go, Rust, Elixir |
| 복잡한 데이터 관계 | 관계형 DB, GraphQL |
| 이벤트 기반 처리 | 메시지 큐, 이벤트 스트리밍 |
| 멀티 테넌트 | Row-Level Security, 스키마 분리 |


### 2. 프론트엔드

입력: 1단계의 기술 요건, 에센스의 "팀 역량"과 "기존 제약".

| 상황 | 권장 기술 | 이유 |
|------|----------|------|
| SSR/SEO 필요 | Next.js, Nuxt | 서버 렌더링 내장 |
| SPA/관리자 도구 | Vite + React | 빠른 HMR, 간결한 설정 |
| 정적 사이트/블로그 | Astro | 빌드 시 HTML, JS 최소화 |
| 모바일 앱 | React Native, Flutter | 크로스 플랫폼 |
| 데스크톱 앱 | Electron, Tauri | Tauri가 번들 크기 작음 |

프론트엔드가 불필요한 프로젝트(API 서버, CLI)는 "없음"으로 명시한다.

UI 라이브러리와 상태 관리도 여기서 결정한다. 디자인 가이드의 컴포넌트 시스템과 일치해야 한다.

| 영역 | 권장 기술 |
|------|----------|
| UI 컴포넌트 | shadcn/ui, Radix, Material UI |
| 상태 관리 | Zustand, Jotai, Redux Toolkit |
| 폼 처리 | React Hook Form + Zod |
| 데이터 페칭 | TanStack Query, SWR |
| 스타일링 | Tailwind CSS, CSS Modules |

버전을 결정할 때는 LTS가 있으면 LTS를 기본으로 한다. Node.js, React 같은 핵심 런타임/프레임워크는 최신 버전이 아닌 LTS(또는 안정 메이저)를 고른다.


### 3. 백엔드

입력: 1단계의 기술 요건, 에센스의 "팀 역량"과 "규모 예상".

| 상황 | 권장 기술 | 이유 |
|------|----------|------|
| Node.js REST API (최소주의) | Express | 생태계 가장 넓음, 학습 자료 많음 |
| Node.js REST API (고성능) | Fastify | Express보다 2배 빠름, JSON 스키마 검증 내장 |
| Python REST API | FastAPI | 타입 힌트 기반 자동 문서화, Pydantic 검증 |
| 대규모 Node.js 서비스 | NestJS | Angular식 DI, 모듈 기반 구조 |
| 풀스택 Python | Django | ORM·관리자·인증 내장, 배터리 포함 |
| 엔터프라이즈 JVM | Spring Boot | 성숙한 생태계, 강한 타입 시스템 |
| BaaS로 대체 가능 | Supabase, Firebase | 서버 코드 불필요 |
| 고성능 (저지연) | Go (Fiber, Echo) | 고루틴 기반 동시성, 낮은 메모리 |
| 고성능 (메모리 안전) | Rust (Axum) | 제로 코스트 추상화, 컴파일 타임 안전성 |
| 마이크로서비스 | gRPC + Go/Rust | 바이너리 프로토콜, 서비스 간 타입 계약 |

백엔드 없이 프론트엔드만으로 동작하는 프로젝트(정적 사이트, BaaS)는 "없음"으로 명시하고 이유를 쓴다.

ORM/데이터 접근도 여기서 결정한다.

| 언어 | 권장 ORM |
|------|---------|
| TypeScript | Prisma, Drizzle |
| Python | SQLAlchemy, Django ORM |
| Go | GORM, sqlc |
| Java | JPA/Hibernate |

런타임/언어 버전은 LTS가 있으면 LTS를 기본으로 한다. Node.js LTS, Python의 활성 지원 버전, Java LTS(17, 21 등)를 우선 고려한다.


### 4. 데이터베이스

입력: 1단계의 기술 요건, 에센스의 "규모 예상"과 "데이터 특성".

| 상황 | 권장 기술 | 이유 |
|------|----------|------|
| 관계형 데이터 | PostgreSQL | 확장성, JSON 지원, RLS |
| 문서형 데이터 | MongoDB | 스키마 유연성 |
| 캐시/세션 | Redis, Valkey | 인메모리, 빠른 읽기 |
| 전문 검색 | Elasticsearch, Meilisearch | 역색인, 한국어 형태소 분석 |
| 시계열 데이터 | TimescaleDB, InfluxDB | 시간 기반 집계 최적화 |
| 로컬 저장 | localStorage, SQLite | 서버 불필요 |
| BaaS | Supabase (PostgreSQL) | 호스팅 DB + 실시간 구독 |

하나의 DB로 모든 요구를 충족할 필요는 없다. 주 DB와 보조 DB(캐시, 검색)를 구분한다.

마이그레이션 도구도 여기서 결정한다. Prisma Migrate, Alembic, Flyway 등 ORM 선택에 따라 자연스럽게 결정된다.

DB 엔진 버전은 LTS 또는 장기 지원 메이저(PostgreSQL의 현재 활성 메이저 등)를 기본으로 한다. 호스팅 서비스(RDS, Supabase)가 지원하는 버전 범위 안에서 고른다.


### 5. 인프라/배포

입력: 에센스의 "배포 환경"과 "예산 범위".

| 상황 | 권장 기술 | 이유 |
|------|----------|------|
| 정적 사이트 | Vercel, Netlify, Cloudflare Pages | 무료, 자동 배포, CDN |
| 컨테이너 | Docker + AWS ECS/GCP Cloud Run | 환경 일관성 |
| 쿠버네티스 | AWS EKS, GKE | 대규모 컨테이너 오케스트레이션 |
| 서버리스 | AWS Lambda, Cloudflare Workers | 사용량 기반 과금 |
| 온프레미스 | Docker Compose, Ansible | 클라우드 불가 환경 |
| 로컬 전용 | 없음 | 배포 불필요 |

배포 전략도 명시한다.

| 전략 | 설명 | 적합한 상황 |
|------|------|------------|
| Rolling | 점진적 교체 | 기본, 소규모 |
| Blue-Green | 두 환경 전환 | 다운타임 제로 필요 |
| Canary | 일부 트래픽만 새 버전 | 대규모, 위험 감소 |

컨테이너를 쓰면 Dockerfile과 docker-compose.yml의 위치를 명시한다. IaC(Infrastructure as Code)를 쓰면 도구(Terraform, Pulumi, CDK)를 여기서 결정한다.


### 6. DevOps/CI·CD

입력: 에센스의 "팀 규모"와 5단계의 인프라 결정.

| 상황 | 권장 기술 | 이유 |
|------|----------|------|
| GitHub 사용 | GitHub Actions | 저장소 내장, 무료 티어 |
| GitLab 사용 | GitLab CI/CD | 저장소 내장 |
| 복잡한 파이프라인 | Jenkins, CircleCI | 세밀한 제어 |
| 모노레포 | Turborepo, Nx + GitHub Actions | 변경 감지, 캐싱 |

CI/CD 파이프라인에 포함할 단계를 정의한다. 최소 파이프라인은 린트 → 테스트 → 빌드 → 배포다.

```
PR 생성 시:   린트 → 타입 체크 → 단위 테스트
main 머지 시: 린트 → 타입 체크 → 전체 테스트 → 빌드 → 배포
```

브랜치 전략(GitHub Flow, Git Flow)에 따라 파이프라인이 달라진다. 깃컨벤션 가이드와 일치해야 한다.


### 7. 모니터링

입력: 에센스의 "규모 예상"과 "비기능 요구사항".

모니터링은 세 영역으로 나뉜다.

에러 추적은 런타임 오류를 수집하고 알린다.

| 도구 | 특징 |
|------|------|
| Sentry | 프론트/백 통합, 소스맵 지원, 무료 티어 |
| Datadog | APM 통합, 대규모 |
| Bugsnag | 안정성 점수, 모바일 |

로그 관리는 애플리케이션 로그를 수집하고 검색한다.

| 상황 | 권장 기술 |
|------|----------|
| 소규모 | 구조화 로그 (pino, winston) + 파일 |
| 중규모 | Loki + Grafana |
| 대규모 | ELK (Elasticsearch + Logstash + Kibana) |

성능 모니터링은 응답 시간, 리소스 사용, 가동 시간을 추적한다.

| 상황 | 권장 기술 |
|------|----------|
| 업타임 체크 | BetterUptime, UptimeRobot |
| APM | Datadog APM, New Relic |
| 인프라 메트릭 | Prometheus + Grafana |
| 프론트엔드 성능 | Lighthouse CI, Web Vitals |

소규모 프로젝트는 Sentry(에러) + 구조화 로그면 충분하다. 규모가 커지면 APM과 인프라 메트릭을 추가한다.

알림 채널도 정의한다. Slack, 이메일, PagerDuty 중 팀 상황에 맞는 것을 선택한다. 심각도별로 알림 경로를 구분해야 알림 피로가 쌓이지 않는다.


### 8. 보안

입력: 에센스의 "보안 요구사항"과 "규제".

인증과 인가를 분리해서 결정한다.

인증(누구인가):

| 상황 | 권장 기술 |
|------|----------|
| 소셜 로그인 | NextAuth.js, Auth.js |
| 자체 인증 | JWT + bcrypt |
| BaaS | Supabase Auth, Firebase Auth |
| 엔터프라이즈 SSO | SAML, OIDC (Keycloak, Auth0) |

인가(뭘 할 수 있는가):

| 상황 | 권장 기술 |
|------|----------|
| 단순 역할 | 역할 기반(RBAC) |
| 세밀한 권한 | 속성 기반(ABAC), 정책 기반 |
| 데이터 행 수준 | PostgreSQL RLS |

데이터 보안도 여기서 다룬다.

| 영역 | 결정 사항 |
|------|-----------|
| 전송 암호화 | TLS 1.3 (HTTPS 필수) |
| 저장 암호화 | DB 암호화, 파일 암호화 |
| 시크릿 관리 | 환경변수, Vault, AWS Secrets Manager |
| 의존성 취약점 | Dependabot, Snyk, npm audit |

규제 요구사항(개인정보보호법, GDPR, PCI DSS)이 있으면 기술 선택에 직접 영향을 준다. 예를 들어 PCI DSS 환경이면 카드 정보를 직접 처리하지 않고 토큰화 서비스를 쓴다.


### 9. API/외부연동

입력: 에센스의 "외부 시스템 연동 대상"과 "기존 시스템 API 명세".

내부 API 설계 방식을 먼저 결정한다.

| 상황 | 권장 방식 |
|------|----------|
| CRUD 위주 | REST |
| 복잡한 데이터 조회 | GraphQL |
| 서비스 간 통신 | gRPC |
| 실시간 양방향 | WebSocket |
| 서버 → 클라이언트 단방향 | SSE (Server-Sent Events) |

외부 연동 대상별로 기술을 정리한다. 대상 지역(국내/글로벌)에 따라 선택지가 달라진다.

| 연동 대상 | 국내 서비스용 | 글로벌 서비스용 |
|----------|-------------|---------------|
| 결제 | Toss Payments, PortOne | Stripe, Paddle |
| 소셜 로그인 | 카카오, 네이버 OAuth2 | Google, Apple, GitHub OAuth2 |
| 푸시 알림 | FCM | FCM, APNs |
| 이메일 | NaverCloud SENS, AWS SES | SendGrid, Postmark, Resend |
| 메신저 알림 | Slack Webhook, KakaoWork | Slack Webhook, Discord |
| 파일 저장 | NaverCloud Object Storage, AWS S3 | AWS S3, Cloudflare R2 |
| 검색 | Meilisearch, Elasticsearch | Algolia, Meilisearch |
| AI/LLM | OpenAI, Anthropic (둘 다 글로벌) | OpenAI, Anthropic, Google Gemini |

각 연동에 대해 SDK 사용 여부, 인증 방식(API Key, OAuth), 에러 처리 전략을 기록한다. Rate limit이 있는 외부 API는 재시도 전략(exponential backoff)을 명시한다.

API 문서화 도구도 여기서 결정한다. REST면 OpenAPI(Swagger), GraphQL이면 GraphQL Playground다.


### 10. 테스트

입력: 에센스의 "프로젝트 유형"과 2-4단계의 기술 선택.

기술 스택에 맞는 테스트 도구를 선택한다. 테스트 전략 자체는 요구사항 가이드와 깃컨벤션의 영역이고, 여기서는 도구만 결정한다.

| 영역 | 권장 도구 |
|------|----------|
| 단위 테스트 (JS/TS) | Vitest |
| 단위 테스트 (Python) | pytest |
| 단위 테스트 (Go) | testing + testify |
| 통합 테스트 | Supertest, httpx |
| E2E 테스트 | Playwright, Cypress |
| API 테스트 | Bruno, Postman |
| 성능 테스트 | k6, Artillery |
| 컴포넌트 테스트 | Storybook, Testing Library |

커버리지 도구도 함께 결정한다. Vitest는 c8/istanbul 내장, pytest는 pytest-cov, Go는 내장 cover다.


### 11. 개발 도구

입력: 2-4단계의 기술 선택, 에센스의 "팀 규모".

코드 품질과 개발 생산성을 위한 도구를 정리한다.

| 영역 | 권장 도구 |
|------|----------|
| 패키지 매니저 | pnpm, bun (JS), uv (Python), go mod (Go) |
| 린터 | ESLint, Biome (JS), Ruff (Python), golangci-lint (Go) |
| 포매터 | Prettier, Biome (JS), Ruff (Python), gofmt (Go) |
| 타입 체크 | TypeScript, mypy, pyright |
