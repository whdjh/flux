# iOS 클라이언트: Native vs React Native

flux는 local-first 앱. 모든 쓰기/읽기가 로컬에서 즉시 일어나고(0ms), 백그라운드로 서버에 동기화됨. 이 구조에서 클라이언트 기술 선택이 성능에 직접 영향을 줌.


## 핵심 기술 스택과의 궁합

loro CRDT(Rust)로 실시간 리치텍스트 편집함.

네이티브(Swift)는 Rust FFI로 직접 바인딩. 브릿지 오버헤드 없음. RN은 키 입력마다 JS → Native → Rust → Native → JS 왕복. 일반 앱에서는 괜찮지만, 실시간 리치텍스트 편집에서는 체감됨.


## iOS 전용 기능

영감 수집 도구의 핵심 접점들이 네이티브 API에 의존함.

- Share Extension: 다른 앱에서 "공유"로 즉시 수집. RN으로 못 만듦. 어차피 네이티브 코드 필요.
- Widgets: 홈 화면 위젯. WidgetKit은 SwiftUI 전용.
- Siri Shortcuts: 음성으로 수집. 네이티브 전용.
- Spotlight 검색 통합: 수집물을 시스템 검색에 노출. 네이티브 전용.

RN을 쓰더라도 이 기능들은 네이티브로 짜야 함. 하이브리드가 되면 오히려 복잡도만 올라감.


## macOS 확장

SwiftUI로 만든 iOS 앱은 macOS와 코드 공유 가능. 같은 SwiftUI 뷰 그대로 씀. react-native-macos는 존재하지만 미성숙.


## 제안

서버 API(REST + WebSocket)는 클라이언트를 모름. JWT가 유효하고 메시지 포맷만 지키면 어떤 클라이언트든 연결 가능. 이걸 활용해서 역할을 나누면 됨.

```
서버(Rust/Axum)          ← 공유 (누구든 이 API 위에 클라이언트를 만들 수 있음)
iOS/macOS (Swift)        ← 핵심 앱, 네이티브 API 활용
Web (React)              ← 데스크톱 보조 클라이언트
Chrome Extension (JS/TS) ← 브라우저 수집 접점
```

각자 강점을 씀. iOS는 네이티브로 최적의 수집 경험을 만들고, Web과 Chrome Extension은 JS/TS로 빠르게 만듦. 같은 서버 API 위에서 독립적으로 개발 가능.

loro는 Rust FFI(Swift용)와 WASM(JS용) 바인딩을 둘 다 제공함. CRDT 동기화가 양쪽에서 동작함.

나중에 Android가 필요하면 그때 RN이나 Kotlin으로 만들면 됨. "갈아엎기"가 아니라 "하나 더 만들기". 서버 API가 잘 정의되어 있으면 새 클라이언트를 붙이는 건 새 앱 하나 만드는 것과 같음.
