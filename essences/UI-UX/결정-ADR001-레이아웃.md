# ADR-001: Three-Panel Layout System

## 한글 요약 / Korean Summary

VS Code 스타일의 3-패널 레이아웃 시스템을 채택한다 (왼쪽 사이드바 20% | 중앙 메인 뷰 60% | 오른쪽 사이드바 20%).

인지 과학적 근거(Fitt's Law, F-Pattern, Miller's Law)와 시장 검증(3,500만 개발자 사용, 74% 만족도)을 바탕으로 선택했다. 영구 네비게이션, 컨텍스트 유지, 도구 접근성이라는 실용적 이점이 있다.

장점은 친숙함, 효율성, 유연성, 확장성이다. 단점은 복잡한 구현과 모바일 부적합이다.

## Status
**Accepted** - 2024-09-15

## Context

### The Problem
Information management applications need to balance several competing needs:
- **Navigation**: Quick access to organized content
- **Focus**: Maximum space for primary content
- **Tools**: Access to auxiliary functions without disrupting flow
- **Flexibility**: Adapt to different workflows and screen sizes

### Existing Solutions Analysis
1. **Single Panel** (like Apple Notes)
   - ✅ Simple
   - ❌ Constant navigation required

2. **Two Panel** (like Slack)
   - ✅ Better than single
   - ❌ Tools compete with navigation

3. **Floating Panels** (like Photoshop)
   - ✅ Flexible
   - ❌ Covers content, requires management

4. **Tab-Based** (like browsers)
   - ✅ Familiar
   - ❌ No persistent navigation

## Decision

We will implement a **VS Code-style three-panel layout system**:

```
|----------|----------------------|----------|
|   Left   |        Center        |  Right   |
| Sidebar  |      Main View       | Sidebar  |
|  (20%)   |        (60%)         |  (20%)   |
|----------|----------------------|----------|
```

### Specific Implementation
- **Left Panel**: File tree navigation (collapsible)
- **Center Panel**: Primary content area with tab system
- **Right Panel**: AI assistant / tools (collapsible)
- **Resizable Boundaries**: Drag to resize any panel
- **Keyboard Shortcuts**: Quick panel toggling

## Rationale

### Why Three Panels?

#### Cognitive Science Support
- **Fitt's Law**: Most frequent actions (navigation) closest to start position (left)
- **F-Pattern Reading**: Natural eye movement from left navigation → center content
- **Miller's Law**: 3 distinct areas within cognitive chunk limit (7±2)

#### Practical Benefits
1. **Persistent Navigation**: Never lose your place
2. **Context Preservation**: See structure while working
3. **Tool Access**: AI/tools available without covering content
4. **Flexibility**: Panels can be hidden when not needed

### Why VS Code's Specific Implementation?

#### Market Validation
- 35 million developers use it daily
- 74% satisfaction rate (Stack Overflow 2023)
- Proven efficient for information-heavy work

#### Design Strengths
- **Proportions**: 20-60-20 golden ratio for visual balance
- **Collapsibility**: Each panel optional
- **Responsiveness**: Gracefully handles window resizing
- **Predictability**: Consistent behavior across operations

## Consequences

### Positive
- ✅ **Familiar**: Millions already know this pattern
- ✅ **Efficient**: Proven productivity in information work
- ✅ **Flexible**: Adapts to different workflows
- ✅ **Scalable**: Works for 10 or 10,000 items
- ✅ **Accessible**: Keyboard navigable

### Negative
- ❌ **Complex Implementation**: Requires sophisticated state management
- ❌ **Performance Cost**: Three render areas vs. one
- ❌ **Mobile Hostile**: Doesn't translate to small screens
- ❌ **Learning Curve**: Power features need discovery

### Risks
- **Over-engineering**: Temptation to add too many panel options
- **Performance**: Multiple panels could impact render performance
- **Compatibility**: Some users may expect different layouts

## Implementation Details

### Technical Architecture
```typescript
interface LayoutState {
  leftPanel: {
    visible: boolean;
    width: number;  // percentage or pixels
    content: 'file-tree' | 'search' | 'custom';
  };
  centerPanel: {
    tabs: Tab[];
    activeTab: string;
    splitMode: 'none' | 'horizontal' | 'vertical';
  };
  rightPanel: {
    visible: boolean;
    width: number;
    content: 'ai' | 'properties' | 'custom';
  };
}
```

### Key Classes/Components
- `MasterLayout`: Top-level layout orchestrator
- `ResizablePanel`: Generic panel component
- `PanelSplitter`: Drag handle between panels
- `LayoutStore`: Zustand store for state

### Performance Optimizations
- Virtual scrolling in file tree
- Lazy loading of panel contents
- Memoized panel renders
- CSS transforms for resize (no reflow)

## Alternatives Considered

### Alternative 1: Floating Panels
```
Why rejected:
- Window management burden on user
- Covers content unpredictably
- Loses spatial consistency
```

### Alternative 2: Tab-Only Interface
```
Why rejected:
- No persistent navigation
- Constant context switching
- Loses hierarchical overview
```

### Alternative 3: Custom Layout System
```
Why rejected:
- High learning curve
- No proven efficiency
- Development risk
```

## Migration Strategy

### From Current State
1. Implement basic three-panel structure
2. Migrate existing components into panels
3. Add resizing capability
4. Add keyboard shortcuts
5. Add persistence

### Rollback Plan
If three-panel proves problematic:
1. Center panel can become full-screen
2. Panels can be permanently collapsed
3. Revert to two-panel as fallback

## Success Metrics

### Quantitative
- Panel resize actions < 3 per session
- Panel toggle actions < 5 per session
- Time to find item < 5 seconds
- Layout persistence 100% reliable

### Qualitative
- "Feels natural" in user feedback
- No complaints about layout in first week
- Power users discover advanced features naturally
