# 온보딩 테스트 피드백

flux-be 프로젝트에 보일러플레이트를 적용하면서 발견한 마찰과 갭.


## 1. 닭과 달걀 문제: 구조 vs 맥락

파이프라인은 `[tree-planner] → project-init`이다. tree-planner가 먼저 구조를 설계하라는 뜻인데, tree-planner에게 줄 맥락이 없다. 프로젝트가 뭔지도 모르는 상태에서 폴더 구조를 설계할 수 없다.

실제 흐름은 이랬다:
1. 맥락이 없어서 tree-planner를 못 돌림
2. 그래서 임의로 `에센스/` 하위에 카테고리를 만듦
3. 사용자가 "tree-planner가 해야 하는 거 아니야?"라고 지적
4. 뒤늦게 tree-planner 실행 — 그러나 tree-planner도 맥락이 부족

보일러플레이트에 빠진 것: "빈 프로젝트에서 시작할 때" 수확 → 구조 설계 사이의 최소 맥락 요건. 어느 정도 맥락이 쌓여야 tree-planner를 돌릴 수 있는지 기준이 없다.


## 2. docs 브랜치 구조 가이드 부재

워크플로우에 "docs 브랜치에서 문서화"라고 적혀있지만, docs 브랜치의 루트 구조에 대한 가이드가 없다.

실제 마찰:
- docs 브랜치에 `docs/에센스/`를 만듦 → 사용자가 "중복 아니야?" 지적
- `에센스/` 하위에 카테고리를 미리 나눔 → 사용자가 "플랫하게" 선택
- 에센스, CLAUDE.md, context/의 관계가 불명확

보일러플레이트에 빠진 것: docs 브랜치의 표준 레이아웃. 뭐가 루트에 오고, 뭐가 하위에 가는지.


## 3. 빈 레포 부트스트랩 절차 없음

flux-be는 커밋이 0개였다. git branch를 만들려면 최소 1커밋이 필요한데, 파이프라인에 이 단계가 없다.

실제 흐름:
1. docs 브랜치를 만들려 함
2. 커밋이 없어서 브랜치 생성 불가
3. .gitignore로 초기 커밋을 만든 뒤 브랜치 분기

보일러플레이트에 빠진 것: project-init이 빈 레포를 처리하는 절차. 또는 "최소 1커밋이 있어야 시작 가능"이라는 전제 조건.


## 4. 이미지 에센스 처리 가이드 없음

스크린샷 6장이 유일한 원재료였는데, 해상도가 낮아 세부 텍스트를 읽기 어려웠다. 에센스 수집 가이드에 이미지 기반 에센스의 처리 방법이 없다.

질문들:
- 이미지에서 텍스트를 추출해야 하나?
- 이미지 설명을 .md로 따로 만들어야 하나?
- 해상도가 낮으면 어떻게 하나?


## 5. 파이프라인 진입점이 불명확

파이프라인: `[tree-planner] → project-init → [essence-sorter] → guide-filler → recipe-checker`

대괄호 `[]`는 선택이라는 뜻인데, 언제 선택하고 언제 필수인지 기준이 없다. "빈 프로젝트"라는 상황에서 어디부터 시작해야 하는지 판단하기 어렵다.

실제로 AI가 tree-planner를 건너뛰고 바로 폴더를 만들었다. 사용자가 안 잡아줬으면 그대로 진행했을 것이다.


## 6. 수확(Harvest) 단계의 구체적 가이드 없음

라이프사이클에 "수확: 산재한 자료 수집 (수동)"이라고만 적혀있다. 수동이라서 에이전트가 도울 수 없다는 뜻이지만, 실제로 에이전트가 도울 수 있는 부분이 있다:
- "어떤 정보가 필요한지" 질문 목록
- "에센스로 변환 가능한 형태"의 가이드
- 사용자가 설명하면 .md로 기록하는 패턴

지금 세션에서 "프로젝트 설명해주세요"라고 했지만, 구체적으로 어떤 정보를 어떤 형태로 받아야 하는지 가이드가 없어서 막연한 질문이 됐다.


## 7. tree-planner의 시제 혼란: 현재 vs 최종 상태

tree-planner가 수확 단계에서 실행됐는데, 최종 상태(CLAUDE.md, context/, .gitmessage.txt)까지 모두 설계했다. 이 파일들은 project-init, context-writer 등 후속 에이전트가 만들 산출물이다.

문제:
- 지금 만들어야 하는 것 vs 나중에 다른 에이전트가 만들 것이 구분 안 됨
- tree-planner가 project-init의 역할까지 침범
- `context/메모.md` 같은 세부 파일까지 명시 — 코드도 없는 프로젝트에 과도

보일러플레이트에 빠진 것: tree-planner에게 "현재 단계에서 필요한 구조만 설계하라"는 스코핑 지시. 또는 파이프라인 단계별로 누가 어떤 파일을 만드는지 명확한 책임 경계.


## 8. docs 브랜치에 `docs/` 폴더 재발

tree-planner 설계안에 `docs/진행현황.md`가 포함됐다. 이미 사용자가 "docs 브랜치에 docs/ 폴더는 중복"이라고 지적했는데, tree-planner가 같은 실수를 반복했다.

원인: tree-planner가 이전 대화 맥락(사용자 피드백)을 모른다. 서브에이전트라서 독립적으로 판단한다.

보일러플레이트에 빠진 것: "docs 브랜치에서는 docs/ 폴더를 만들지 않는다"는 규칙. 또는 서브에이전트에게 이전 대화에서 발생한 제약을 전달하는 메커니즘.


## 9. 파이프라인 순서 재발견: project-init이 먼저

테스트 중 사용자가 "빈 프로젝트에서 .gitmessage.txt, context/, CLAUDE.md 골격은 먼저 만들어야 하지 않나?"라고 지적했다. 이 파일들은 프로젝트 맥락에 의존하지 않는 범용 인프라다.

이 관찰에서 도출된 올바른 순서:
```
project-init (범용 골격)  →  수확 (에센스 수집)  →  guide-filler (골격 채움)
```

기존 파이프라인 `[tree-planner] → project-init`에서 tree-planner는 문서 인프라 설계에 불필요하다. project-init이 만드는 건 정해진 틀이다. tree-planner는 코드 구조 설계(구현 단계)에서 유용하다.

보일러플레이트에 빠진 것: tree-planner의 적용 시점 명시. "문서 인프라 = project-init, 코드/도메인 구조 = tree-planner"라는 구분.


## 10. 에이전트 분류 체계 부재: 역할별 구분 필요

보일러플레이트에서 에이전트는 라이프사이클 단계별로만 분류된다 (수확→정리→부트스트랩→분해→구현). 하지만 실제 사용 시 성격별 구분이 더 직관적이다.

테스트에서 도출된 분류:

횡단 (어디서든 호출 가능한 범용 도구):
- scope-validator: 스코프 발견/검증
- naming-advisor: 이름 평가/제안
- tree-planner: 구조 설계 (문서든 코드든 컬렉션이든)
- essence-sorter: 비정형 맥락 분류

보일러플레이트 관리 (레시피/가이드 자체를 다루는 메타 도구):
- recipe-builder: 레시피 골격 생성
- recipe-checker: 완성도 검증

프로젝트 작업 (프로젝트 산출물을 만드는 도구):
- project-init: 범용 골격 생성
- guide-filler: 레시피 + 에센스 → 프로젝트 문서
- feature-decomposer: 기능 분해
- prompt-builder: 세션 프롬프트 변환

기록 (세션 추적):
- context-writer: context/MMDD.md
- chat-logger: 세션 히스토리

기존 단계별 분류는 "언제 쓰나"를 알려주지만, "뭘 하는 녀석인가"를 알려주지 않는다. 역할별 분류가 보일러플레이트에 추가되면 에이전트 선택이 쉬워진다.
