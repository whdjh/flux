## Demo-First 개발

### 1단계: 데모 생성

demos/ 폴더에 빠른 프로토타입을 만든다. any 타입이든 하드코딩이든 인라인 스타일이든 상관없다. 작동만 하면 된다.

```typescript
// src/demos/my-feature/MyFeatureDemo.tsx
export const MyFeatureDemo = () => {
  const [data, setData] = useState<any>([]);

  return (
    <div style={{ padding: 20 }}>
      <h2>실험 중인 기능</h2>
    </div>
  );
};
```

### 2단계: 데모 등록

DemoIndex.tsx에 추가한다.

```typescript
{
  title: 'My Feature',
  path: '/demos/my-feature',
  status: 'wip',
  description: '새로운 기능 실험'
}
```

### 3단계: 검증

브라우저에서 /demos로 가서 실제로 사용해본다. UX를 확인하고 성능 문제를 체크하고 엣지 케이스를 발견한다.

### 4단계: 프로덕션 이동

검증이 끝나면 features/로 이동한다.

```
src/features/my-feature/
├── components/    // 정제된 컴포넌트
├── hooks/         // 로직 분리
├── types/         // 타입 정의
└── index.ts       // Public API
```

## 개발 흐름

Demo 단계는 1-2일이다. any 타입, 하드코딩, 인라인 스타일 모두 허용된다. 빠른 프로토타입으로 아이디어를 검증하는 게 목표다.

검증 단계는 1일이다. 사용자 피드백을 수집하고 성능을 측정하고 엣지 케이스를 테스트한다.

프로덕션화는 2-3일이다. TypeScript 타입을 정의하고 에러 처리를 추가하고 테스트를 작성한다. 성능을 최적화하고 접근성을 검토한다.

## 코드 스타일

### TypeScript

타입을 명확히 정의한다. any는 데모에서만 허용된다.

```typescript
interface FileItem {
  id: string;
  name: string;
  path: string;
}
```

### React

컴포넌트를 작게 나눈다. 500줄짜리 거대 컴포넌트는 피한다.

```typescript
const FileExplorer = ({ children, ...props }) => {
  return <Explorer {...props}>{children}</Explorer>;
};
```

### 상태 관리

로컬 상태는 useState를 쓴다. 전역 상태는 Zustand를 쓴다.

```typescript
const [isOpen, setIsOpen] = useState(false);

const useLayoutStore = create((set) => ({
  leftSidebarOpen: true,
  toggleLeftSidebar: () => set((state) => ({
    leftSidebarOpen: !state.leftSidebarOpen
  }))
}));
```

```typescript

export interface MyFeatureAPI {

  saveData(data: Data): Promise<void>;

```

2. Backend Handler를 구현한다.

```typescript
// src/backend/interfaces/ipc/myFeatureHandler.ts
export class MyFeatureHandler implements MyFeatureAPI {
  async getData(): Promise<Data[]> {
    // 구현
  }
}
```

3. Frontend에서 사용한다.

```typescript
const data = await window.electronAPI.myFeature.getData();
```

## 피해야 할 것

데모를 프로덕션에 직접 쓰면 안 된다. 데모는 실험용이고 프로덕션은 안정성이 필요하다.

전역 상태를 남용하면 안 된다. 로컬로 충분하면 로컬을 쓴다.

과도한 최적화를 피한다. 측정을 먼저 하고 최적화는 나중에 한다.

테스트 없이 배포하면 안 된다. 최소한 핵심 기능은 테스트한다.

## 권장 사항

PR은 작게 나눈다. 리뷰하기 쉽게 만든다.

커밋 메시지는 명확하게 쓴다.

```
feat: Add file search functionality
fix: Resolve tab closing issue
refactor: Extract FileTree component
```

복잡한 로직은 주석을 추가한다. API는 JSDoc을 작성한다.

기존 패턴을 따른다. 스타일 가이드를 준수한다.

## 병렬 개발

Demo-First 개발에서는 여러 데모를 동시에 실험한다. demo/file-explorer와 demo/chrome-tabs를 동시에 작업할 수 있다. 문제는 Claude Code가 작업 디렉토리의 .gitignore를 기준으로 코드베이스를 로드한다는 점이다. 같은 디렉토리를 여러 Cursor 창에서 열면 컨텍스트가 공유된다.

Git worktree로 물리적 디렉토리를 분리하면 각 Cursor 창이 완전히 독립된 Claude Code 컨텍스트를 가진다. 각 데모는 독립된 브랜치에서 작업하고, 완성되면 main 브랜치로 머지한다.

### 초기 설정

```bash
# Worktree 디렉토리 생성
mkdir -p {workspace-dir}
```

### 데모 worktree 생성

```bash
# 데모마다 worktree 생성 (브랜치 자동 생성)
git worktree add {workspace-dir}/file-explorer -b demo/file-explorer
git worktree add {workspace-dir}/chrome-tabs -b demo/chrome-tabs
git worktree add {workspace-dir}/split-view -b demo/split-view

# node_modules 공유 (디스크 절약)
ln -s $(pwd)/node_modules {workspace-dir}/file-explorer/node_modules
ln -s $(pwd)/node_modules {workspace-dir}/chrome-tabs/node_modules
ln -s $(pwd)/node_modules {workspace-dir}/split-view/node_modules
```

### Cursor로 열기

```bash
# 각 디렉토리를 별도 Cursor 창으로 열기
cursor {workspace-dir}/file-explorer
cursor {workspace-dir}/chrome-tabs
cursor {workspace-dir}/split-view
```

각 Cursor 창의 Claude Code가 독립된 코드베이스 컨텍스트를 로드한다. file-explorer 데모를 작업하는 Claude는 file-explorer 코드만 본다.

### 데모 통합

데모가 완성되면 features/로 이동한다.

```bash
# file-explorer worktree로 이동
cd {workspace-dir}/file-explorer

# 변경사항 커밋
git add .
git commit -m "feat: Add file explorer demo"

# main 브랜치로 전환하고 머지
git checkout main
git merge demo/file-explorer

# features/로 코드 이동 (리팩토링)
# main 브랜치에서 작업
```

### Worktree 관리

```bash
# Worktree 목록 확인
git worktree list

# Worktree 제거 (데모 완료 후)
git worktree remove {workspace-dir}/file-explorer

# 브랜치 삭제
git branch -d demo/file-explorer
```

### /sc:spawn과의 차이

**`/sc:spawn`**: 하나의 Claude 세션 내에서 작동한다. 작업을 서브태스크로 쪼개서 순차 실행한다. 같은 코드베이스를 본다. 데모 하나를 처음부터 끝까지 만들 때 쓴다.

**`Git worktree`**: 여러 Claude 세션이 독립적으로 작동한다. 각 세션이 물리적으로 다른 디렉토리를 본다. 컨텍스트가 완전히 격리된다. 여러 데모를 동시에 실험할 때 쓴다.
