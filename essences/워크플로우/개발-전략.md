전략 배경과 원리를 설명한다. 실행 방법은 [개발-워크플로우.md](./개발-워크플로우.md) 참고.

## 컨텍스트 최소화

컨텍스트가 작을수록 AI가 관련 정보에 집중한다.

Claude Code는 200K 컨텍스트를 쓸 수 있다. 프로젝트 코드베이스가 125K를 차지하면 작업 공간은 75K만 남는다. 베이스라인을 20K로 줄이면 작업 공간이 180K로 늘어난다.

컨텍스트가 길어질수록 AI는 관련 없는 정보에 산만해진다. "Lost in the Middle" 연구에서는 긴 컨텍스트의 중간 부분이 30-40% 덜 활용된다는 걸 보여준다. 필요한 것만 로드하면 AI가 중요한 정보에 집중할 수 있다.

목표는 베이스라인 컨텍스트를 최소화하는 것이다. 프로젝트마다 다르지만 이 프로젝트에서는 20K 정도가 적절하다.

## 5가지 원칙과 컨텍스트

기존 개발 원칙이 컨텍스트 최소화와 자연스럽게 맞아떨어진다.

데모 우선 개발은 작은 컨텍스트로 시작한다. Demo 단계에서는 28K만 쓰기 때문에 전체 아키텍처를 몰라도 된다. 실험 철학과 코딩 규칙만 있으면 빠르게 프로토타입을 만들 수 있다.

분해 가능한 설계는 컨텍스트를 격리한다. 각 조각이 독립적이면 해당 조각 컨텍스트만 로드하면 된다. UI, Logic, Data로 나누면 각각을 따로 이해할 수 있기 때문에 한 번에 전체를 읽지 않아도 된다.

리프 노드 아키텍처는 2-4시간 단위로 작업한다. 한 세션에 완성 가능한 크기라서 컨텍스트 스위칭이 없다. 하나의 리프 노드는 하나의 agent 템플릿으로 커버 가능해서 컨텍스트를 계속 유지하면서 몰입 상태를 지킬 수 있다.

익숙한 패턴 활용은 설명 컨텍스트를 줄인다. VS Code 레이아웃이나 Chrome 탭 시스템은 이미 검증된 패턴이라서 긴 설명이 필요 없다. "VS Code처럼"이라고만 하면 AI가 바로 이해한다.

사용자 중심 개발은 불필요한 컨텍스트를 배제한다. 추측으로 만든 기능은 문서화도 많이 필요하고 설명도 복잡하다. 데이터로 검증된 기능만 만들면 간단명료하다.

## .gitignore 전략

.gitignore는 컨텍스트 관리의 첫 번째 방어선이다.

다음을 제외한다:
```
node_modules/        # 의존성 패키지
dist/, out/, .vite/  # 빌드 아티팩트
.cache/, *.log       # 임시 파일
.env*                # 보안
```

node_modules는 프로젝트에서 가장 큰 디렉토리다. 의존성 소스 코드는 AI가 읽을 필요가 없다. 패키지 이름과 API 문서면 충분하다.

빌드 아티팩트는 생성된 코드라서 제외한다. dist/, out/, .vite/ 같은 폴더는 소스 코드에서 만들어진 결과물이다. 소스만 있으면 빌드 결과는 언제든 다시 만들 수 있다.

완료된 작업은 선택적으로 제외한다:
```
PHASE3-*.md          # 완료된 리팩토링
demos/archived/      # 실패한 실험
03-REFERENCE/        # 검색 시만
```

완료된 리팩토링 문서나 실패한 실험은 일상 개발에 불필요하다. 이미 끝난 작업이기 때문이다.

이 프로젝트의 경우 .gitignore로 상당한 토큰을 절약한다.

## Docs 구조화 전략

문서를 계층화하면 컨텍스트를 단계별로 로드할 수 있다.

46개 문서를 한 번에 읽으면 125K가 된다. 이걸 4단계로 나눠서 필요할 때만 읽으면 베이스라인이 20K로 줄어든다. 세션 시작 시 5K만 로드하고, Demo 단계에서 10K, 통합 단계에서 15K를 추가로 읽는다. 컨텍스트가 작을수록 AI가 관련 정보에 집중한다.

```
docs/
├── 00-시작/          (4개, 5K)   - 항상 로드
├── 01-워크플로우/     (5개, 10K)  - Demo 단계
├── 02-아키텍처/       (11개, 15K) - 통합 단계
└── 03-참고자료/       (26개, 30K+) - 검색 전용
```

세션 시작 시 5K만 로드한다. 필요한 단계에서 10-15K씩 추가로 읽는다. 총 베이스라인이 125K에서 15-30K로 줄어든다.

00-시작은 프로젝트 개요, 폴더 구조, Quick Start를 담는다. 모든 세션이 읽기 때문에 최대한 간결하게 핵심만 담는다. 00-시작하기.md, 01-개요.md, 02-구조.md, README.md가 있다.

01-워크플로우는 Demo-First, 개발 원칙, 코딩 컨벤션을 담는다. Demo 단계에 필요한 문서들이다. 개발-워크플로우.md, 개발-전략.md, 코딩-가이드.md, 비전-개발원칙.md, 11-코딩컨벤션.md, 개발-시작가이드.md가 있다.

02-아키텍처는 컴포넌트 구조, IPC 패턴, 상태 관리, 보안을 담는다. 통합 단계에 필요한 깊은 이해를 위한 문서들이다. 03-흐름.md부터 10-상태관리.md까지 핵심 아키텍처 문서와 가이드 문서들이 있다.

03-참고자료는 나머지 상세 문서들을 모두 넣는다. 기본적으로 안 읽고 검색할 때만 참고한다. 빌드, 테스트, 스타일가이드, ADR, 명세서, 참고 문서들이 포함된다.

## Git Worktree 전략

Worktree는 물리적 디렉토리를 분리해서 컨텍스트를 격리한다.

Worktree 자체는 브랜치를 새 디렉토리에 체크아웃하는 것이다. demo/inbox 브랜치가 main에서 갓 분기했다면 worktree에도 전체 코드가 있다. 컨텍스트 감소는 worktree가 아니라 작업 방식에서 온다. demos/inbox/ 폴더만 집중적으로 작업하면 AI가 해당 폴더 코드만 주로 로드한다. 나머지 코드는 참조만 하거나 안 읽는다. 이렇게 하면 125K 코드베이스 중 demos/inbox/ 폴더의 15K만 활발히 로드된다.

Claude Code는 작업 디렉토리의 코드베이스를 로드한다. 같은 디렉토리를 여러 창에서 열면 컨텍스트가 공유된다. 백엔드 작업 시 프론트엔드 코드가 섞이고, 프론트 작업 시 백엔드 코드가 섞인다. 필요 없는 코드가 토큰을 낭비하고 AI를 산만하게 만든다.

Worktree로 디렉토리를 분리하면 각 창이 독립된 컨텍스트를 가진다. demos/inbox 작업 시 inbox 코드만 보고, backend/api 작업 시 API 코드만 본다. 컨텍스트 혼선이 없다.

단일 세션에서 3개 데모를 순차 개발하면 작업 공간이 점점 줄어든다. Demo1(15K) + Demo2(15K) + Demo3(15K) = 45K가 누적되면 작업 공간이 200K에서 155K로 줄어든다. Worktree로 분리하면 각 창이 독립적으로 15K만 쓴다. 작업 공간이 200K - 15K = 185K가 된다. 3개 창이면 185K × 3 = 555K다. 3.6배 효율이다.

컨텍스트 오염도 없다. Inbox worktree의 Claude는 Project나 Capture 코드를 전혀 모른다. "Lost in the Middle" 문제가 발생하지 않는다.

Worktree는 단일 기능 개발과 병렬 개발 모두에서 쓴다. 단일 기능도 worktree로 격리하면 컨텍스트가 깨끗하다. 병렬 개발 시에는 2-3개 worktree를 동시에 사용한다.

분리된 worktree는 나중에 main에 병합할 때 문제없다. 각 worktree의 커밋 히스토리가 독립적으로 유지되다가 merge 시점에 깔끔하게 합쳐진다. Git이 자동으로 처리하기 때문에 충돌만 해결하면 된다.

## Codex-Claude Loop 전략

품질 검증 루프다. Claude가 계획하고 구현하면 Codex가 검증해서 피드백한다. 반복해서 코드 품질을 올린다.

6단계로 진행된다. Claude가 계획을 세우면 Codex가 로직 오류, 빠진 엣지 케이스, 보안 문제를 찾는다. 문제가 있으면 Claude가 수정하고 다시 검증받는다. 계획이 통과하면 Claude가 구현한다. 구현이 끝나면 Codex가 코드를 리뷰한다. 버그나 성능 이슈가 있으면 Claude가 고치고 재검증받는다. 품질 기준을 만족할 때까지 반복한다.

복잡한 알고리즘은 generate_code로 Codex를 호출해서 생성할 수 있다. 보안 관련(OAuth, JWT, 암호화), 성능 critical(정렬 알고리즘, 데이터 처리), 수학 연산(통계, 인코딩)이 해당한다. Claude가 구현 중에 PKCE 같은 복잡한 알고리즘을 만나면 generate_code로 Codex를 호출해서 생성하고 프로젝트에 통합한다. 나머지는 Claude가 직접 구현한다.

결과적으로 코드 품질이 올라간다. 계획 단계에서 로직 오류를 잡고, 구현 단계에서 버그를 미리 발견한다. 복잡한 알고리즘은 검증된 코드를 쓰고, 전체 일관성은 Claude가 유지한다.

구현 단계에서 AI가 복잡도를 판단해서 자동으로 사용한다. 인증/결제/보안 로직 같은 품질 중요 기능에서 주로 실행된다.

## Poetiq-TDD 전략

테스트 기반 자동화 개발 루프다. Poetiq ARC-AGI 논문에서 영감을 받았다. 테스트 결과가 피드백이 되어 AI가 스스로 개선한다.

핵심 원칙은 세 가지다. 테스트가 진실의 원천이다. 주관적 코드 리뷰보다 객관적 테스트 결과를 신뢰한다. 컨텍스트는 작게 유지한다. Worktree와 배치 분할로 격리한다. 실패는 학습이다. 실패 피드백을 다음 시도에 활용한다.

Codex-Claude Loop와의 차이가 있다. Codex-Claude는 Codex가 코드를 리뷰해서 피드백한다. Poetiq-TDD는 테스트 실행 결과가 피드백이다. 둘 다 쓸 수 있다. 복잡한 기능은 Codex-Claude로 설계하고, 구현은 Poetiq-TDD로 검증한다.

실행 흐름은 다음과 같다:

```
1. 테스트 케이스 선택 (배치 단위, 5-10개)
2. AI가 구현
3. 테스트 실행 (Vitest)
4. 실패 시 → 에러 메시지를 피드백으로 재구현
5. 통과 시 → 다음 배치로
6. 최대 5회 시도, 실패 시 스킵 & 로그
```

배치 분할 기준이 있다. 의존성 순서를 따른다. 선행 테스트가 먼저다. 복잡도를 고려한다. 쉬운 것부터 한다. 모듈 단위로 묶는다. 같은 컴포넌트끼리 배치한다.

예시를 보면:
- Batch 1: F4-8~11 (탭 단축키) - 같은 모듈
- Batch 2: U7-1~4 (접근성) - 같은 관심사
- Batch 3: M5-1~4 (파일 관리) - 같은 기능

피드백 구조는 다음과 같다:

```json
{
  "test_id": "F4-8",
  "status": "fail",
  "error": "KeyboardEvent not triggered",
  "expected": "new tab created",
  "actual": "no change"
}
```

자동 종료 조건이 있다. 모든 테스트 통과, lint 통과, 타입 체크 통과면 완료다. 5회 시도 후에도 실패하면 스킵하고 로그를 남긴다. 스킵된 테스트는 나중에 수동 검토한다.

Tier별 진행 계획이 있다. Tier 1은 뼈대, UI, 메모다. 4일이면 31%에서 41%로 올라간다. Tier 2는 정리, 포스트잇, 검색이다. 2주면 67%가 된다. Tier 3는 수집, AI, 협업이다. 4주면 100%다.

테스트 케이스 문서는 docs/구현목표/테스트케이스/에 있다. 갭 분석 문서도 같은 위치에 있다.
