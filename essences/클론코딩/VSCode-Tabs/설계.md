# 설계.md - VSCode Tabs 핵심 설계 결정

VSCode Tabs 구현의 핵심 설계 결정과 이유를 기록한다.

## 아키텍처 개요

VSCode 탭 시스템을 완벽하게 복제했다. 단일/다중 창 환경에서 탭을 드래그해서 분할하고, 그룹을 재배치하고, 창 간 이동할 수 있다.

크게 3개 계층으로 나뉜다:
- Core 계층: 순수 로직 (상태 관리, 드래그 처리, 분할 알고리즘)
- Integration 계층: React 통합 (컴포넌트, 훅)
- IPC 계층: 멀티 윈도우 통신

## 핵심 설계 결정

### 1. 좌표계 설계 - 다중 창 환경

다중 창에서 드래그하면 좌표가 복잡해진다. 창마다 원점이 다르고, 마우스 이벤트는 각 창의 로컬 좌표로 들어온다.

우리는 글로벌 화면 좌표계를 사용한다. 모든 좌표를 스크린 기준으로 변환해서 창 경계를 넘어도 일관되게 처리한다.

```typescript
// 로컬 → 글로벌 변환
const globalX = clientX + window.screenX;
const globalY = clientY + window.screenY;
```

이렇게 하면 다른 창으로 드래그할 때도 정확한 위치 계산이 가능하다.

### 2. 상태 관리 - Zustand로 단순화

VSCode처럼 복잡한 UI는 상태 관리가 중요하다. 우리는 Zustand를 선택했다.

Redux는 너무 복잡하다. boilerplate가 많고 설정이 귀찮다. Context API는 리렌더링 문제가 있다. Zustand는 둘의 장점만 가져왔다.

```typescript
const useEditorGroupStore = create<EditorGroupState>((set) => ({
  groups: [],
  activeGroupId: null,
  addGroup: (group) => set((state) => ({
    groups: [...state.groups, group]
  }))
}));
```

스토어 설계는 VSCode의 EditorGroupsService를 참고했다. 그룹 단위로 상태를 관리하고, 각 그룹은 독립적인 탭 리스트를 가진다.

### 3. 드래그 앤 드롭 - 네이티브 API 사용

React DnD 같은 라이브러리를 쓰지 않았다. 네이티브 HTML5 Drag and Drop API만으로도 충분하다.

특히 Electron 환경에서는 네이티브가 더 안정적이다. 창 간 드래그를 지원하려면 어차피 브라우저 API를 직접 다뤄야 한다.

```typescript
const handleDragStart = (e: DragEvent, tab: EditorTab) => {
  e.dataTransfer.effectAllowed = 'move';
  e.dataTransfer.setData('application/vscode-tab', JSON.stringify({
    tabId: tab.id,
    groupId: currentGroupId
  }));
};
```

문제는 드래그 중 실시간 피드백이다. `dragover` 이벤트에서 드롭 존을 계산하고 시각적 힌트를 업데이트한다.

### 4. 분할 알고리즘 - Grid 기반 레이아웃

VSCode는 그룹을 그리드로 배치한다. 우린 동일한 알고리즘을 구현했다.

핵심은 드래그 위치에 따라 분할 방향을 결정하는 거다. 그룹의 어느 영역에 드롭하느냐에 따라 상하좌우로 나눈다.

```typescript
function calculateDropPosition(
  rect: DOMRect,
  x: number,
  y: number
): DropPosition {
  const threshold = 0.3; // 30% 영역
  const relX = (x - rect.left) / rect.width;
  const relY = (y - rect.top) / rect.height;

  if (relX < threshold) return 'left';
  if (relX > 1 - threshold) return 'right';
  if (relY < threshold) return 'top';
  if (relY > 1 - threshold) return 'bottom';
  return 'center'; // 탭으로 추가
}
```

분할하면 그룹이 2개로 나뉜다. GridView가 자동으로 레이아웃을 계산해서 50:50 비율로 배치한다.

### 5. IPC 통신 - Auxiliary Window 패턴

다중 창 지원이 가장 어려웠다. Electron의 BrowserWindow는 독립적인 프로세스라 직접 통신이 안 된다.

우리는 Main Process를 중계자로 쓴다:
1. 창 A에서 드래그 시작 → Main에 알림
2. Main이 모든 창에 드래그 상태 브로드캐스트
3. 창 B에서 드롭 → Main이 탭 데이터 전달
4. Main이 창 A에 탭 제거 명령

```typescript
// Renderer → Main
window.electronAPI.tabs.startDrag({ tabId, groupId, windowId });

// Main → All Windows
mainWindow.webContents.send('tab-drag-update', dragState);
```

이 패턴은 VSCode의 Auxiliary Window API를 참고했다. VSCode도 동일하게 메인 프로세스가 창 간 상태를 동기화한다.

### 6. 성능 최적화 - 렌더링 최소화

탭이 많아지면 리렌더링이 문제가 된다. 특히 드래그 중에는 60fps를 유지해야 자연스럽다.

최적화 전략:
- `React.memo`로 불필요한 리렌더 방지
- `useMemo`로 비싼 계산 캐싱
- 드래그 피드백은 CSS transform 사용 (리페인트 최소화)
- 디바운싱으로 이벤트 빈도 제어

```typescript
const TabItem = React.memo(({ tab, isActive }: TabItemProps) => {
  // 탭 내용
}, (prev, next) => {
  // 커스텀 비교 함수
  return prev.tab.id === next.tab.id
    && prev.isActive === next.isActive;
});
```

특히 `dragover` 이벤트는 초당 수십 번 발생한다. 디바운싱 없이는 UI가 버벅인다.

### 7. 타입 안전성 - 계약 기반 설계

IPC 통신은 타입이 없어서 위험하다. 우린 계약(Contract) 패턴을 사용한다.

```typescript
// contracts.ts
export interface TabsAPI {
  createGroup(options: CreateGroupOptions): Promise<EditorGroup>;
  moveTab(tabId: string, targetGroupId: string): Promise<void>;
}

// renderer
const group = await window.electronAPI.tabs.createGroup(options);
```

계약을 먼저 정의하고, Main과 Renderer가 같은 타입을 사용한다. 타입 불일치는 컴파일 타임에 잡힌다.

## 설계 원칙

### 단일 책임 원칙

각 모듈은 하나의 역할만 한다:
- `EditorGroupStore`: 상태 관리만
- `DragCoordinator`: 드래그 로직만
- `SplitAlgorithm`: 분할 계산만
- `GridView`: 레이아웃 렌더링만

책임이 명확하면 테스트하기 쉽고, 수정할 때 영향 범위가 작다.

### 의존성 역전

상위 레벨 모듈이 하위 모듈에 의존하지 않는다. 둘 다 추상화(인터페이스)에 의존한다.

```typescript
// Bad: GridView가 구체적인 Store에 의존
class GridView {
  constructor(private store: EditorGroupStore) {}
}

// Good: 인터페이스에 의존
interface GroupProvider {
  getGroups(): EditorGroup[];
}

class GridView {
  constructor(private provider: GroupProvider) {}
}
```

이렇게 하면 테스트할 때 Mock을 쉽게 주입할 수 있다.

### 개방-폐쇄 원칙

기능 추가는 쉽게, 기존 코드 수정은 최소화한다.

예를 들어 새로운 드롭 존 타입을 추가하려면:
```typescript
// 기존 코드 수정 없이 확장
type DropZone = 'tab' | 'split-left' | 'split-right'
  | 'split-top' | 'split-bottom' | 'new-window'; // 새로 추가
```

switch 문 대신 맵을 사용하면 더 확장하기 쉽다.

## 트레이드오프

### 복잡도 vs 기능

VSCode 완벽 복제를 목표로 했기 때문에 코드가 복잡해졌다. 단순한 탭 시스템이라면 이렇게까지 할 필요 없다.

특히 다중 창 지원은 코드 복잡도를 2배로 늘렸다. 하지만 사용자 경험은 확실히 좋아졌다.

### 성능 vs 정확도

드래그 피드백은 30ms마다 업데이트한다. 더 자주 하면 정확하지만 CPU를 많이 쓴다. 30ms는 눈으로 느끼기 어려운 지연이라 적절한 타협점이다.

### 타입 안전성 vs 유연성

엄격한 타입 체크는 안전하지만 제약이 많다. 우린 안전성을 선택했다. 런타임 에러보다 컴파일 에러가 낫다.

## 참고한 VSCode 코드

- `src/vs/workbench/browser/parts/editor/editorGroupsService.ts`: 그룹 관리 로직
- `src/vs/base/browser/ui/grid/grid.ts`: 그리드 레이아웃 알고리즘
- `src/vs/workbench/services/auxiliaryWindow/electron-sandbox/auxiliaryWindowService.ts`: 다중 창 처리

VSCode는 오픈소스라 코드를 볼 수 있다. 알고리즘과 패턴을 많이 참고했다.

## 다음 개선 방향

현재 구현은 기본 기능은 완벽하다. 하지만 VSCode에는 더 많은 기능이 있다:

1. 탭 그룹 크기 조절 (드래그해서 비율 변경)
2. 키보드 네비게이션 (Ctrl+Tab으로 탭 전환)
3. 탭 미리보기 (호버 시 내용 미리보기)
4. 세션 복원 (앱 재시작 시 탭 상태 복원)

하지만 지금은 "Demo → Feature" 철학에 맞춰 핵심만 구현했다. 나머지는 필요할 때 추가한다.
