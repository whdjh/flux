# 시나리오: 데이터 모델

하이브리드 모델(Item + Document)이 실제 사용 흐름에서 어떻게 동작하는지 보여준다.


## UX 리서치 시나리오

브라우저에서 닐슨노먼 그룹 아티클을 읽다가 중요한 문장을 드래그해서 수집한다. ARC 브라우저 스크린샷도 찍는다. 드리블에서 본 UI 이미지도 저장한다. 10개쯤 쌓인다.

정리 단계에 들어간다. 메모를 열고 "UX 리서치 정리"를 쓰기 시작한다. 수집한 것 중 3개를 메모로 드래그해서 넣고, 자기 생각을 덧붙인다.

```
items 테이블 (가벼움, SQLite):
  { id: 1, type: "text", content: "닐슨노먼 문장...", url: "...", summary: "...", keywords: [...] }
  { id: 2, type: "image", file_path: "arc-screenshot.png", summary: "..." }
  { id: 3, type: "image", file_path: "dribbble-ui.png", summary: "..." }

documents 테이블 (무거움, loro CRDT):
  { id: 1, title: "UX 리서치 정리", crdt_doc: <loro binary> }

  loro 문서 내부:
    - 텍스트 블록: "내 생각은..."
    - 임베드 블록: { item_id: 1 }  ← items 참조
    - 임베드 블록: { item_id: 2 }  ← items 참조
    - 텍스트 블록: "이 UI가 좋은 이유는..."
```

수집은 items에 행 하나 INSERT. 메타데이터만 저장하니 < 100ms. 메모 작성은 documents에서 loro로 리치 편집. 드래그하면 원본 Item을 참조한다. Item 원본은 항상 보존된다(비전의 진본성 원칙).


## 검토한 대안

분리형(A)은 Item과 Note가 완전히 별개 테이블이다. 드래그로 옮길 때 복사하면 원본과 분리되고, 참조하면 두 테이블 사이 관계가 복잡해진다. 검색도 따로 해서 합쳐야 한다.

통합형(B)은 모든 것이 loro 문서다. 수집물도 loro 문서로 만든다. 통일성은 좋지만 링크 하나 저장하는데 변경 이력을 추적하는 loro 문서를 만드는 건 과하다. 수집 < 100ms 제약을 지키기 어렵다.

하이브리드(C)는 수집은 가볍게, 편집은 무겁게. 각자의 성격에 맞는 저장 방식을 쓴다.


## 비용 최적화

Redis를 제거하고 tokio::broadcast(인메모리)로 시작하기로 했다. 규모별 전환 기준:

```
tokio::broadcast (단일 서버):      동시접속 수천, DAU 1만 미만
PostgreSQL LISTEN/NOTIFY (2~3대):  DAU 수만
Redis pub/sub (10대+):             DAU 수십만
```

개인 생산성 도구 특성상 동시접속이 적다. 유저 1만이면 동시 WebSocket 2~3만(기기 2~3대). tokio::broadcast로 충분하다.

이미지 압축(WebP 변환, 썸네일)은 아키텍처 결정이 아니라 구현 디테일로 보류했다. 구현할 때 정한다.


## 프로젝트 구조 (미결정)

두 가지 안을 검토했다. A안(단일 크레이트 + 모듈)을 추천한 상태. 사용자 결정 전에 컴팩트됨.

A) 단일 크레이트: src/ 아래 auth/, handlers/, models/, services/, db/, sync/ 모듈. 초기에 간단하고 나중에 워크스페이스로 분리 가능.

B) Cargo 워크스페이스: crates/ 아래 server, domain, db, sync, auth 크레이트. 컴파일 캐싱 이점 있지만 초기 보일러플레이트 많음.
