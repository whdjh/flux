1. scaffolder 자동감지 의도
project-scaffolder.md Step 3-4를 보면 의도가 명확하다:

Step 3 (기술 스택 감지): package.json, pyproject.toml 등 기존 설정 파일을 읽어서 프레임워크, 빌드 명령어, 의존성을 파악
Step 4 (디렉토리 구조 스캔): 기존 폴더를 스캔해서 src/, components/, api/ 등 역할을 추론
Step 5 (CLAUDE.md 생성): 감지한 정보로 7개 섹션을 채우고, 감지 불가한 건 {TODO}로 남김
"자동감지로 만든다" = 기존 프로젝트 파일에서 정보를 추출해서 CLAUDE.md 초안을 만든다는 뜻이다. 새로 설계하는 게 아니라 읽는 것이다.

꼬인 부분: tree-planner가 구조를 설계하고 scaffolder가 구조를 스캔하는데, 설계한 구조를 실제로 만드는 단계가 없다. tree-planner 출력(폴더 트리)을 받아서 mkdir -p로 생성하는 역할이 scaffolder에 있어야 하는지, 별도 단계인지가 미정이다. 커밋 메시지에 TODO로 남기겠다.

2. naming-reviewer: 생성 vs 검증
naming-reviewer.md를 보면 검증 전용이 맞다:

Input Modes 3가지 모두 "이미 존재하는 이름"을 전제
Step 4 "Suggest Alternatives"에서 대안을 제안하긴 한다 — 하지만 이건 "기존 이름이 나쁠 때 대체안"이지 "처음부터 이름을 지어주는 것"이 아니다
에이전트.md의 2단계 설명은 정확하다:

"naming-reviewer 자체는 생성이 아니라 검증을 한다. 그래서 2단계로 진행한다."

이름이 필요할 때 naming-reviewer에 바로 "이름 지어줘"라고 하면 동작은 하겠지만, 설계 의도는 생성과 검증을 분리하는 것이다. 같은 AI가 만들고 검증하면 자기 생성물에 편향된다.

다만, 현실적으로 2단계가 번거로우면 naming-reviewer에 "생성 모드"를 추가하는 것도 고려할 수 있다. 지금 에이전트 스펙을 바꿀지는 별도 결정이 필요하니 커밋 메시지에 같이 적겠다.

핵심: 세 가지 연산이 반복된다
에센스, 스코프, 이름생성은 개별 에이전트가 아니라 모든 정리/생성 작업에 반복되는 기본 연산이다.
연산	질문	북마크 1300개	흩어진 파일 15경로	프로젝트 시작
에센스	이것들이 뭔가?	글, 도구, 튜토리얼, 영감...	연구, 포트폴리오, 메모...	요구사항, 디자인, 레퍼런스...
스코프	어떻게 묶을까?	주제별? 용도별?	프로젝트별? 시기별?	기능별? 레이어별?
이름	뭐라 부를까?	폴더명 생성	폴더명 생성	모듈명, 파일명 생성
구조	어디에 놓을까?	트리 설계	통합 트리 설계	프로젝트 구조 설계
대화	이게 맞아?	수정, 확인	수정, 확인	수정, 확인
규모와 대상이 달라도 연산은 같다. 그리고 매 단계마다 대화가 끼어든다.

전체 라이프사이클
너가 설명한 흐름을 단계로 나눠본다.
1. 수확 (Harvest)
흩어진 것들을 모은다. 북마크 1300개, 파일 15경로, 아이디어 s들. 아직 구조는 없다. "가지고 있는 것"의 목록을 만드는 단계다.
에센스 연산이 여기서 발생한다. 각 항목이 뭔지 분류한다.
현재 에이전트: 없음. 사람이 직접 모으거나, 도구(브라우저 내보내기, find 명령 등)로 수집한다.
갭: 에센스 추출을 돕는 에이전트가 없다. guide-filler가 에센스를 소비하지만, 수확은 사람 몫이다.
2. 정리 (Organize)
수확한 것들에 구조를 부여한다. 스코프를 발견하고, 트리를 설계하고, 이름을 짓고, 대화하면서 다듬고, 확인되면 생성한다.
세 연산(스코프 → 구조 → 이름)이 여기서 모두 발생하고, 대화 루프가 이 단계의 핵심이다.
에이전트: scope-validator, tree-planner, naming-reviewer
3. 부트스트랩 (Bootstrap)
프로젝트를 시작한다. 정리된 아이디어와 레퍼런스에서 프로젝트 골격을 만든다.
CLAUDE.md, context/, .gitmessage 생성
기술 스택, 인프라 결정
디자인 컨벤션, 깃 컨벤션, 문서 기록 방식 결정
각 가이드를 레시피 + 에센스로 채움
에이전트: project-scaffolder (→ tree-planner), scope-validator, recipe-builder, guide-filler, recipe-checker
4. 분해 (Decompose)
기능을 최대한 잘게 쪼갠다. 병렬 가능한 작업을 분리하고, 각 워크트리에 넣을 프롬프트를 생성한다.
기능 목록 → work unit 분해
의존 관계 파악 → 병렬/순차 구분
worktree 명령어 + 세션 프롬프트 생성
에이전트: planner/architect, feature-decomposer, prompt-builder
5. 구현 루프 (Build Loop)
코드를 작성하면서 동시에 문서를 업데이트하는 루프다. 이 두 가지가 분리된 단계가 아니라 하나의 루프 안에서 돈다.

┌─────────────────────────────────────────┐
│  코드 작성 (tdd-guide)                    │
│    ↓                                     │
│  리뷰 (code-reviewer, security-reviewer)  │
│    ↓                                     │
│  커밋                                     │
│    ↓                                     │
│  맥락 기록 (context-writer)               │
│    ↓                                     │
│  문서 업데이트 (feature-map, 진행현황)      │
│    ↓                                     │
│  다음 work unit ──→ (루프 반복)            │
└─────────────────────────────────────────┘
에이전트: tdd-guide, code-reviewer, security-reviewer, build-error-resolver, database-reviewer, context-writer
6. 탐색 (Discover)
모든 단계에 걸쳐 있다. "이 작업에 맞는 에이전트가 있나?" "이 문제를 해결하는 도구가 있나?"
현재: agents.md 규칙에서 수동으로 매칭
갭: 작업을 설명하면 적합한 에이전트를 추천하는 메커니즘이 없다

현재 갭
단계	갭	심각도
수확	에센스 추출 에이전트 없음	보통 (사람이 할 수 있다)
정리	tree-planner에 대화 루프가 프로세스로 명시 안 됨	높음 (이번 세션에서 수정 중)
구현 루프	루프 오케스트레이션이 사람 의존	보통 (구현 단계니까 자연스러움)
탐색	에이전트 추천 메커니즘 없음	낮음 (에이전트가 10개 수준이라 수동으로 충분)
여기까지가 내가 이해한 전체 그림이다. 빠진 단계나 잘못 나눈 부분이 있으면 알려줘.
