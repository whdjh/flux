1. scaffolder 자동감지 의도
project-scaffolder.md Step 3-4를 보면 의도가 명확하다:

Step 3 (기술 스택 감지): package.json, pyproject.toml 등 기존 설정 파일을 읽어서 프레임워크, 빌드 명령어, 의존성을 파악
Step 4 (디렉토리 구조 스캔): 기존 폴더를 스캔해서 src/, components/, api/ 등 역할을 추론
Step 5 (CLAUDE.md 생성): 감지한 정보로 7개 섹션을 채우고, 감지 불가한 건 {TODO}로 남김
"자동감지로 만든다" = 기존 프로젝트 파일에서 정보를 추출해서 CLAUDE.md 초안을 만든다는 뜻이다. 새로 설계하는 게 아니라 읽는 것이다.

꼬인 부분: tree-planner가 구조를 설계하고 scaffolder가 구조를 스캔하는데, 설계한 구조를 실제로 만드는 단계가 없다. tree-planner 출력(폴더 트리)을 받아서 mkdir -p로 생성하는 역할이 scaffolder에 있어야 하는지, 별도 단계인지가 미정이다. 커밋 메시지에 TODO로 남기겠다.

2. naming-reviewer: 생성 vs 검증
naming-reviewer.md를 보면 검증 전용이 맞다:

Input Modes 3가지 모두 "이미 존재하는 이름"을 전제
Step 4 "Suggest Alternatives"에서 대안을 제안하긴 한다 — 하지만 이건 "기존 이름이 나쁠 때 대체안"이지 "처음부터 이름을 지어주는 것"이 아니다
에이전트.md의 2단계 설명은 정확하다:

"naming-reviewer 자체는 생성이 아니라 검증을 한다. 그래서 2단계로 진행한다."

이름이 필요할 때 naming-reviewer에 바로 "이름 지어줘"라고 하면 동작은 하겠지만, 설계 의도는 생성과 검증을 분리하는 것이다. 같은 AI가 만들고 검증하면 자기 생성물에 편향된다.

다만, 현실적으로 2단계가 번거로우면 naming-reviewer에 "생성 모드"를 추가하는 것도 고려할 수 있다. 지금 에이전트 스펙을 바꿀지는 별도 결정이 필요하니 커밋 메시지에 같이 적겠다.

3. 무신사 코테 예시
수강신청 시스템이 보일러플레이트 테스트 케이스로 딱 맞다:

CLAUDE.md 필수 (과제 제출물에 포함)

이건 다음 세션에서 실제로 파이프라인을 돌려보면 된다. 지금은 커밋부터 하겠다.

빈곳이 없어?

큰 그림, 각각의 에이전트, 레시피, 가이드마다의 의도들이 모두 잘 적혀있고, 사용자가 스캔하기 좋아?
빈 것들이 없어?
근거, 의도,
'이 설계에서 사람의 역할이 정확히 한 곳에 집중되어 있다 — 재료 수집. 스코프 발견, 레시피 생성, 문서 변환, 완전성 검증은 전부 에이전트가 하지만, "이 프로젝트의 브랜드 색상이 뭔지", "클라이언트가 뭘 요구했는지"는 사람만 알 수 있다. 자동화할 수 있는 건 자동화하고, 사람만 할 수 있는 건 사람에게 남긴 것이다.
'
"이 보일러플레이트가 존재하는 이유", "해결하려는 근본 문제", "설계 철학의 전체 그림"
'프로젝트가 바뀔 때마다 CLAUDE.md를 처음부터 쓰고, 규칙을 다시 정하고, 워크플로우를 재발명하는 반복을 없애려는 것이다. 한 번 검증된 패턴을 레시피로 고정하고, 새 프로젝트에서는 재료만 넣으면 프로젝트 문서가 나오게 만든다.'

'① scope-validator       스코프 발견/검증
② recipe-builder        레시피 골격 생성
③ tree-planner          폴더/파일 구조 설계
④ project-scaffolder    CLAUDE.md + 문서 체크리스트
⑤ guide-filler          재료 수집 + 변환 + 자체 검증
⑥ recipe-checker        완전성 검증'

여기서 폴더, 파일 구조 제안하는 에이전트에 이름짓기 에이전트가 들어가겠지. 또 필요한데 빼먹은 녀석들이 있나?'

사용자가 이 보일러플레이트를 처음 만나면
1단계: README를 읽는다

핵심 개념(에센스, 스코프, 레시피)을 이해하고, 폴더 구조를 본다. 워크플로우 7단계를 읽는다. "아, 에센스를 모으고 AI에게 주면 문서를 만들어주는 시스템이구나."

여기까지는 괜찮다.

2단계: 설치하려 한다

README.md:274-280의 설치 순서를 따른다:

Claude Code 설치
/config 설정

"추가 파일들 cp로 복사"

3단계: 새 프로젝트를 시작한다

project-scaffolder를 실행한다. CLAUDE.md, context/, .gitmessage.txt가 생기고 문서 체크리스트가 나온다. "디자인 가이드(에센스: 브랜드 색상, 타이포), 워크플로우 가이드(에센스: 팀 규모, 도구)를 만들어라."

여기까지 순조롭다.

4단계: 에센스를 모으려 한다

→ 가장 큰 막힘. "에센스를 수집하라"는데:

어디에 넣지? README 폴더 구조는 guides/디자인/에센스/를 보여주는데, 이건 보일러플레이트 안이다. 보일러플레이트는 심링크로 공유하는 템플릿인데, 프로젝트별 에센스를 여기에 넣으면 다른 프로젝트와 섞인다. 프로젝트 디렉토리에 넣어야 하는 건지, 보일러플레이트에 넣어야 하는 건지 안 쓰여 있다.

뭘 모으지? 체크리스트가 "브랜드 색상 HEX 값"이라고 하는데, Figma에서 캡처하면 되나? 텍스트로 정리해야 하나? "날것도 괜찮다"고 하지만 구체적 예시가 없다.

얼마나 모으면 충분하지? 체크리스트의 [ ] 항목을 다 채워야 하는 건지, 일부만 있어도 guide-filler가 나머지를 [TODO]로 남기는 건지.

5단계: guide-filler를 부른다

에센스를 어떻게든 모았다고 치면, "디자인 가이드 만들어줘"라고 한다. guide-filler가 에센스 완전성 보고를 하고 문서를 생성한다.

→ 여기는 에이전트가 잘 안내하므로 상대적으로 순조롭다.

6단계: 생성된 문서를 확인하고 recipe-checker를 돌린다

이것도 괜찮다.

설치	"추가 파일들 cp로 복사"가 모호	README 설치 순서 불완전

가장 큰 문제는 에센스의 물리적 위치다. 보일러플레이트 폴더 구조에 에센스/가 있어서 "여기에 넣으라는 거구나"로 보이는데, 보일러플레이트는 공유 템플릿이니까 프로젝트별 에센스가 여기 들어가면 안 된다. 이 아키텍처 결정이 명시되지 않았다.

★ Insight ─────────────────────────────────────

README의 폴더 구조 다이어그램이 "이렇게 생겼다"를 보여주지만 "이건 템플릿이고 에센스/는 프로젝트에 복사된다"인지 "보일러플레이트에 직접 넣는다"인지가 불명확하다. 이건 GAP 1-8과 다른 종류의 빈 곳이다. 의도나 경로의 빈 곳이 아니라 아키텍처의 빈 곳이다.
