## Backend-Centric File System

### 설계 원칙

**"Frontend는 UI만, Backend는 모든 로직"**

Renderer는 비즈니스 로직이 없다. path 계산, 캐싱, 재귀 알고리즘 모두 Backend에 있다.

```
┌─────────────────────────────────────────┐
│   Renderer (Dumb UI)                    │
│  - IPC 호출만                           │
│  - UI 렌더링만                          │
│  - path.join() 사용하지 않음             │
│  - 비즈니스 로직 없음                    │
└──────────────┬──────────────────────────┘
               │
          IPC 호출
               │
┌──────────────┴──────────────────────────┐
│   Main (Smart Backend)                  │
│  - 모든 path 계산                       │
│  - 파일 시스템 로직                     │
│  - 데이터 검증 (Zod)                    │
│  - 보안 검증 (PathValidator)            │
│  - 캐싱, 배치 처리                      │
└─────────────────────────────────────────┘
```

### API 설계: Result Objects

```typescript
// Rich Result Objects
interface RenameResult {
  success: boolean;
  oldPath: string;
  newPath: string;  // Backend 계산
}

// Renderer: 이름만 전달
await renameItem('/home/file.txt', 'newName.txt')
// Backend가 newPath 계산해서 반환

// 이전: Renderer가 path 계산 (금지)
const newPath = path.join(path.dirname(oldPath), newName)
```

### 보안 3-Layer

```typescript
// Layer 1: Zod (IPC 입력 검증)
const RenameSchema = z.object({
  oldPath: z.string(),
  newName: z.string().max(255)
});

// Layer 2: PathValidator (보안 검증)
if (path.includes('..')) throw Error('Path traversal');

// Layer 3: File System (실제 작업)
await fs.rename(oldPath, newPath);
```

### 성능 최적화

```typescript
// 병렬 배치 처리
await Promise.all(paths.map(p => deleteItem(p)));

// Backend Only 캐싱 (중복 제거)
FileCacheService.get(key);

// 불필요한 IPC 호출 감소
computeCopiedPaths() // Backend에서 한 번에 계산
```

### 이점

- **보안**: PathValidator가 모든 path 검증
- **크로스 플랫폼**: Backend가 Windows/Unix path 처리
- **성능**: 병렬 처리, 단일 캐싱
- **유지보수**: 명확한 책임 분리, 테스트 용이
- **타입 안전**: Result objects로 명확한 API

## 폴더 매핑

### demos/ vs features/

demos/는 실험적 기능을 담는다. 테스트 없어도 괜찮고, 빠른 프로토타입이 목적이다. 삭제 가능하다.

features/는 프로덕션 준비 완료된 기능을 담는다. 테스트가 필수고, 문서화도 필수다. 안정적인 API를 제공한다.

### Monolithic vs Modular

현재는 Feature-Based Modular 구조다.

src/features/file-explorer/는 파일 탐색 기능을 담는다. src/features/editor-groups/는 에디터 그룹 기능을 담는다. 각 feature는 독립적이다. components, hooks, store, tests를 모두 가지고 있다.

## 의존성 방향

```
UI Components
    ↓
Zustand Store
    ↓
IPC API (Preload)
    ↓
Main IPC Handler
    ↓
Application Use Case
    ↓
Domain Logic
    ↓
Infrastructure (DB)
```

위에서 아래로만 의존한다. 역방향은 금지다.
