이제 전체 여정을 추적하겠다. 사용자가 묘사한 흐름을 단계별로 따라가면서 현재 UX와 갭을 짚는다.

1단계: 수확 — 흩어진 재료 모으기

북마크 1300개, 파일 경로 15개, 메모들
        ↓
    "프로젝트 시작하고 싶다"
현재 UX: 완전 수동. 라이프사이클에서 수확(Harvest)은 "(수동)"으로 명시되어 있다.

갭: 5기본연산은 여기서도 작동하지만, 에이전트가 없다. 사용자가 1300개 북마크를 직접 훑어야 한다. essence-sorter는 프로젝트 내부 에센스를 가이드 폴더에 분류하는 거지, "내 인생의 북마크"를 정리하는 게 아니다.

환원이 필요한 곳: 여기. 1300개 → "이 프로젝트에 관련된 게 뭔가?" 이 필터링은 현재 사람만 한다. 하지만 보일러플레이트가 정의할 수 있는 건 있다 — "프로젝트 아이디어가 있을 때 기존 자료에서 관련 맥락을 뽑는 패턴".

2단계: 아이디어 종합 → 프로젝트 결정

관련 메모 + 레퍼런스
        ↓
    기능, 기술스택, 인프라, 디자인 윤곽
현재 UX: 도구 없음. 사람이 머릿속에서 종합한다.

갭: 종합(synthesis) 자체는 사람의 일이 맞다. 하지만 종합 결과물의 포맷이 정의되어 있지 않다. "기능 목록, 기술 선택 근거, 디자인 레퍼런스"를 어떤 형식으로 정리해야 다음 단계(부트스트랩)에서 바로 쓸 수 있는지.

스코프가 필요한 곳: 여기. "이 프로젝트의 경계가 어디까지인가?"를 결정하는 게 scope-validator의 일인데, 현재 scope-validator는 레시피/가이드 스코프만 다룬다. 프로젝트 스코프를 잡는 도구가 없다.

3단계: 부트스트랩

project-scaffolder
    → CLAUDE.md (기술 스택 감지, {TODO} 플레이스홀더)
    → context/_template.md, 메모.md
    → .gitmessage.txt
    → 문서 체크리스트
현재 UX: 좋다. scaffolder가 기술 스택을 감지하고 초안을 만든다.

갭: scaffolder의 문서 체크리스트가 "어떤 에센스를 모아야 하는지" 힌트를 주지만, 2단계에서 이미 정리한 재료를 자동으로 연결하지 못한다. 사용자가 2단계 결과물을 수동으로 에센스 폴더에 옮겨야 한다.

4단계: 맥락 채우기

에센스 수집 → essence-sorter → guides/*/에센스/
                                    ↓
                              guide-filler → 프로젝트 문서
현재 UX: 이론상 좋다. 하지만 미테스트. guide-filler, essence-sorter 모두 실전 사용 경험이 없다.

환원이 필요한 곳: essence-sorter의 입력이 텍스트로 제한된다. 사용자가 "이 스크린샷이 디자인 에센스야", "이 URL이 기술 레퍼런스야"라고 할 때, 현재 에이전트는 URL을 읽거나 이미지를 분석할 수 없다. essence-sorter의 도구 목록에 WebFetch가 없다.

5단계: 기능 분해 + 병렬 프롬프트

feature-decomposer → work units
        ↓
prompt-builder → worktree 프롬프트 + 실행 명령어
현재 UX: 미테스트. 에이전트 정의는 있지만 한 번도 실행한 적 없다.

구조가 필요한 곳: prompt-builder가 프롬프트를 생성하지만, worktree를 누가 만드는가? git worktree add를 실행하고, 각 worktree에서 세션을 시작하는 과정이 수동이다. prompt-builder의 출력 형식을 보면 실행 명령어를 생성하긴 하지만, 사용자가 tmux 창을 열고 복사-붙여넣기 해야 한다.

6단계: 구현 루프

tdd-guide → code-reviewer → 커밋 → context-writer
     ↑                                    |
     └────── 다음 work unit ──────────────┘
현재 UX: 코드 루프는 좋다. agents.md의 MUST 규칙이 자동 호출을 유도한다.

갭: 사용자가 말한 "기능, 인프라, 디자인, 룰 등 작업 과정에서 필요한 모든 문서들을 업데이트하며" — 이건 현재 없다. context-writer는 세션 종료 시 context/MMDD.md만 만든다. CLAUDE.md 아키텍처 섹션 업데이트, 디자인 문서 갱신, feature-map 진행 표시 같은 건 전부 수동이다.

환원이 필요한 곳: 코드 변경에서 "어떤 문서가 영향받는가?"를 자동으로 감지하는 게 없다. 예를 들어 새 API 엔드포인트를 추가했으면 CLAUDE.md의 아키텍처 섹션이 갱신되어야 하는데, 이 연결을 사람이 기억하고 있어야 한다.

7단계: 맥락 자동 기록

코드 변경 → ??? → 문서 자동 업데이트
              ↑
          현재 이 부분이 없다
현재 UX: 포착.md가 비전을 정의한다 — Raw → Captured → Synthesized → Integrated. 하지만 구현은 Raw(자동, hooks)와 Synthesized(context-writer) 두 레이어만 작동한다. Captured → Integrated 자동화가 없다.

종합: 어디에 뭐가 더 필요한가

단계          환원    스코프   구조    현재 UX
─────────────────────────────────────────────
1. 수확        ●●●    ●●     ●       수동
2. 종합        ●●     ●●●    ●       수동
3. 부트스트랩   ●      ●      ●●      좋음
4. 맥락 채우기  ●●     ●      ●       미테스트
5. 분해+병렬   ●      ●●     ●●●     미테스트
6. 구현 루프    ●      ●      ●       좋음(코드), 나쁨(문서)
7. 자동 기록    ●●●    ●      ●●      비전만 있음
환원이 가장 부족한 곳: 1단계(수확)와 7단계(자동 기록). 대량의 비정형 입력에서 "뭐가 중요한가?"를 걸러내는 능력이 양 끝에서 부족하다. 시작할 때 1300개를 줄이는 것, 끝에서 코드 변경을 문서 업데이트로 변환하는 것.

스코프가 가장 부족한 곳: 2단계(종합). "이 프로젝트의 범위가 어디까지인가?"를 잡는 도구가 없다. scope-validator가 레시피/가이드 스코프만 다루고, 프로젝트 스코프를 안 다룬다.

구조가 가장 부족한 곳: 5단계(분해+병렬). worktree 생성, 세션 관리, 머지 순서가 자동화되지 않았다. prompt-builder가 프롬프트를 만들어도 실행은 사람이 한다.

가장 큰 UX 단절 3개
이 세 지점에서 사용자 흐름이 끊긴다:

1. 수확 → 부트스트랩 전환 (1→3단계)

"내가 가진 재료"에서 "프로젝트 시작"으로 넘어갈 때. 북마크, 파일, 메모가 흩어져 있는데, scaffolder는 빈 프로젝트에서 기술 스택을 감지하는 것부터 시작한다. 사용자의 기존 재료를 읽어서 초기 에센스로 변환하는 연결고리가 없다.

2. 에센스 입력의 형식 제한 (4단계)

essence-sorter가 텍스트만 받는다. 사용자가 말한 "이미지, 텍스트, 링크, 스크린샷, 클립보드"를 다 받으려면 essence-sorter에 WebFetch(URL), Read(이미지/파일) 도구가 추가되어야 한다. 그리고 각 형식을 에센스로 변환하는 정규화 규칙이 필요하다.

3. 구현 중 문서 자동 갱신 (6→7단계)

코드 → 문서 연결이 수동이다. "API 추가 → CLAUDE.md 업데이트", "디자인 변경 → 디자인 문서 업데이트"를 사람이 기억해야 한다. 이 연결을 맥락 라우팅이 해결할 수 있다 — 워크플로우 레시피에 추가한 그 흐름이 여기서 작동하면 된다.

이 분석을 context/0210.md에 기록하고 다음 단계를 정할까? 아니면 특정 갭부터 바로 해결할까?

---
1. 맥락이면 모두 수집할 수 있게 해야해.
대화 — 세션 중 AI에게 직접 전달
파일 시스템 — 폴더에 파일을 넣어둠 (북마크 내보내기, 스크린샷, 문서)
메모.md — 폰이나 메모장에서 한 줄씩 append
외부 — 브라우저, 노션, 슬랙 등 시스템 밖
---
다중 경로 — 대화, 파일 시스템, 메모.md, 외부 도구
비동기 시간 — 한 번에 몰아넣는 게 아니라 며칠에 걸쳐 쌓임
단일 라우팅 — 어떤 경로로 들어오든 같은 5기본연산을 탄다
---
2. 브레인스토밍하면서 아이디어 맥락 수집. 1번에서 재료를 수집했으면, 거기서 맥락을 뽑고 정리하고 하는 정밀한 과정이 필요하겠지. 사용자가 무엇을 하려는지.
3. 사용자의 맥락이 충분히 쌓였으면, 어떤 구조로 작성하려는지, 이름은 뭐로 하려는지, 뭐가 필요한지 등.
구조도 생성하고, 미리 만들어둔 가이드에 따라 docs/에서 폴더도 만들고, 필요한 것만 추려서(디자인, 깃컨벤션, 인프라(얘도 만들어야겠네) 같은거) 가이드에 템플릿대로 문서도 만들고, 복사도 해오고 해야겠지. 정리한 에센스를 자동으로 연결해줘야겠지.
---
4. 이거 여기있는게 맞나? 맥락 채우는건 프로젝트를 하면서 언제든 문서에 채워넣고, 코드작업을 하고, 코드 작업한걸 문서에 다시 업데이트하고, 대화하면서 문서에 맥락을 추가하고, 다시 코드작업하고.. 이런 루프를 돌겠지.
---
5. 맥락이 쌓이고 요구사항이 충분해지고 기능이 되었으면 기능을 최대한 잘게 쪼개는 작업을 해야겠지. '환원'이란 개념이 여기서도 활용 될 필요가 있을지 궁금하네.
---
6. 이제 단일/병렬 작업을 phase 로 나누면서 작업을 하겠지. 만약 1단일 2병렬 3단일 이렇게 마무리한다면, 2번에서 tmux로 여러개의 터미널 세션을 띄우고 worktree를 만들고 잘게 쪼갠 기능 하나마다 프롬프트를 만들어서, 그 터미널에 넣어줘야겠지.
그리고 화면을 계속 보면서 총작업을 할 거야.
