# 워크플로우

## 프로젝트 설정

```bash
# 클론 및 설치
git clone [repo-url]
cd electron-boilerplate
npm install

# 환경 변수 설정
cp .env.example .env
# .env에 Supabase 자격 증명 추가 (DATABASE_URL, VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)

# DB 초기화 및 실행
npx drizzle-kit push
npm start
```

환경 요구사항: Node.js 18+(권장 20 LTS), npm 9+, Git.

권장 VS Code 확장: ESLint, Prettier, TypeScript, Tailwind CSS IntelliSense, Vitest Runner.


## Demo-First 개발

모든 기능은 데모에서 시작한다. demos/에서 프로토타입을 만들고, 검증이 끝나면 features/로 이동한다.

### 10단계 워크플로우

```
Step 1: Worktree 생성          git worktree add {dir} -b demo/{feature}
Step 2: Demo 폴더 생성         mkdir -p src/demos/{feature}, DemoIndex 등록
Step 3: Cursor 창 열기         cursor {dir}
Step 4: 코드 분석              기존 패턴 재사용 확인
Step 5: UI 설계                레이아웃, 그리드, breakpoint 정의
Step 6: 구현
  ├─ 6-1: 컴포넌트 구현        각 컴포넌트 독립적으로 구현
  └─ 6-2: 통합                 상태 관리(Zustand), UI 연결
Step 7: 사용자 검증            npm start → http://localhost:3000/demos
Step 8: 보안 검증              IPC, XSS, CSP, 파일 시스템 접근 체크
Step 9: 코드 리뷰              아키텍처/성능/보안/품질 분석
Step 10: 병합 및 정리          git mv demos → features, 커밋, 병합, worktree 제거
```

### 데모 UI 원칙

"달랑 원칙"을 따른다. 핵심만 담고 군더더기를 없앤다. 기능을 직접 테스트할 수 있는 버튼, 현재 상태를 보여주는 시각적 요소, 필수적인 한 줄 설명만 넣는다.

모든 데모 페이지는 SimpleTitlebar로 시작한다. 기능이 먼저(상단), 테스트 버튼이 다음(중단), 기술 정보는 필요시에만(하단) 배치한다.

장황한 설명, 불필요한 애니메이션/장식, 사용하지 않을 옵션, 과도한 박스/구분선은 제거한다.


## 컨텍스트 최소화 전략

"최소 컨텍스트로 최대 바이브 코딩"이 핵심이다. 125K 코드베이스를 20K 베이스라인으로 줄인다. 84% 감소.

컨텍스트가 길어질수록 AI는 관련 없는 정보에 산만해진다. "Lost in the Middle" 연구에서 긴 컨텍스트의 중간 부분이 30-40% 덜 활용된다는 걸 보여준다. 필요한 것만 로드하면 AI가 중요한 정보에 집중할 수 있다.

### .gitignore 전략

컨텍스트 관리의 첫 번째 방어선이다. node_modules(의존성), dist/out/.vite(빌드 아티팩트), .cache/*.log(임시), .env(보안)을 제외한다. 완료된 작업(PHASE3-*.md, demos/archived/)도 선택적으로 제외한다.

### Docs 구조화

문서를 4단계로 계층화해서 필요할 때만 로드한다.

```
docs/
├── 00-시작/          (4개, 5K)   항상 로드
├── 01-워크플로우/     (5개, 10K)  Demo 단계
├── 02-아키텍처/       (11개, 15K) 통합 단계
└── 03-참고자료/       (26개, 30K+) 검색 전용
```

### Git Worktree 전략

Worktree로 디렉토리를 물리적으로 분리해서 컨텍스트를 격리한다.

```bash
git worktree add {workspace-dir}/inbox -b demo/inbox
cursor {workspace-dir}/inbox
```

각 Cursor 창의 Claude Code가 독립된 코드베이스 컨텍스트를 로드한다. inbox 데모를 작업하는 Claude는 inbox 코드만 본다. 컨텍스트 오염이 없다.

단일 세션에서 3개 데모를 순차 개발하면 컨텍스트가 누적(45K)되지만, Worktree로 분리하면 각 창이 독립적으로 15K만 쓴다. 3.6배 효율이다.

### 병렬 개발

2-3개 기능을 동시에 개발할 때는 worktree를 여러 개 만든다.

```bash
git worktree add {dir}/feature-a -b demo/feature-a
git worktree add {dir}/feature-b -b demo/feature-b
git worktree add {dir}/feature-c -b demo/feature-c
# 각각 Cursor 창 열기
```


## 품질 검증

### Codex-Claude Loop

Claude가 계획하고 구현하면 Codex가 검증해서 피드백하는 품질 검증 루프다. 6단계로 진행된다.

1. Claude가 계획 수립
2. Codex가 로직 오류, 엣지 케이스, 보안 문제 검토
3. 문제 있으면 Claude 수정 → 재검증 (반복)
4. 계획 통과 후 Claude가 구현
5. Codex가 코드 리뷰 (버그, 성능)
6. 문제 있으면 수정 → 재검증 (반복)

AI가 코드 복잡도를 보고 자동으로 판단한다. 인증(OAuth, JWT), 결제, 보안 로직처럼 품질이 중요한 기능에서 실행된다.

### Poetiq-TDD 전략

테스트 기반 자동화 개발 루프다. Poetiq ARC-AGI 논문에서 영감을 받았다. 테스트 결과가 피드백이 되어 AI가 스스로 개선한다.

```
테스트 케이스 선택 (배치 5-10개) → AI 구현 → Vitest 실행
→ 실패 시: 에러 메시지를 피드백으로 재구현 (최대 5회)
→ 통과 시: 다음 배치로
```

Codex-Claude와의 차이: Codex-Claude는 Codex가 코드를 리뷰해서 피드백한다. Poetiq-TDD는 테스트 실행 결과가 피드백이다. 둘 다 쓸 수 있다. 복잡한 기능은 Codex-Claude로 설계하고, 구현은 Poetiq-TDD로 검증한다.


## 코딩 컨벤션

### 네이밍

```
파일: PascalCase.tsx (컴포넌트), camelCase.ts (훅/유틸), UPPER_SNAKE_CASE.ts (상수)
변수: camelCase (일반), UPPER_SNAKE_CASE (상수), is/has/should (Boolean)
함수: 동사+명사 (readFile), is/has (Boolean 반환), handle+이벤트 (핸들러)
컴포넌트: PascalCase, Props 타입은 컴포넌트명+Props
```

### Feature 폴더 구조

```
src/features/{feature}/
├── components/    # UI 컴포넌트
├── hooks/         # 커스텀 훅
├── store/         # Zustand 스토어
├── types/         # 타입 정의
├── utils/         # 유틸리티
└── index.ts       # Public API
```

### Import 순서

1. React 관련
2. 외부 라이브러리 (zod, clsx)
3. 내부 절대 경로 (@/shared, @/features)
4. 내부 상대 경로
5. 타입 import (type)
6. 스타일

### TypeScript

- interface: 확장 가능한 객체에 사용
- type: Union, Utility 타입에 사용
- 매개변수와 반환 타입 명시
- 간단한 경우 타입 추론 활용

### 에러 처리

```typescript
try {
  const content = await readFile(path);
  return { success: true, data: content };
} catch (error) {
  if (error instanceof ValidationError) {
    return { success: false, error: error.message };
  }
  throw error;  // 예상치 못한 에러는 상위로
}
```

### 코드 포맷팅

ESLint + Prettier. 줄 길이 80자 권장, 최대 100자.

### BDD 패턴

Given-When-Then 패턴을 사용한다.

```typescript
describe('Feature: 파일 탐색기', () => {
  it('Given 파일 탐색기가 열려있고, When 폴더를 클릭하면, Then 하위 파일 목록이 표시된다', async () => {
    // Given
    const { getByText } = render(<FileExplorer />);
    // When
    await userEvent.click(getByText('src'));
    // Then
    expect(getByText('components')).toBeInTheDocument();
  });
});
```

### 보안 테스트 (182개)

6개 카테고리로 182개 테스트를 실행한다. 모두 100% 통과 필수다.

- CSP 우회 시도 (23개): inline script, eval(), 외부 CDN
- XSS 공격 패턴 (31개): `<script>` 삽입, `<img onerror>`, HTML 속성 주입
- Path Traversal (42개): `../../etc/passwd`, URL 인코딩 우회
- SQL Injection (18개): `' OR '1'='1`, Union-based
- Rate Limit 초과 (28개): 100ms 반복, 동시 다발, DoS
- 입력 검증 우회 (40개): 타입 혼동, 길이 초과, 정규식 우회

### Mock 전략

테스트 환경에서 IPC, FileSystem, Supabase를 Mock으로 대체한다.

```typescript
// IPC Mock
global.window.electron = {
  readFile: vi.fn((path) => Promise.resolve('mock content')),
  writeFile: vi.fn(() => Promise.resolve()),
  listDirectory: vi.fn(() => Promise.resolve(['file1.txt', 'file2.txt']))
};

// FileSystem Mock
vi.mock('fs/promises', () => ({
  readFile: vi.fn(), writeFile: vi.fn(), readdir: vi.fn()
}));

// Supabase Mock
vi.mock('@/backend/infrastructure/db/client', () => ({
  db: { select: vi.fn().mockReturnThis(), from: vi.fn().mockReturnThis(), where: vi.fn().mockResolvedValue([]) }
}));
```
