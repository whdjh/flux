### 클라우드가 생성한 클라우드플레어의 커밋을 모두 읽어보았다
~2025-06-06

며칠 전, 우리 CTO인 Chris가 클라우드플레어(Cloudflare)의 오픈소스 OAuth 2.1 라이브러리를 공유해줬어. 거의 전체를 클로드(Claude)가 작성한 코드였지.

내 시선을 끈 건 기술적 성취뿐만이 아니었어. 그들은 창작 과정 전체를 기록으로 남겨두었더군. 모든 프롬프트, 모든 수정 과정, 모든 인간의 개입 순간이 git 커밋 메시지에 보존되어 있었지. 마치 인간과 AI 협업의 고고학적 기록처럼 느껴졌어. 개발 히스토리를 읽는 것은 인간의 직관과 인공지능 사이의 실시간 대화(그리고 때로는 고군분투)를 지켜보는 것 같았지.

프로젝트를 이끈 엔지니어 @kentonv는 원래 AI 회의론자였대. "회의론이 맞다는 걸 증명하려 했는데, 결국 내가 틀렸다는 걸 증명하고 말았다."라고 하더군. 두 달 후, 클로드는 운영 환경에 바로 사용 가능한 수준의 인증 라이브러리 코드를 거의 다 만들어냈어.

#### 프롬프트와 코드를 함께 커밋하기
Kenton은 코드를 생성하는 데 사용한 프롬프트를 모든 커밋에 포함시켰고, 덕분에 이런 탐구가 가능했지. 개발 과정에서 AI 도구에 더 많이 의존하게 될수록, 이런 습관은 점점 더 중요해질 거야. 때로는 엔지니어가 잘못된 가정을 선언하고 모델이 그걸 맹목적으로 따를 때, 결과물인 코드보다 원본 프롬프트를 리뷰하는 게 더 가치 있고 (그리고 더 쉽지).

이런 투명성은 git 히스토리를 단순한 변경 기록에서 '의도의 기록'으로 바꾸고, 인간의 추론과 기계의 구현을 잇는 새로운 형태의 문서화를 만들어내.

#### 인간-AI 협업의 패턴들
50개 정도의 커밋을 읽어보니, 이 협업이 실제로 어떻게 전개되었는지에 대한 몇 가지 흥미로운 패턴이 보였어.

*   **예제로 프롬프트하기.** 초기 프롬프트는 라이브러리를 구현하는 워커(worker)가 이 라이브러리를 어떻게 사용할지 정확하게 보여주는 상당한 양의 코드 블록이었어. 이 접근 방식은 메서드 시그니처에 대한 모호함을 없애는 동시에, 추상적인 명세서에서는 놓치기 쉬운 실용적인 고려사항들을 드러내 줬지. 이건 춤을 설명하는 것과 직접 춤 동작을 보여주는 것의 차이와 같아.

*   **"X라고 했는데, Y로 해야 해. 수정해줘."** 가장 효과적인 프롬프트는 일관된 패턴을 따랐어. 현재 상태에 대한 명확한 맥락, 변경이 필요한 이유에 대한 설명, 그리고 앞으로 나아갈 구체적인 방향 제시. 정교한 지시 없이도, 마치 동료의 실수를 바로잡는 듯한 맥락에 맞는 피드백이었지.

*   **개인적인 생각:** 나도 Cursor를 쓰면서 문서 링크를 직접 포함시키는 게 도움이 된다는 걸 알게 됐어. 프롬프트에 `@<붙여넣은_문서_링크>`를 쉽게 참조할 수 있는데, 클로드 코드는 아직 그 정도까진 사용해보지 않아서 비슷한 워크플로우가 있는지는 모르겠네.

*   **문서화는 식은 죽 먹기.** 단 한 문장의 프롬프트로 포괄적인 스키마 문서가 생성됐어. 모델들이 이런 문서 생성 작업에 뛰어나다는 걸 느꼈지. 과거에는 지루한 잡무였던 일이 개발의 자연스러운 부산물로 바뀌었어.

#### AI가 고전한 부분
커밋 20개쯤 읽었을 때, Kenton이 직접 개입해야 하는 부분을 발견했어. 클로드는 클래스 선언을 제대로 옮기지 못해서, 위치를 바로잡기 위한 후속 커밋이 필요했지. 나중에는 검색 및 바꾸기 기능이 중복 코드 블록을 처리하지 못해서 `grep`과 `sed` 같은 bash 명령어를 사용하는 데 의존하기도 했어.

"아, 이건 그냥 내가 손으로 하는 게 더 빨랐겠다. 뭐, 어쩔 수 없지." 라는 코멘트가 특히 공감됐어.

커밋 40개 지점부터는 수동 커밋이 잦아졌어. 스타일링, 미사용 메서드 제거 등 코딩 모델이 여전히 힘들어하는 종류의 정리 작업들이었지. AI가 코드의 95% 이상을 생성한 건 분명하지만, 인간의 감독은 과정 내내 필수적이었어.

#### 실용적인 교훈
만약 AI 코딩 도구를 사용하고 있다면, 그들의 접근 방식에서 몇 가지 교훈을 얻을 수 있어.

*   **결과물에 집중하라.** 백엔드 서비스라면 공개 엔드포인트와 예상 동작을 정의하고, CLI 도구라면 사용 예시를 보여주고, 라이브러리라면 통합 방법을 시연해라.
*   **프롬프트를 버전 관리 자산으로 취급하라.** 프롬프트를 커밋 메시지에 포함하면 미래의 유지보수와 디버깅에 유용한 맥락이 만들어진다.
*   **여러 번의 프롬프트는 기본이라고 생각하라.** 거의 모든 기능은 여러 번의 반복과 개선을 필요로 했다. 이건 한계가 아니라, 협업이 작동하는 방식이다.
*   **직접 손대는 것을 두려워하지 마라.** 어떤 버그나 스타일링 문제는 프롬프트를 통해 해결하는 것보다 수동으로 수정하는 것이 더 빠르다. 언제 개입해야 할지 아는 것도 기술의 일부다.

#### 소스 코드로서의 프롬프트
이 커밋들을 읽다가 이런 아이디어가 떠올랐어. 만약 우리가 프롬프트를 실제 소스 코드로 취급한다면 어떨까? 결과물인 구현체 대신, 기능을 생성하는 데 사용된 프롬프트를 커밋하는 버전 관리 시스템을 상상해봐. 모델이 필연적으로 개선되면, 최신 버전을 연결해서 향상된 기능으로 전체 코드베이스를 다시 생성할 수도 있겠지.

이 접근법은 비즈니스 로직을 본질적으로 자가-문서화(self-documenting)하게 만들 거야. 영어를 읽을 수 있는 사람이라면 누구나 언제, 왜 기능이 추가되었는지 이해할 수 있게 되겠지. 프롬프트는 애플리케이션을 성장시키는 데 필요한 필수 정보를 담은 유전적 지침처럼 될 거야.

물론, 이건 모델이 엄격하게 프롬프트를 따른다는 가정 하에 가능하고, 모델에 대한 매우 높은 수준의 신뢰를 필요로 해. 현실에서는 생성된 코드도 배포, 테스트, 유지보수가 필요하지. 하지만 흥미로운 질문을 던져줘. 만약 모든 비즈니스 로직이 자가-문서화되는 프롬프트 안에 담길 수 있다면, 언젠가 이 프롬프트 커밋 히스토리 자체가 모델에서 직접 실행되는 "애플리케이션"이 되는 지점에 도달할 수 있지 않을까? 중간의 코드 생성 단계를 완전히 제거할 수도 있지 않을까?

뭐, 어쨌든 다시 현실로 돌아와서.

#### 개인적인 회고
이 OAuth 라이브러리는 기술적인 이정표 이상의 것을 상징해. 바로 새롭게 부상하는 창의적인 역학 관계의 증거지. 인공지능이 기계적인 구현을 처리하는 동안, 인간은 방향, 맥락, 그리고 판단을 제공하는 관계 말이야.

이 과정 내내 상당한 인간의 개입이 있었다는 건 명백해. AI가 독립적으로 이 정도 범위의 라이브러리를 구현하기까지는 아직 갈 길이 멀어. 거의 모든 기능은 여러 번의 프롬프트가 필요했고, 어떤 버그들은 자동화된 수정 시도에 모두 저항했고, 특정 기능들은 수동으로 하는 게 더 빨랐을 것이고, 모든 프롬프트를 만들고 전략적인 방향을 제시한 것은 인간이었지.

이런 한계에도 불구하고, AI는 이 라이브러리의 기능적인 코드 대부분을 생성해냈어. 클로드 코드는 공개된 지 불과 2주밖에 안 됐는데, 이미 이 정도 수준의 협업을 가능하게 하고 있어.

지금으로서는, 그저 또 다른 도구일 뿐이야. 하지만 망치와는 달리, 이 도구는 스스로를 개선하고, 모든 상호작용에서 배우며, 반복할 때마다 더욱 유능해지고 있어.
