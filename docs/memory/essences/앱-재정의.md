# Flux 앱 재정의

가치와 비전은 유지하면서, 머릿속에 넣을 수 있도록 하나하나 정의한다.

제품 정의에도 집중한다.

Flux는 AI 기반 세컨드 브레인이다.

리서치 중 발견한 링크, 이미지, 스크린샷을 북마크하고 레퍼런스로 기록한다. 거기에 메모와 노트를 붙이면 단순한 클리핑이 나만의 지식 아카이브로 바뀐다.

AI가 수집한 자료를 자동으로 정리하고, 필요할 때 검색과 요약까지 해준다. 그래서 쌓아둔 자료가 묻히지 않는다.

기존 도구들은 한쪽만 강하다. 북마크 앱은 메모가 안 되고, 메모 앱은 수집이 안 되고, PKM 도구는 정리에 시간이 너무 든다. Flux는 수집부터 기록, 큐레이션까지 한 앱에서 해결한다. 팀과 함께 쓸 수 있는 생산성 도구다.

## 0. 비전

초기 메모에서 발췌:

> 사람 하나의 생산성을 25% 높이면. 만약 여러명이면, 그리고 높인 사람 중에 중요한 의사 결정자가 있으면.
>
> 인지 전환 비용을 줄여서 세상을 더 나은 세상으로 만드는 것, 현재 AI 발전에 가속을 더해주는 것.
>
> 생각과 기억과 기록에 소프트웨어라는 병목을 줄여주는 것.

인지 전환 비용을 줄이면 두 방향으로 이어진다. 세상이 나아지고, AI 발전이 빨라진다.

생각과 기억과 기록 — 전환이 아니라 각 행위 자체에서 소프트웨어가 병목이다.

비전은 앱보다 크다. 이 문서는 비전의 구현체인 Flux의 제품 정의에 집중한다.


## 1. 한 줄 정의

수집부터 기록, 큐레이션까지 한 앱에서 팀과 함께 — AI 기반 세컨드 브레인


### 정의까지의 과정

에센스(이 문서를 쓰기 전에 모은 원재료 — 텍스트, 이미지, 링크, 메모 등 형태 무관)에서 이 앱을 부르는 방식이 여러 개 있었다. "영감 수집 생산성 도구", "리서치 통합 도구", "인지 보호막(Cognitive Shield)", "키고 적으면 알아서 정리되는 메모장", "정리는 프로그램이, 활용은 사용자가". 각각 다른 면을 강조해서 하나로 수렴되지 않았다.

세 가지 프레임이 가능했다.

수집 도구로 보면 흩어진 정보를 한 곳에 모으는 게 핵심이다. mymind, Eagle, Raindrop 같은 북마크/클리퍼 쪽에 가깝다.

메모 도구로 보면 생각을 기록하고 정리하는 게 핵심이다. Notion, Obsidian 쪽에 가깝다. 수집은 입력 수단일 뿐이다.

리서치 도구로 보면 수집부터 발상까지 전체 흐름을 지원하는 게 핵심이다. 개별 기능보다 흐름의 연결이 가치다.

에센스에서 반복되는 말이 "생각의 흐름이 끊어진다"였다. 수집 자체가 목적이 아니라, 수집할 때도 흐름이 안 끊기고 나중에 쓸 때도 흐름이 안 끊기는 게 진짜 풀려는 문제다. 리서치 도구 프레임이 기능은 가장 잘 설명하지만, "리서치 도구"라는 이름만으로는 왜 필요한지가 안 드러난다. 2장에서 파고 보니 핵심은 "몰입"이었다. 글을 쓰다가 자료를 찾으러 브라우저로 넘어가고, 찾은 걸 메모 앱에 옮기고, 다시 돌아오는 — 이 전환 때문에 생각이 끊긴다. 저장·정리·메모·검색을 한 도구에 두면 전환이 사라지고, 생각이 이어진다.


### 어떤 가치를 강조하는가

- 속도 — 즉시 캡처, 흐름 끊김 없음
- 자동 정리 — 사용자는 수집만, 정리는 프로그램이
- 통합 — 여러 소스, 여러 기기, 한 곳에서


### 기능 전체 목록

처음에 11개를 나열했다. 이 중 보존(원본 유지, 비파괴 편집)은 기능이 아니라 원칙이고, 큐레이션은 수집+정리+AI의 조합이다. 9개가 남았다 — 수집, 정리, 메모, 검색, AI, 협업, 동기화, 공유, 창 관리.

사용자 경험 순위: 1순위 메모, 정리, AI / 2순위 수집, 검색, 협업 / 3순위 창 관리, 동기화, 공유. 구현 순서(8장)와는 다른 축이다.


### 기능의 관계

처음에는 4개(수집, 정리, 메모, 검색)만 핵심 기능이고 나머지는 수단/인프라/UI라고 분류했다. 하지만 그건 개발자 관점이다. 사용자에게 "이 앱 뭐 해?"라고 물으면 "AI가 알아서 정리해줘", "폰에서 찍은 거 노트북에서 바로 써"도 답이 된다. 9개 전부 사용자가 경험하는 기능이다.

빼지 않되, 관계를 잡아야 한다. 9개 기능이 전부 등장하는 시나리오로 확인한다.

> 앱 온보딩 화면을 개선하려고 레퍼런스를 모으고 있다. 브라우저 옆에 Flux를 포스트잇 모드로 띄워둔다 [창 관리].
>
> UX 아티클에서 중요한 문장을 드래그해서 수집한다. 다른 앱의 온보딩 화면을 스크린샷 찍는다. 핀터레스트에서 본 레퍼런스 이미지를 저장한다 [수집]. 수집하는 순간 AI가 각 항목에 요약, 키워드 3개, 출처를 붙인다 [AI → 정리]. 10개쯤 쌓인다.
>
> 퇴근길 지하철에서 폰을 열면 아까 노트북에서 수집한 것들이 그대로 있다 [동기화]. 훑어보면서 별 표시로 중요한 것 3개를 골라둔다 [정리].
>
> 다음 날 노트북에서 메모를 연다. 별 표시한 3개를 메모로 드래그하면 수집한 게 메모 안에 들어간다. 자기 생각을 덧붙인다 [메모]. 지난주에 수집한 관련 자료가 생각나서 검색하면 AI가 의미까지 고려해서 관련 항목을 찾아준다 [검색 + AI].
>
> 동료에게 메모 링크를 보낸다 [공유]. 동료가 열어서 코멘트를 달고, 자기가 찾은 자료를 추가한다. 둘이 동시에 같은 메모를 편집한다 [협업].

두 번째 시나리오는 폰에서 시작해서 웹으로 이어지는 흐름이다.

> 카페에서 읽던 책에 좋은 문장이 있다. 폰으로 사진 찍고 Flux에 저장한다 [수집]. 걸어가다가 떠오른 생각을 음성 메모로 남긴다 [수집]. 인스타에서 본 인테리어 사진도 공유 버튼으로 Flux에 보낸다 [수집]. AI가 각각 요약과 키워드를 붙인다 [AI → 정리].
>
> 집에 와서 노트북을 연다. 브라우저에서 Flux 웹을 열면 폰에서 모은 것들이 다 있다 [동기화]. 넓은 화면에서 폴더별로 정리하고 [정리], 메모를 열어서 오늘 모은 것들을 엮으며 생각을 정리한다 [메모]. 예전에 비슷한 주제로 모았던 자료를 검색해서 함께 본다 [검색 + AI].

첫 번째 시나리오는 데스크톱 중심(브라우저 → 앱 → 폰 → 앱), 두 번째는 모바일 중심(폰 → 웹)이다. 같은 기능이 다른 맥락에서 작동한다.

중심에 루프가 있고, 나머지가 각 단계를 강화하는 구조다:

```
중심 루프:
  수집 → 정리 → 메모 → 검색 (다시 수집으로)

강화:
  수집 ← 창 관리 (포스트잇, 항상 위)
  정리 ← AI (자동 태깅, 요약)
  메모 ← 협업 (공동 편집)
  검색 ← AI (의미 검색)
  전체 ← 동기화 (멀티 디바이스)
  전체 ← 공유 (결과물 전달)
```


## 2. 문제


### 수집한 에센스

문제 정의의 근거를 소스별로 모았다.

#### 학술 연구

Gloria Mark (2008, CHI): 작업 전환 후 원래 작업으로 복귀하는 데 평균 23분 15초가 걸린다. 사무직 근로자는 평균 3분마다 작업이 중단된다. 중단된 작업의 18%는 당일 내에 재개되지 않는다. 작업 속도를 높여 보상하려 하지만 더 높은 스트레스를 동반한다.

Information Overload (2024, ScienceDirect): 정보 과부하의 원인 세 가지. 정보 절대량의 기하급수적 증가, 정보의 분산, 검색/정리 도구의 부족.

Multitasking (2024, Current Psychology): 작업 전환으로 인지 능력 20% 감소. 하루 평균 300회 이상 작업 전환, 31.6회 중단. 연간 4,500억 달러의 글로벌 생산성 손실 추산.

Task Switching (2025, Cognitive Research): 작업 전환 효과는 즉각적이지 않고 11.5초간 지속된다. 하루 300회 전환하면 57.5분을 인지 저하 상태로 보내는 셈이다. 기능 추가가 아니라 전환 자체를 줄이는 통합 설계가 핵심이다.

#### 경쟁 환경

직접 경쟁:

- Notion — 올인원, 협업. 느린 속도, 복잡성.
- Obsidian — 연결 중심, 로컬 우선. 높은 학습 곡선, 협업 없음.
- Evernote — 단순함, 안정성. 혁신 부족.
- Readwise — 수집 특화 (하이라이트, 기사). 아이디어 발상 기능 없음.
- Eagle (eagle.cool) — 디자인 에셋 수집/정리 특화. 브라우저 확장 원클릭 저장, 90+ 파일 형식, 태그/폴더/색상 정리, 빠른 미리보기. 일회성 구매($29.95). 약점: 데스크톱 전용(모바일 없음), 네이티브 동기화 없음, 협업 없음, AI 없음, 텍스트/메모 작성 불가(시각 에셋 전용). Flux와의 차이: Eagle은 "이미지를 잘 정리하는 도구", Flux는 "모든 종류의 정보를 모아서 생각으로 연결하는 도구".

Gemini 3/GPT-5.1 지원. 2025.12 Explore 모드 추가(콘텐츠 사이 관계 탐색, 우연한 재발견). 초기 피드백의 영의님이 "fabric으로 정착했음"이라고 한 앱. Flux와의 차이: Fabric은 클라우드 기반, Flux는 로컬 우선. #### 핵심 수치

- 23분 15초 — 한 번 끊기면 돌아오는 데 걸리는 시간 (Gloria Mark, 2008)
- 11.5초 — 전환 후 인지 저하 지속 시간 (Task Switching, 2025)
- 300회 — 하루 평균 작업 전환 횟수 (Multitasking, 2024)
- 57.5분 — 하루 중 인지 저하 상태로 보내는 시간 (Task Switching, 2025)
- 18% — 중단 후 당일 재개 안 되는 작업 비율 (Gloria Mark, 2008)
- 20% — 작업 전환으로 인한 인지 능력 감소 (Multitasking, 2024)


### 문제 분석

1장에서 "수집부터 기록, 큐레이션까지 한 앱에서"를 핵심으로 정의했다. 왜 한 앱이어야 하는지, 문제를 분석하면 답이 나온다.

에센스에서 반복되는 말이 있다. "생각의 흐름이 계속 끊어진다"(개인 동기), "그때그때 편하게 남기는 게 되게 중요해요"(정규영 CD), "사람은 앞에 있는거 쓴다"(초기 피드백), "키고 적으면 알아서 정리되는 메모장"(개인 동기).

학술 연구도 같은 방향이다. 글을 쓰다가 자료를 찾으러 브라우저로 넘어가고, 찾은 걸 메모 앱에 옮기고, 다시 글로 돌아오는 — 이런 앱 간 전환이 하루 평균 300번 일어난다(Multitasking, 2024). 한 번 전환할 때마다 몰입을 되찾는 데 최대 23분이 걸린다(Gloria Mark, 2008). 핵심 수치는 위에 정리했다.

그래서 앱 전환 횟수 자체를 줄여야 한다. 자료 저장(수집), 태그·폴더 분류(정리), 생각 기록(메모), 다시 꺼내기(검색)를 한 도구 안에서 할 수 있으면 전환이 사라진다. 하지만 기존 도구들은 이 중 하나만 푼다 — Pocket은 저장만, Notion은 정리만, Apple 메모는 기록만.

6층으로 나눠서 본다.

#### 1층: 증상 — 저장한 것들이 여기저기 흩어져 있다

링크는 카톡에, 스크린샷은 갤러리에, 메모는 메모장에. "어디 저장했지?" 찾을 때마다 여러 앱을 뒤진다.

#### 2층: 행동 — 가장 쉬운 곳에 던진다

카톡 나에게 보내기, 바탕화면 txt, 머릿속. 마찰이 제로인 곳에 던진다. 게으른 게 아니라 합리적 선택이다. 수집 순간에는 의미 판단("이게 왜 중요하지?")이 일어나는데, 분류 판단("이걸 어디에 넣지?")까지 동시에 할 수 없다. 분류를 포기하는 게 인지적으로 맞다.

#### 3층: 구조 — 도구의 한계

세 가지 문제가 있다.

링크를 저장하는 건 10초면 된다. 하지만 나중에 그걸 폴더로 나누려면 10분이 걸린다. 저장하는 순간에는 정리할 여유가 없고, 정리하려고 앉으면 뭘 왜 모았는지 잊는다.

링크, 스크린샷, 메모가 200개 넘으면 폴더로 나누는 게 저장하는 것보다 힘들다. 정규영 CD가 말한 "200~300개 모이면 처음에 못 느꼈던 게 보인다"의 전제는 그걸 다시 볼 수 있어야 한다는 것이다.

Pocket에 저장하고, Notion에 정리하고, 메모장에 적으면 해결될 것 같다. 하지만 도구를 바꿀 때마다 어디까지 했는지 다시 파악해야 한다.

이 세 가지가 만드는 총 비용이 학술 연구에 나타난다. 하루 평균 300회 작업 전환(도구 전환 포함), 전환마다 11.5초 인지 저하가 지속되어 하루 57.5분을 저하 상태로 보낸다.

#### 4층: 본질 — 앱을 바꾸면 어디까지 했는지 잊는다

세 문제가 합쳐지면, 글을 쓰다가 자료를 찾으러 브라우저를 열고, 찾은 걸 메모 앱에 옮기고, 다시 돌아왔을 때 어디까지 썼는지 잊는다. 에센스에서 "흐름이 끊긴다"는 말이 반복되는 이유다.

23분이라는 숫자가 뜻하는 건 시간 낭비가 아니다. 돌아와서 위부터 다시 읽고, 어디까지 했는지 파악하고, 아까 떠올랐던 아이디어가 뭐였는지 되짚어야 한다.

#### 5층: 대가 — 그래서 뭘 잃는가

"이 글이랑 아까 본 그 사진이랑 합치면..." 하던 생각이 앱을 바꾸는 사이에 날아간다. 정보는 다시 찾을 수 있다. 근데 그 순간 머릿속에서 이어붙이고 있던 조각은 다시 못 맞춘다. 정규영 CD가 말한 "여러 레퍼런스들이 함수처럼 연결돼서 새로운 아이디어로 디벨롭된다"는 게 이것이다. 그 연결은 몰입 상태에서만 일어난다.

3주 뒤에 북마크를 열면 "이걸 왜 저장했지?"가 된다. 저장할 때는 "이 색감 조합 나중에 써야지", "이 논문 결론 부분 기획서에 넣어야지" 같은 이유가 있었다. 하지만 저장하고 쓰는 사이에 시간이 지나면 그 이유가 사라진다. 링크는 남아 있는데 왜 저장했는지는 사라진 것이다. 정규영 CD가 "파이트 클럽을 보고 적어놨던 메모"에서 아이디어가 나온 건, 메모에 의도가 녹아 있었기 때문이다. URL만 저장하는 도구는 의도를 저장하지 않는다.

하루에 300번 앱을 전환한다. 전환할 때마다 11.5초가 들어서, 하루 57.5분을 잃는다. 1년이면 약 350시간이다. 근데 진짜 문제는 시간이 아니다. 350시간 동안 만들어졌을 수 있는 연결, 떠올랐을 수 있는 아이디어가 사라진다. 측정이 안 되니까 아무도 심각하게 안 느낀다. 대부분의 사람은 축적의 임계점(200~300개)에 도달하기 전에 도구를 바꾸거나, 정리를 포기하거나, "그냥 기억하지 뭐"로 돌아간다.

#### 6층: 근본 — 깊은 작업일수록 자료가 더 필요하고 앱을 더 자주 바꾼다

깊이 생각하려면 자료가 필요하다. 자료를 가져오려면 앱을 바꿔야 한다. 앱을 바꾸면 어디까지 했는지 잊는다. 깊은 작업일수록 자료가 더 필요하니까 앱을 더 자주 바꾸고, 더 자주 잊는다.

얕은 작업(이메일, 메시지)은 전환해도 별 타격이 없다. 리서치, 글쓰기, 기획 같은 깊은 작업일수록 전환 비용이 기하급수적으로 커진다. 가장 중요한 작업이 가장 많이 피해를 받는다.

"AI가 정리해줄게요"도 이 역설에서 자유롭지 않다. Fabric이 정확히 이 접근이다. AI가 수집과 정리를 자동화해서 정리 비용은 줄었다. Fabric은 여기서 한 발 더 나가서 Explore 모드(2025.12)로 콘텐츠 사이 관계를 탐색하고 우연한 재발견을 돕는다. 활용 순간의 마찰을 풀려는 시도다.

근데 Explore는 "이미 저장된 것들 사이에서 관계를 보여주는" 수동적 발견이다. 사용자가 능동적으로 생각을 만들고 있는 순간 — 메모를 쓰면서 자료를 끌어오고, 연결하고, 자기 말로 바꾸는 그 과정의 몰입은 별개 문제다. Flux가 수집→정리→메모→검색을 한 도구 안에 두려는 이유가 여기 있다. 연결을 보여주는 게 아니라, 연결을 만드는 순간에 흐름이 안 끊기게 하는 것이다.

### 보편적 수집 흐름

6층 분석은 도구의 문제를 파고들었다. 하지만 도구 이전에, 사람이 무언가를 배우거나 만들려 할 때 보편적으로 거치는 흐름이 있다. 미용실에서 머리를 잘 하고 싶은 사람, 레퍼런스 영상을 수십 개 모아서 작업하는 3D 그래픽 디자이너, 자기 취향에 맞는 옷을 찾는 사람 — 도메인이 전혀 다르지만 같은 구조가 나온다.

먼저 욕망이 있다. 원하는 건 분명한데, 구체적으로 뭘 원하는지는 모른다. 어떤 머리를 하고 싶은지, 어떤 영상을 만들고 싶은지, 어떤 스타일이 내 것인지. 형태 없는 욕망이 출발점이다.

그래서 탐색한다. 핀터레스트를 뒤지고, 레퍼런스 영상을 돌려보고, 룩북 링크를 돌아다닌다. 아직 기준이 없으니 넓게 훑을 수밖에 없다.

훑다 보면 마음에 걸리는 게 생긴다. 저장하고, 스크린샷 찍고, 북마크한다. 망각을 피하기 위해서. 이게 포착이다.

모아둔 걸 다시 보면 패턴이 드러난다. "내가 이런 걸 좋아하는구나." 모은 것 자체가 자기 취향의 거울이 된다. 수집물이 곧 자기 이해가 된다.

윤곽이 잡히면 비로소 행동이 가능해진다. 미용사에게 사진을 보여주고, 레퍼런스를 따라 만들고, 옷을 고른다. 경로가 보이는 건 이 시점이다.

다섯 단계로 정리된다.

1. 욕망 — 원하는 건 있지만 형태가 없다
2. 탐색 — 기준 없이 넓게 훑는다
3. 포착 — 마음에 걸리는 걸 건져둔다
4. 윤곽 — 모아둔 것에서 패턴이 드러난다
5. 적용 — 구체적 행동이 가능해진다

기존 도구는 3번 이후부터 시작한다. 1번과 2번 — 뭘 원하는지 모르는 상태에서 탐색하고, 기준 없이 포착하는 과정은 도구의 도움을 거의 받지 못한다. Flux가 풀려는 지점은 2~4단계 사이의 마찰이다. 탐색에서 포착으로, 포착에서 윤곽으로 넘어갈 때 흐름이 끊기지 않게 하는 것.

이 프레임은 문제의 보편성을 보여주기 위한 것이다. 도메인이 달라도 같은 구조가 나타난다는 근거다. 이후 기능 설계는 5장의 세 행위(수집, 검토, 메모)로 다룬다.


## 3. 핵심 가설

우리가 걸고 있는 베팅. 이게 맞으면 앱이 성립한다. 중요도 순이다.

가설 1: 문제가 있다. 깊은 작업을 하는 사람들은 정보 도구 간 전환으로 몰입이 반복적으로 깨지고, 이것이 사고의 질을 떨어뜨린다.

근거가 가장 강한 가설이다. 학술 연구 4편(Gloria Mark, Information Overload, Multitasking, Task Switching), 정규영 CD 인터뷰, 초기 사용자 피드백, 개인 동기 모두 같은 방향을 가리킨다.

가설 2: 통합이 해결책이다. 수집→정리→메모→검색을 한 도구 안에서 끊김 없이 할 수 있으면, 도구 전환이 줄고 몰입 시간이 늘어난다.

핵심 베팅이다. 근데 Notion이 이미 "올인원"을 시도했고 느려서 실패했다. 통합만으로는 안 된다는 교훈이 있다. 속도 조건은 가설 7에서 다룬다.

가설 3: AI가 메타데이터를 대신 붙인다. AI가 수집 순간에 요약, 키워드, 출처를 자동 기록하면, 수집 마찰이 카톡 나에게 보내기 수준으로 낮아진다.

"정리는 프로그램이, 활용은 사용자가"의 핵심이다. 사용자는 저장만 하고, AI가 나중에 찾을 수 있게 메타데이터를 붙인다. 폴더 분류는 시키지 않는다 — 사용자가 검토하면서 자연스럽게 일어난다. 이게 안 되면 "또 하나의 메모앱"이 된다.

가설 4: 의도를 보존할 수 있다. AI가 수집 순간의 맥락을 기록하면 "왜 저장했지?"가 사라지고, 나중에 활용률이 올라간다.

2장 5층 — "왜 저장했는지 잊는" 문제를 해결하는 가설이다. URL만 저장하는 도구와 달리 맥락을 함께 저장하면 3주 뒤에도 의도가 살아 있다. 정규영 CD가 "파이트 클럽 메모"에서 아이디어를 꺼낸 건 메모에 의도가 녹아 있었기 때문이다.

가설 5: 즉각적 보상이 습관을 만든다. 수집 순간에 AI가 주는 즉각적 보상(요약, 키워드, 연결)이 수집 행위 자체를 재미있게 만들고, 축적 임계점 도달 전에도 자발적으로 쓰게 한다.

가설 3과 다른 축이다. 가설 3은 "마찰을 낮출 수 있는가"이고, 이건 "마찰이 낮아도 쓸 동기가 있는가"다. 정규영 CD가 "당위가 아니라 재미가 있으면 누가 시키지 않아도 된다"고 했다. 임계점 전에 이탈하는 게 가장 큰 위험이므로 이 가설이 리텐션의 열쇠다.

가설 6: 축적의 임계점이 있다. 200~300개 축적 후 레퍼런스 간 연결과 재발견의 가치가 급증하고, 이 지점을 넘긴 사용자는 이탈하지 않는다.

정규영 CD의 증언이 근거다. "처음에 열 개 20개가 모여져 있으면은 그런 느낌이 안 들어요. 근데 200개, 300개 모아지고 나면은 처음에 모았을 때 느끼지 못했던 것들이 보인다." 이 임계점까지 사용자를 데려가는 것이 온보딩의 핵심 과제다.

가설 7: 로컬 우선이 체감 차이를 만든다. 로컬 우선 아키텍처가 수집 < 100ms를 보장하고, 이 속도가 수집 습관 형성에 결정적 차이를 만든다.

Fabric과의 기술적 차별점이다. 이게 틀려도 앱 자체는 성립하지만, "왜 Fabric 안 쓰고 Flux를 쓰나?"에 답하기 어려워진다.


### 검증 계획

가설 1(문제가 있다) — 베타 사용자 30명 인터뷰. "정보를 다루다가 흐름이 끊긴 경험"을 물어서 70% 이상이 공감하면 통과.

가설 2(통합이 해결책이다) — 베타 사용자의 앱 전환 횟수를 측정한다. Flux 사용 전후로 리서치 작업 중 앱 전환이 30% 이상 줄면 통과.

가설 3(AI가 메타데이터를 대신 붙인다) — 수집 후 AI가 붙인 요약·키워드의 정확도를 사용자가 평가한다. 수정률이 20% 이하면 통과. 수집 마찰은 평균 수집 소요 시간으로 측정 — 3초 이내면 통과.

가설 4(의도를 보존한다) — 수집 후 2주 뒤에 아이템을 다시 열었을 때 "왜 저장했는지 안다"고 답하는 비율. 80% 이상이면 통과.

가설 5(즉각적 보상이 습관을 만든다) — 첫 주 일평균 수집 건수가 2주차에도 유지되는지. 주간 수집 건수 감소율 20% 이내면 통과.

가설 6(축적 임계점) — 수집 200개를 넘긴 사용자와 못 넘긴 사용자의 30일 리텐션을 비교한다. 200개 초과 그룹의 리텐션이 2배 이상이면 통과.

가설 7(로컬 우선이 체감 차이를 만든다) — 수집 응답 시간을 측정한다. p95가 100ms 이내면 기술적 통과. 사용자 설문에서 "빠르다"고 답하는 비율 80% 이상이면 체감 통과.


### 핵심 메트릭

제품 전체의 건강을 측정하는 지표다. 개별 가설 검증과 별개로, 이 숫자들이 제품이 작동하고 있는지를 말해준다.

- 일간 수집 건수 — 사용자가 매일 얼마나 모으는가. 수집이 없으면 나머지가 다 무의미하다.
- 주간 활성 사용자(WAU) — DAU보다 WAU가 맞다. 매일 쓰는 도구가 아니라 "생각할 때마다 쓰는 도구"이므로 주 단위가 자연스럽다.
- 임계점 도달률 — 전체 사용자 중 200개 수집을 넘긴 비율. 가설 6의 핵심 전환점이다.
- 검토 비율 — 수집한 아이템 중 다시 열어본 비율. 수집만 하고 안 보면 "카톡 나에게 보내기"와 다를 바 없다.
- 30일 리텐션 — 가입 후 30일 뒤에도 쓰고 있는가. 임계점 도달 여부와 교차 분석한다.


## 4. 타겟 사용자


### 기존 정의의 문제

에센스에서 나오는 타겟 정의가 세 가지다. "R&D 연구원, BI, 기획자, 작가, CD" 같은 직군 나열, "파워 유저" 같은 레이블, 2장에서 나온 "깊은 작업을 하는 사람".

직군 나열은 너무 넓다. R&D 연구원과 작가의 정보 수집 패턴은 다르다. "파워 유저"는 형용이지 정의가 아니다 — 이걸로는 사용자를 찾을 수 없다. "깊은 작업을 하는 사람"은 방향은 맞지만 구체적이지 않다.


### 행동으로 정의한다

타겟은 직군이 아니라 행동 패턴으로 정의한다. 세 가지 조건의 조합이다.

1. 정보를 일상적으로 수집한다 (안테나가 켜져 있다)
2. 현재 여러 도구에 흩어져 있다
3. 수집한 것으로 결과물을 만들거나, 만들고 싶어한다 (활용 의도가 있다)

세 조건을 모두 충족하면 핵심 타겟이다. 1-2만 충족하면 확장 타겟이다.


### 두 가지 동기

에센스에서 타겟의 동기가 두 갈래로 나온다.

하나는 생산성이다. 기획서를 쓰면서 레퍼런스를 찾고, 마감에 쫓기며 보고서를 쓰고, 발표 자료를 정리한다. 업무의 결과물이 정보의 질에 의존하는 사람이다.

다른 하나는 호기심이다. 정규영 CD가 마쓰다 세이코에 빠져서 일본어를 배우고, 일본 카피를 발견한 건 생산성 추구가 아니라 덕질이었다. "당위가 아니라 재미가 있으면 누가 시키지 않아도 된다"고 했다.

이 두 동기가 다른 사람에게 있는 게 아니라, 같은 사람 안에 공존한다. 업무 중에는 기획서를 쓰면서 레퍼런스를 찾고(생산성), 일상에서는 간판과 영화에서 영감을 수집한다(호기심). Flux는 이 두 모드를 자연스럽게 오가는 도구다. "일할 때만 쓰는 도구"가 아니라 "생각할 때마다 쓰는 도구"다.


### 같은 사람, 다른 단계

"연결해서 새로운 것을 만드는 사람"이 타겟인가, "수집만 하는 사람"도 타겟인가. 이건 다른 사람이 아니라 같은 사람의 다른 단계다.

처음에는 수집만 한다. 링크를 저장하고, 사진을 찍고, 메모를 남긴다. 이 단계에서는 "찾기 편한 것"이 가치다. 200~300개 쌓이면 연결이 보이기 시작한다. 정규영 CD도 "처음에 열 개 20개가 모여져 있으면은 그런 느낌이 안 들어요"라고 했다. 이 전환이 가설 6(축적의 임계점)이다.

그래서 타겟은 "연결까지 가는 사람"이 아니라 "수집을 시작하고, 임계점까지 도달할 수 있는 사람"이다. 임계점까지 데려가는 것이 제품의 일이다.


### 초기 타겟과 확장 타겟

초기 사용자 피드백에서 스펙트럼이 보인다.

초기 타겟은 영의님(7번) 같은 사람이다. Readwise → Omnivore → mymind → Fabric을 거쳐 도구를 계속 바꿔봤다. 불편함을 명확히 인식하고, 더 나은 도구를 능동적으로 찾고 있다. 설득이 필요 없고 제품만 좋으면 쓴다.

확장 타겟은 단짝 친구(3번) 같은 사람이다. "그냥 앞에 있는 거 쓴다." 메모장을 우측에 길게 세팅해두고, 불편하지만 감수하고 있다. 이 사람을 전환시키려면 마찰이 극적으로 낮아야 한다 — 지금 쓰는 메모장보다 더 쉬워야 한다.


### 가장 큰 시장

"수집-연결-창작"을 이미 잘 하는 사람은 소수다. 가장 큰 시장은 수집은 하는데 활용을 못 하고 있는 사람이다. 사업계획서 멘토님이 "기록해둔 링크를 2줄로 요약해주면 쓰겠다"고 한 건, 링크를 모으긴 하는데 나중에 열면 "이게 뭐였지?"가 되기 때문이다. "왜 저장했는지 잊는" 문제(2장 5층)가 정확히 이 사람들의 문제다.

인스타 저장, 유튜브 나중에 보기, 카톡 나에게 보내기 — 이걸 하는 사람이 다 넓은 의미의 수집자다. 자기가 "정보 수집"을 하고 있다는 자각이 없을 뿐이다. Flux가 저장할 때 이유를 함께 남겨서(가설 4) 나중에 열어도 왜 저장했는지 알 수 있으면, 링크만 쌓아두던 사람이 그걸 꺼내서 기획서에 쓰기 시작한다.

초기에 시장이 좁아도 괜찮다. Obsidian이 PKM 마니아에서 시작해서 넓어졌고, Figma가 디자이너에서 시작해서 비디자이너까지 갔다. 좁은 타겟에서 강한 리텐션(가설 6, 축적 임계점)을 만들면 자연스럽게 퍼진다.


### 수집 순간의 맥락

타겟이 도구를 꺼내는 순간이 다양하다. 웹을 읽다가, 길을 걷다가, 영화를 보다가, 회의 중에, 책을 읽다가. 각 순간의 디바이스와 긴급도가 다르다.

패턴이 있다. 수집은 모바일에서 시작하고, 활용은 데스크톱에서 한다. 정규영 CD가 "핸드폰으로 찍고 나중에 한꺼번에 모은다"고 했다. 단짝 친구는 "우측에 메모장을 길게 세팅해둔다"고 했다. 타겟은 멀티 디바이스 사용자다. 모바일 수집 → 데스크톱 활용 흐름이 끊기지 않아야 한다.

"생각할 때마다 쓰는 도구"라면 항상 접근 가능해야 한다. 이건 가설 7(로컬 우선, < 100ms)의 타겟 관점 근거다. 항상 켜져 있으면서 느리지 않으려면 로컬이어야 한다. 이겨야 할 상대는 Notion이 아니라 카톡 나에게 보내기다.

플랫폼별 수집 경로는 기준(정한것)/플랫폼.md에 정리했다. 핵심은 폴더 감시, 클립보드 감시, 공유 시트 같은 OS 기본 경로를 연결해서 "저장한다"는 행위 자체를 없애는 것이다.


### 활용의 스펙트럼

위 정의의 3번 조건이 "수집한 것으로 결과물을 만들거나, 만들고 싶어한다"인데, "활용"의 폭이 생각보다 넓다.

에센스에서 세 사람의 "활용"이 다 다르다. 사업계획서 멘토님은 "링크를 2줄로 요약해주면 쓰겠다"고 했다. 나중에 다시 열었을 때 "이게 뭐였지?"가 안 되게 해달라는 거다 — 참조다. 정규영 CD는 "200-300개 모이면 연결이 보인다"고 했다. 쌓인 것에서 예상 못한 패턴을 찾는 것이다 — 발견이다. 단짝 친구는 "우측에 메모장을 길게 세팅해둔다"고 했다. 지금 하는 작업의 맥락을 유지하는 것이다 — 즉시 참조다.

활용에는 세 층위가 있다.

1. 참조 — 나중에 다시 이해하고 싶다
2. 조합 — 여러 정보를 엮어서 결과물을 만든다
3. 발견 — 쌓인 것에서 예상 못한 패턴을 찾는다

"결과물을 만든다"만이 활용이 아니다. "나중에 다시 이해하고 싶다"도 활용 의도다. 이렇게 보면 타겟이 넓어진다. 사업계획서 멘토님(참조)도, 정규영 CD(발견)도 모두 타겟이다.

기능 설계에도 영향을 준다. 참조를 위한 기능(AI 요약, 맥락 보존)과 발견을 위한 기능(연결 탐색, 의미 검색)이 다르다. 두 종류의 활용을 모두 지원해야 타겟을 넓게 잡을 수 있다.


### 감정 궤적

타겟의 여정을 감정으로 그리면 선형이 아니다. 루프와 전환점이 있다.

먼저 불안의 루프가 있다. 수집을 할수록 흩어지고, 흩어질수록 불안해지고, 불안해서 더 수집한다. 카톡에도 보내고, 인스타도 저장하고, 스크린샷도 찍는다. 수집 자체가 불안을 키우는 악순환이다. 이 루프가 임계점을 넘으면 2장 2층 — 가장 쉬운 곳에 던지기 시작한다. 수집을 포기하는 게 아니라, 활용을 포기하는 것이다.

Flux의 첫 번째 역할은 이 루프를 끊는 것이다. "여기에 넣으면 안전하다"는 확신 하나가 불안의 루프를 끊는다.

감정의 전환점이 다섯 단계로 나뉜다.

```
불안 ("어디 저장했지?")
→ 안도 ("여기 다 있네")
→ 통제 ("내 것이 다 보인다")
→ 희열 ("이런 연결이!")
→ 정체성 ("나는 체계적인 사람이다")
```

안도감이 첫 관문이다. 에센스에서 "5분 안에 아하 모먼트"라고 했는데, 이 "아하"는 AI 자동 정리가 아니라 "여기 다 있네"일 수 있다. 처음 설치하고 폴더 경로만 연결하면 이미 있던 스크린샷이 쏟아져 들어오는 순간이다. 이게 첫 안도감이다.

통제감은 양이 늘어도 유지돼야 한다. 100개일 때 통제감이 있었는데 1,000개가 되니까 압도감으로 바뀌면 안 된다. AI 자동 정리와 검색이 통제감을 지키는 역할을 한다.

희열은 예상 못한 연결에서 온다. 정규영 CD가 파이트 클럽 메모에서 현대증권 광고 아이디어를 뽑아낸 것처럼. 이건 설계할 수 없지만 발생 조건은 설계할 수 있다 — 축적과 검색 가능성이 만나면 우연한 연결의 확률이 올라간다.

심리학에서 말하는 변동비율 강화(variable ratio reinforcement)와 같다. 수집할 때마다 즉시 보상이 오진 않지만, 가끔 예상 못한 발견이 나오면 강한 보상이 된다. "당위가 아니라 재미"의 메커니즘이 이것이다.

마지막은 정체성이다. 에센스에서 "체계적이고 통찰력 있는 전문가로 보이고 싶다"는 사회적 욕구가 있었다. 수집을 꾸준히 하고, 연결을 발견하고, 결과물을 만들면 자기 인식이 바뀐다. "카톡에 아무거나 던지는 사람"에서 "자기만의 아카이브를 가진 사람"으로.

활용의 세 층위가 각각 다른 감정을 준다. 참조는 안도감, 조합은 통제감, 발견은 희열이다. 이게 온보딩과 리텐션 설계에 직접 연결된다. 첫 5분에 안도감을 줘야 쓰기 시작하고, 축적 임계점에서 통제감과 희열을 줘야 계속 쓴다.


### 도구 순회자의 정착 조건

영의님이 Readwise → Omnivore → mymind → Fabric을 거쳤다. 감정으로 보면 반복된 실망이다. 기대 → 시도 → 부족함 발견 → 이탈. 매번 "이번엔 괜찮을까"로 시작해서 "역시 안 되네"로 끝난다.

각 도구를 떠난 이유를 추론할 수 있다. Readwise는 하이라이트에 특화돼서 텍스트 외 수집이 약했다. Omnivore는 웹 클리핑에 특화됐지만 서비스가 종료됐다. mymind는 AI 자동 정리가 있지만 활용까지 연결되지 않았을 수 있다. Fabric은 AI로 수집, 정리, 검색을 동시에 만족시켜서 "정착"에 이르렀다.

정착은 감정으로 환원된다. "이 도구에서 안도감과 통제감을 지속적으로 얻을 수 있다"는 확신이다. 수집, 정리, 검색 중 하나만 약해도 실망이 오고 순회가 다시 시작된다.

Flux가 Fabric에서 사용자를 빼올 필요는 없다. 아직 정착 못 하고 순회 중인 사람, 또는 순회를 시작하지도 않은 사람이 훨씬 큰 시장이다. 카톡 나에게 보내기에 머물러 있는 사람 — "가장 큰 시장"에서 말한 바로 그 사람들이다.


### 타겟이 아닌 사람

타겟 밖의 경계도 명확하다.

이미 하나의 도구로 만족하는 사람. 정윤이형이 "옵시디언 잘 쓰고 있으니까 괜찮다"고 했다. 흩어짐을 겪지 않으므로 Flux가 해결할 문제가 없다.

얕은 작업만 하는 사람. 이메일, 메시지 위주의 업무. 2장에서 말했듯 전환 비용이 낮아서 앱을 오가도 하던 일을 잊지 않는다.

협업이 주 목적인 사람. Notion의 핵심 사용자. Flux도 협업을 지원하지만, 핵심 가치는 개인의 수집→메모 흐름이다(8장 구현 순서). 협업만을 위해 쓰는 사람은 타겟이 아니다.

정보를 거의 수집하지 않는 사람. 기억에 의존하거나 수집 습관 자체가 없다. 안테나가 꺼져 있는 사람에게 안테나를 켜주는 건 Flux의 역할이 아니다.

매일 정보를 수집하고, 여러 곳에 흩어진 채 살고, 그걸로 무언가를 만드는 사람. 이 사람이 불안에서 안도로, 안도에서 희열로 가는 여정을 Flux가 설계한다.


## 5. 워크플로우


### 기존 모델과의 관계

에센스에 5단계 워크플로우가 있었다. 수집→검토→통합→정제→발상. Electron 시대에 정의한 것이다.

이 모델이 틀린 건 아니다. 추상화 수준이 다르다. 수집→검토→통합→정제→발상은 리서치 과정 전체를 설명하는 프레임이다. "사람이 정보를 모아서 결과물을 만드는 과정"으로 보면 맞다. 근데 Flux가 설계해야 하는 건 도구 사용 흐름이다. 사용자가 앱을 열고, 뭔가를 하고, 닫는 그 흐름. 그래서 같은 5단계를 그대로 쓸 수 없다.

안 맞는 부분이 네 가지 있다.

첫째, 빈 상태에서 시작한다고 가정한다. 이 모델은 프로젝트가 시작되는 순간부터 수집을 시작하는 구조다. 실제로는 이미 쌓인 것들이 있을 수 있다. 인스타 저장, 카톡 나에게 보내기, 스크린샷, 브라우저 북마크. Flux를 처음 설치하는 사람의 풀이 반드시 비어 있지는 않다. 기존 모델에는 "이미 있는 것을 가져오는" 시작점이 없다.

둘째, 모드 구분이 안 된다. 포스트잇 모드를 생각하면 명확하다. 브라우저 옆에 Flux를 띄워두고 웹을 읽다가 드래그해서 수집하고, 수집한 것을 훑어보다가 메모를 적고, 메모를 쓰면서 다시 검색한다. 수집과 검토와 통합이 한 화면 안에서 동시에 일어난다.

셋째, 검토가 독립된 필수 단계가 아니다. 기존 모델에서 검토는 수집 다음에 오는 별도 단계다. 실제로는 수집하는 순간에 이미 판단이 일어나고(이거 저장할까 말까), 나중에 쓸 때 다시 판단이 일어난다(이게 쓸만한가). 검토가 없는 게 아니라, 다른 행위에 녹아 있거나 나중으로 밀린다.

넷째, 시간 축이 없다. 5단계는 한 프로젝트 안의 순서를 말한다. 근데 실제로는 3주 전에 수집한 게 오늘 갑자기 쓸모 있어지고, 오늘 수집한 게 6개월 뒤에 다른 맥락에서 연결된다. 같은 아이템이 시간에 따라 역할이 바뀐다. 5단계 모델은 이 시간 축을 담지 못한다.

플랫폼도 달라졌다. Electron 시대에는 데스크톱 앱 하나였다. 지금은 모바일(RN)이 수집의 주 경로이고, 데스크톱은 활용의 주 경로다. 같은 워크플로우가 디바이스를 넘나든다.


### 세 행위

사용자가 Flux에서 하는 일은 세 가지다. 수집, 검토, 메모.

수집. 링크를 저장하고, 사진을 찍고, 텍스트를 드래그한다. 경로는 여러 개지만 행위는 하나다 — 바깥에서 안으로 가져온다.

검토. 쌓인 것을 훑고, 별 표시를 달고, 필요 없는 걸 치운다. 수동에서 능동까지 스펙트럼이 있다 — 그냥 스크롤하다가 눈에 띄면 멈추고, 멈추다 보면 별을 달고, 별을 달다 보면 비교하기 시작한다. 사용자가 이 사이를 의식적으로 전환하지 않는다. 그래디언트다.

1번 파트에서 "검토가 다른 행위에 녹아 있다"고 했는데, 녹아 있는 곳이 여기다. 또한 검토는 나머지 둘의 촉발제이기도 하다. 훑다가 관련 자료가 떠오르면 수집하고, 연결이 보이면 메모를 시작한다.

메모. 노트를 열고, 수집한 것을 끌어오고, 자기 생각을 덧붙인다. 여기서 "메모"는 완성된 글을 쓰는 게 아니다. 수집물을 엮으면서 생각을 만드는 중간 행위다. Flux는 정리된 생각의 중간 결과물까지를 다루고, 최종 산출물(발표 자료, 보고서)은 기존 도구의 영역이다.

이 세 가지는 단계가 아니다. 동시에 일어나되 비율이 달라진다. 비율을 바꾸는 건 시간보다 맥락이다. 퇴근길 지하철에서는 수집이 대부분이고, 주말에 노트북 앞에 앉으면 검토와 메모가 주가 된다. 디바이스와 상황이 비율을 결정한다.

세 행위가 사용자가 하는 일이라면, 정보 흐름은 그때 정보에 일어나는 일이다.

들어옴. 어디선가 정보가 풀에 들어온다. 링크, 이미지, 텍스트, 스크린샷, 음성 메모.

쌓임. 들어온 것이 풀에 머문다. 당장 쓰이지 않아도 사라지지 않는다.

걸러짐. 쌓인 것 중에 일부가 올라오고 일부가 가라앉는다. AI가 태그와 요약을 자동으로 붙이고, 자주 여는 건 위로 올라오고, 사용자가 별을 달거나 지울 수도 있다.

엮임. 걸러진 것들이 연결된다. 메모 안에서 자료가 만나고, 사용자의 생각이 덧붙여진다.

나감. 엮인 것이 풀 바깥으로 나간다. Flux 안의 메모일 수도 있고, 다른 도구로 내보낸 결과물일 수도 있다.

이 흐름은 선형이 아니라 순환이다. 나간 것이 다시 들어올 수 있다. 6개월 전에 쓴 메모가 새 프로젝트의 참고 자료가 되고, 예전에 치웠던 링크가 다시 쓸모 있어진다.

풀 안에는 항상 네 종류가 섞여 있다. 갓 들어온 것, 오래 쌓여 있는 것, 지금 만들고 있는 것, 끝난 것. 빈 풀에서 시작해서 채우는 게 아니라, 이 네 가지가 동시에 존재하는 상태가 Flux의 기본이다.


### 쌓인 것 중에 중요한 게 올라오는 과정

위에서 한 줄로 정의했다. 펼치면 세 층이 있다.

자동. AI가 수집 시점에 붙이는 것이다. 요약, 키워드 3개, 출처, 타임스탬프. 사용자가 아무것도 안 해도 일어난다. 폴더에 넣거나 분류하지 않는다 — 나중에 찾을 수 있게 메타데이터만 붙인다. 가설 3의 구체적 작동 지점이다.

암묵적. 사용자 행위에서 드러나는 선호다. 자주 여는 아이템은 올라오고, 안 여는 건 가라앉는다. 별도 판단 없이 사용 패턴 자체가 필터 역할을 한다.

명시적. 사용자가 직접 하는 판단이다. 별 표시, 삭제, 아카이브. 가장 강한 신호지만 마찰도 가장 크다.

"왜 저장했는지"를 남기는 것도 중요한 게 올라오는 과정에 속한다. 2장 5층에서 다뤘다 — 링크를 저장하고 3주 뒤에 열면 "이게 뭐였지?"가 되는 문제. AI가 자동으로 붙이는 요약과 키워드가 이걸 막는다.

저장 이유를 남기는 방법도 세 층이 있다. 링크를 저장하면 URL, 시각, 어떤 앱에서 저장했는지가 자동으로 붙는다. AI가 페이지를 읽고 2줄 요약과 키워드 3개를 뽑아서 3주 뒤에 열어도 뭔지 안다. 사용자가 원하면 "이 디자인 온보딩에 참고"처럼 한 줄 메모를 남길 수 있지만, 안 남겨도 된다.

세 층 모두 마찰이 0이거나 최소다. 같은 시간대 수집물을 묶는 것은 활성 맥락에서 다룬다. 가설 4(의도를 보존할 수 있다)의 구현이다.

시간이 쌓이면 아이템마다 "무게"가 달라진다. 자주 열리고 별이 달린 건 무겁다. 한 번 들어와서 안 열린 건 가볍다. 이 무게가 검색과 연결 제안의 근거가 된다.


### 엮임의 트리거

풀에 쌓인 것이 연결되는 순간이다. 워크플로우에서 가장 중요한 전환점이다 — 풀(재료)에서 문서(결과물)로 넘어가는 지점이기 때문이다.

트리거가 세 종류다.

외부 압력. 마감이 온다. 기획서를 내야 하니까 쌓인 레퍼런스를 엮기 시작한다.

내부 충동. 훑다가 연결이 보인다. 정규영 CD가 파이트 클럽 메모에서 광고 아이디어를 뽑아낸 순간이 이것이다. 검토가 촉발제 역할을 하는 지점이기도 하다.

축적 임계점. 200~300개 쌓이면 처음에 못 느꼈던 게 보인다(3장 가설 6). 양 자체가 트리거가 된다.

세 번째 트리거가 제품 설계에 중요하다. 외부 압력과 내부 충동은 사용자에게 달린 것이지만, 축적 임계점은 제품이 도울 수 있다. 200개가 쌓였을 때 "이런 연결이 보이기 시작합니다"를 알릴 수 있는가. 이건 열린 질문이다.


### 활성 맥락

"지금 이 주제로 모으고 있다"를 선언하는 횡단 레이어다. 풀의 모든 단계 — 들어올 때, 거를 때, 엮을 때 — 에 방향을 준다.

활성 맥락이 있으면 수집할 때 "어디에 넣지?"를 안 물어도 된다. 2장 2층에서 "분류 판단을 포기하는 게 인지적으로 맞다"고 했는데, 활성 맥락은 그 판단을 수집 전에 미리 해놓는 것이다. 활성 맥락이 켜져 있으면 거기 가고, 없으면 inbox로 간다. AI는 어디에 넣을지를 정하지 않고 메타데이터(요약, 키워드)만 붙인다.

폴더와 세션의 시간 방향이 반대다. 폴더는 과거를 정리하는 도구다. 이미 수집한 것들을 끌어다 넣는다. 세션은 미래를 향한 도구다. "지금부터 이 주제야"를 선언하면, 앞으로 수집하는 것들이 자동으로 담긴다. Arc 브라우저의 Space가 이 원리다 — 그 Space에서 열리는 탭은 자동으로 거기 소속된다.

기본은 자동이다. 사용자가 아무것도 선언하지 않아도, AI가 시간적 근접성과 내용 유사성을 보고 수집물을 묶는다. "2월 17일 오후, 디자인 시스템 관련 수집 4건" 같은 자동 세션이 만들어진다. 마찰이 0이다.

사용자가 원하면 명시적으로 지정할 수도 있다. 포스트잇에 "온보딩 리서치"라는 제목을 달고 열어두면, 그 포스트잇이 열려 있는 동안 수집하는 것들이 거기 연결된다. 풀 앱에서 특정 폴더를 "수집 대상"으로 지정하는 것도 가능하다.

깊이에 따라 활성 맥락이 다르게 작동한다. 감시(폴더 감시, 클립보드 감시)에서는 맥락 지정이 불가능하다 — 사용자가 관여하지 않으니까. 캡처(공유 시트, 단축키)에서는 활성 맥락이 있으면 자동 귀속되고, 없으면 inbox로 간다.

포스트잇 모드에서는 포스트잇 자체가 맥락이다. 풀 앱에서는 열려 있는 문서나 폴더가 맥락이다.

세션은 저장 이유를 시간 단위로 묶어주기도 한다. "이 5개 링크를 왜 모았지?"의 답이 개별 링크에는 없다. 세션으로 묶이면 "온보딩 UI 조사 중에 모았음"이 맥락으로 남는다. AI가 세션 단위로 요약을 붙이면 3주 뒤에도 의도가 살아있다.

Arc와 다른 점이 하나 있다. Arc의 Space는 닫히면 아카이브되고 끝이다. Flux의 세션은 닫혀도 연결이 살아있다. "온보딩 리서치" 세션에서 모은 색채 팔레트가 3개월 뒤 "브랜딩 프로젝트"에서 검색으로 다시 나올 수 있다. 세션은 닫힌 컨테이너가 아니라 열린 맥락 레이어다.


### 순환과 재발견

워크플로우가 선형이 아니라는 것의 구체적 근거다. 순환이 세 가지 길이로 일어난다.

짧은 순환. 문서를 쓰다가 레퍼런스가 부족하다. 수집하러 간다. 다시 문서로 돌아온다. 한 세션 안에서 수 분 단위로 반복된다.

중간 순환. 포스트잇 모드로 가볍게 수집하다가 주제가 커진다. 풀 앱을 열어서 본격적으로 엮기 시작한다. 하루에서 며칠 단위다.

긴 순환. 수집이 쌓인다. 임계점(200~300개)을 넘긴다. 연결이 보이기 시작하면서 문서를 시작한다. 주에서 월 단위다. 가설 6(축적 임계점)이 이 순환에서 작동한다.

재발견은 "나감" 이후의 순환이다. 6개월 전에 쓴 메모가 새 프로젝트의 참고 자료가 된다. 예전에 치웠던 링크가 다시 쓸모 있어진다. 풀의 가치가 시간이 갈수록 커지는 이유다. 정규영 CD가 파이트 클럽 메모에서 현대증권 광고를 꺼낸 건 긴 순환의 재발견이다.

같은 아이템이 시간에 따라 역할이 바뀐다. 수집 직후에는 참조다. 일주일 뒤에는 조합 재료가 된다. 3개월 뒤에는 발견 촉매가 될 수 있다. 4장에서 정의한 활용의 스펙트럼(참조→조합→발견)이 시간 축에서 자연스럽게 펼쳐지는 것이다. 아이템이 수집 시점의 맥락에 갇히면 안 되는 이유가 여기 있다.

프로젝트 단위로 보면 세 행위의 비율이 바뀐다. 초기에는 수집이 대부분이고, 중기에는 검토와 엮기가 주가 되고, 후기에는 메모와 나감이 주가 된다. 완전히 한 모드로만 있는 시점은 없다 — 항상 세 행위가 공존하되 비율이 달라진다.


### 설계 원리

1~6이 사용자 경험이라면, 여기는 그 경험을 가능하게 하는 내부 구조다. 사용자에게 보이지 않지만 기능 결정의 근거가 된다.

#### 깊이 모델

사용자의 몰입도를 네 단계로 나눈다.

감시. 앱을 안 쓰고 있다. 폴더 감시, 클립보드 감시가 백그라운드에서 돈다. 스크린샷이 자동으로 들어온다.

캡처. 지나가다 수집한다. 공유 시트, 단축키. 1~2초 안에 끝난다.

포스트잇. 다른 작업 하면서 Flux가 옆에 떠 있다(포스트잇 모드 — 투명 창, 항상 위). 수집과 참조와 메모가 동시에 일어나는 상태다.

몰입. 풀 앱을 열고 엮고 쓴다. 검색하고, 정리하고, 문서를 만든다.

깊이 사이의 전환에는 트리거가 있다. 올라가는 방향부터 보면 — 감시에서 캡처로는 자극이다. 눈에 뭔가 띈다. 캡처에서 포스트잇으로는 흥미의 지속이다. 닫지 않고 "좀 더 보자"가 된다. 포스트잇에서 몰입으로는 양의 축적이다. 포스트잇으로는 부족해진다.

내려가는 방향도 있다. 몰입에서 포스트잇으로는 피로나 전환이 트리거다. 포스트잇에서 감시로는 관심 소멸이다.

Flux의 역할은 전환을 유도하는 게 아니라 전환할 때 마찰을 없애는 것이다. 포스트잇에서 풀 앱으로 갈 때 메모가 그대로 이어져야 하고, 풀 앱에서 포스트잇으로 돌아갈 때 지금 쓰던 문서가 포스트잇에서 계속 보여야 한다.

플랫폼별로 깊이 분포가 다르다. 모바일은 감시와 캡처만 일어난다. 포스트잇과 몰입은 데스크톱이다. 4장에서 "모바일에서 수집하고 데스크톱에서 쓴다"고 한 것과 같다.

#### 시간

세 가지 시간 축이 있다.

세션 시간. 앱을 열고 닫는 단위다. "지금 이 주제로 모으고 있다"를 AI가 자동으로 묶는 게 이 단위에서 작동한다.

아이템 시간. 수집된 후 경과 시간에 따라 역할이 바뀐다. 순환과 재발견에서 설명한 참조→조합→발견이 이 축이다.

프로젝트 시간. 주제의 생애주기다. 시작→축적→임계점→엮임→완료. 완료된 프로젝트의 재료가 새 프로젝트로 재발견되므로, 이것도 순환이다.

#### AI 역할

깊이에 따라 AI의 역할이 달라진다.

감시에서 AI는 유일한 행위자다. 폴더에 스크린샷이 들어오면 AI가 요약과 키워드를 자동으로 붙인다. 정확도보다 마찰 0이 중요하다 — 틀려도 나중에 고치면 된다.

캡처에서 AI는 즉시 보상 역할이다. 링크를 수집하면 2초 안에 요약이 뜬다. 가설 5(즉각적 보상이 습관을 만든다)가 여기서 작동한다. 이건 정확해야 한다 — 요약이 틀리면 보상이 아니라 노이즈다.

포스트잇에서 AI는 맥락 연결 역할이다. 메모를 적으면, 기존 수집물 중 관련 있는 것을 조용히 제안한다. 능동적으로 끼어들지 않는다. 사용자가 필요할 때 볼 수 있게 해놓을 뿐이다.

몰입에서 AI는 동료 역할이다. 문서를 쓰면서 "이 부분에 대한 자료 찾아줘"를 할 수 있다. 수집한 것들을 바탕으로 RAG 대화를 한다. 여기서만 AI가 대화형이다.

패턴이 있다. 깊이가 낮을수록 AI는 자동이고, 깊이가 높을수록 AI는 대화형이다. 감시에서는 존재감이 0이고, 몰입에서는 옆에 앉은 동료다.


### 열린 질문

아직 답이 없는 것들이다.

출력 경계. Flux는 어디까지 다루는가. "쓰다"에서 "정리된 생각의 중간 결과물"이라고 했지만, 구체적 경계가 불명확하다. 메모에서 발표 자료로 넘어가는 지점이 Flux 안인가 밖인가.

임계점 넛지. 200~300개 쌓였을 때 제품이 연결을 보여줄 수 있는가. 알린다면 어떤 형태가 적절한가. 푸시인가, 앱 안의 조용한 배너인가, AI가 자동으로 연결을 보여주는 것인가.

오프라인 워크플로우. 감시, 캡처, 포스트잇은 로컬로 충분하다(가설 7, 로컬 우선). 몰입의 AI 대화만 온라인이 필요하다. 온라인 없이도 AI가 자동으로 태그와 요약을 붙일 수 있는가.

워크플로우는 단계가 아니라 풀이다. 정보가 들어오고, 쌓이고, 걸러지고, 엮이고, 나간다. 사용자는 수집하고, 검토하고, 메모한다. Flux는 이 풀의 흐름이 끊기지 않게, 각 깊이에서 맥락이 이어지게 설계한다.


## 6. 철학

기능을 넣을지 뺄지 판단할 때 꺼내 보는 원칙.


### 기존 원칙의 한계

에센스에 원칙이 여러 세트 있었다. 설계 철학 5개(인지 부하 최소화, 몰입 유지, 점진적 복잡성, 즉각적 피드백, 로컬 우선), 디자인 원칙 5개(본질, 즉각, 몰입, 집중, 배려), 기록학 원칙 4개(진본성, 무결성, 맥락성, 검색성). 각각 다른 시점에 다른 맥락에서 만든 것이다.

문제는 두 가지다. 하나는 수가 많다 — 14개를 머릿속에 넣고 기능을 판단할 수 없다. 다른 하나는 추상화 수준이 다르다 — "인지 부하 최소화"와 "진본성"을 같은 기준으로 쓸 수 없다. 실제로 1~5장을 쓰면서 이 원칙들을 직접 참조한 적이 거의 없다. 대신 반복적으로 쓰인 암묵적 판단 기준이 있었다.


### 하나의 목적

0장에서 "인지 전환 비용을 줄이는 것"이라고 했다. 제품 수준에서 이게 뜻하는 건 — 글을 쓰다가 자료를 찾으러 갔을 때, 돌아와서 어디까지 했는지 바로 이어갈 수 있게 하는 것이다.

2장 전체가 이 문제를 정의했다. 깊은 작업일수록 앱을 더 자주 바꾸고(6층), 바꿀 때마다 어디까지 했는지 잊고(4층), 이어붙이던 아이디어를 잃는다(5층). 4장의 감정 궤적도 결국 "흐름이 끊기는 불안 → 흐름이 유지되는 안도"다. 5장의 깊이 모델도 "전환할 때 마찰을 없앤다"다.

모든 기능 판단이 여기서 시작한다. "이 기능이 흐름을 끊는가, 지키는가?"

흐름을 끊는 것이 여섯 가지 있다.

- 도구 전환 (2장 3층)
- 분류 강제 (2장 2층)
- 느린 반응 (가설 7)
- 정리 부담 (2장 3층)
- 맥락 손실 (2장 5층)
- 네트워크 의존 (아키텍처)

이 여섯 가지의 반대편에 원칙이 선다. 네 가지로 묶인다.


### 끊기지 않게

도구 전환이 흐름을 깨는 주범이다. 2장에서 하루 300번 전환, 전환마다 11.5초 인지 저하, 하루 57.5분 손실이라고 했다. 수집→정리→메모→검색을 한 도구 안에서 하는 게 가설 2(통합이 해결책이다)의 핵심이다.

포스트잇 모드가 이 원칙의 가장 극단적인 구현이다. 5장에서 "수집과 참조와 메모가 동시에 일어나는 상태"라고 했다. 브라우저를 떠나지 않고, Flux를 떠나지 않고, 생각을 떠나지 않는다. 마찰은 기능의 수가 아니라 전환의 수에서 온다.


### 시키지 않게

2장 2층에서 "분류를 포기하는 게 인지적으로 맞다"고 했다. 사용자가 합리적으로 포기하는 것을 도구가 강제하면 안 된다. 정리를 시키지 않고, 분류를 강요하지 않고, 설정을 요구하지 않는다.

"정리는 프로그램이, 활용은 사용자가"가 이 원칙의 슬로건이다. AI가 알아서 태그를 붙이고, 자주 여는 건 위로 올리고, 수집 주제를 자동으로 묶는 것 — 전부 여기서 나왔다.

중요한 경계가 있다. "시키지 않게"는 "막지 않게"와 다르다. 사용자가 원하면 별 표시, 폴더 정리, 세션 선언을 할 수 있다. 하지만 안 해도 돌아간다. AI가 붙이는 태그와 사용 패턴만으로도 돌아가야 하고, 사용자가 직접 별을 달거나 폴더에 넣지 않아도 충분해야 한다.



### 잊지 않게

링크는 남아 있는데 왜 저장했는지가 사라지는 문제를 2장 5층에서 다뤘다. 5장에서 URL·시각을 자동으로 붙이고, AI가 요약을 뽑고, 사용자가 원하면 한 줄 메모를 남기는 구조를 설계한 이유다.

원본 보존도 여기에 속한다. 수집한 원본을 수정하지 않는다. 출처를 반드시 남긴다. 기록학의 진본성, 무결성, 맥락성이 이 원칙 안에 있다. 검색성은 "잊지 않게"의 다른 면이다 — 보존했는데 못 찾으면 잊은 것과 같다.

"쌓일수록 좋아진다"도 이 원칙의 시간 축 버전이다. 대부분의 수집 도구는 쌓이면 부담이 된다. Flux는 반대여야 한다. 쌓일수록 검색이 풍부해지고, 연결이 늘어나고, AI가 더 잘 분류하고, 우연한 발견 확률이 올라간다. 100개일 때 좋은데 1,000개가 되면 무너지는 기능은 이 원칙에 어긋난다.


### 기다리지 않게

가설 7에서 "로컬 우선이 체감 차이를 만든다"고 했다. 수집 < 100ms. 이 속도가 습관을 만든다.

기다림은 두 종류다. 하나는 반응 지연이다. 버튼을 눌렀는데 0.5초 뒤에 반응하면 흐름이 끊긴다. 다른 하나는 네트워크 의존이다. 비행기에서, 지하철에서, 와이파이 없는 카페에서 — 이런 순간에 "연결 중입니다"가 뜨면 흐름이 끊긴다.

로컬 우선 아키텍처가 두 가지를 동시에 푼다. 쓰기는 로컬에서 즉시(0ms), 읽기도 로컬에서 즉시. 동기화는 백그라운드에서 나중에. 네트워크는 동기화와 AI 대화에만 필요하다.


### 충돌할 때

네 원칙이 항상 같은 방향을 가리키지는 않는다. 충돌하면 이 순서로 판단한다.

끊기지 않게 > 시키지 않게 > 잊지 않게 > 기다리지 않게.

흐름 보호가 존재 이유이므로 언제나 첫째다.

예를 들어 — 원본 보존(잊지 않게) 때문에 수집이 0.5초 느려지면(기다리지 않게), 보존이 이긴다. 속도를 조금 양보해도 원본은 지킨다.

하지만 보존 때문에 사용자가 직접 뭔가를 해야 하면(시키지 않게), 자동화 방법을 찾아야 한다. "시키지 않게"가 "잊지 않게"보다 위에 있기 때문이다.

기능을 판단할 때 네 가지를 순서대로 묻는다. 이 기능이 흐름을 끊는가? 사용자에게 뭔가를 시키는가? 맥락이 유실되는가? 기다려야 하는가? 네 개 다 통과하면 넣는다. 하나라도 걸리면 다시 설계한다.

Flux는 생각의 흐름을 끊지 않기 위해 존재한다. 끊기지 않게, 시키지 않게, 잊지 않게, 기다리지 않게. 이 네 가지가 모든 기능 결정의 기준이다.


## 7. 핵심 개념

앱을 구성하는 엔티티, 행위, 상태, 설계 어휘. 코드의 네이밍, UI의 레이블, 팀의 소통 언어가 여기서 통일된다.


### 엔티티

데이터의 단위다. 코드명과 UI 이름을 함께 정의한다.

아이템(Item). 풀에 있는 모든 단위다. 링크, 이미지, 텍스트, 스크린샷, 클립보드, 음성 메모. 가볍다 — SQLite INSERT 한 번이면 끝나고 100ms 안에 저장된다. 타입별로 content(텍스트 본문 또는 파일 경로)와 metadata(URL, 제목, 파비콘, 출처 앱)가 다르다. AI가 자동으로 요약과 키워드를 붙인다.

"수집물"이 아니라 "아이템"으로 부르는 이유가 있다. 폴더 감시로 자동 들어온 것은 사용자가 "수집"한 게 아니다. 출처와 무관하게 풀에 있는 모든 단위가 아이템이다.

노트(Document). 사용자가 생각을 엮는 공간이다. 리치텍스트로 아이템을 끌어오고 자기 생각을 덧붙인다. 무겁다 — loro CRDT 기반이라 실시간 협업과 오프라인 병합이 된다. 코드에서는 Document이지만 UI에서는 "노트"라고 부른다. "메모"는 행위 이름("메모를 적다")으로만 쓰고, 결과물은 "노트"로 구분한다.

폴더(Folder). 정리 단위다. 트리 구조(parent_id)로 중첩할 수 있다. 5장에서 "과거를 정리하는 도구"라고 했다 — 이미 수집한 것들을 끌어다 넣는다.

세션(Session). 시간+주제로 묶인 수집 묶음이다. 5장에서 "미래를 향한 도구"라고 했다 — "지금부터 이 주제야"를 선언하면 앞으로 수집하는 것들이 자동으로 담긴다. 폴더와 다른 점이 세 가지다. 시작/종료 시각이 있고, AI가 자동으로 만들 수 있고, 하나의 아이템이 여러 세션에 속할 수 있다. 닫혀도 연결이 살아있다 — 닫힌 컨테이너가 아니라 열린 맥락 레이어다.

아이템 임베드(ItemEmbed). 아이템이 노트 안에 참조되는 관계다. 사용자에게는 "노트에 끌어온 아이템"으로 보인다. 아이템을 삭제해도 노트에서 참조가 깨지지 않도록 soft delete를 쓴다.


### 행위

사용자가 하는 일과 정보에 일어나는 일, 두 시점이 있다.

사용자가 하는 일은 세 가지다(5장). 수집(바깥에서 안으로 가져온다), 검토(쌓인 것을 훑고 판단한다), 메모(아이템을 엮어 생각을 만든다). 동시에 일어나되 비율이 달라진다.

정보에 일어나는 일은 정보 흐름으로 설명한다(5장). 들어옴, 쌓임, 걸러짐, 엮임, 나감. 선형이 아니라 순환이다.

앱이 제공하는 기능은 9개다(1장). 수집, 정리, 메모, 검색, AI, 협업, 동기화, 공유, 창 관리. 세 행위가 "왜 하는가"라면, 9개 기능은 "뭘로 하는가"다. 매핑이 1:1이 아니다 — 검색은 수집에도 쓰이고, 검토에도 쓰이고, 메모에도 쓰인다.


### 상태

데이터 상태와 앱 상태가 있다.

데이터 상태는 동기화와 관련된다.

동기화됨. 서버와 로컬이 같다.

로컬 전용. sync_file이 꺼진 바이너리다. 다른 기기에서 "이 아이템은 {기기명}에만 있음"으로 보인다.

오프라인 대기. 변경됐는데 아직 서버에 못 올린 것이다. 온라인 복귀 시 큐에서 순서대로 전송한다.

삭제됨. soft delete다. 노트에서 "[삭제된 아이템]"으로 표시한다.

앱 상태는 런타임에 존재한다. 활성 맥락(지금 수집 대상으로 지정된 폴더나 세션 — 5장에서 정의), 깊이(감시/캡처/포스트잇/몰입 — 사용자의 현재 몰입도, 데이터에 저장되지 않는다).


### 설계 어휘

코드나 UI에 직접 쓰이지 않지만, 팀이 기능을 설계하고 판단할 때 쓰는 내부 언어다.

정보 흐름(5장). 정보의 생애주기. 들어옴→쌓임→걸러짐→엮임→나감. 순환한다.

깊이 모델(5장). 사용자 몰입도의 네 단계. 감시(앱이 알아서 수집)→캡처(1~2초 수집)→포스트잇(옆에 띄워두고 작업)→몰입(풀 앱). 전환 트리거와 역방향이 있다.

걸러짐 3층(5장). 자동(AI), 암묵적(사용 패턴), 명시적(사용자 판단). 자동과 암묵적이 명시적 없이도 충분해야 한다.

의도 보존 3층(5장). 자동(URL, 타임스탬프), 추론(AI 요약, 키워드), 선택(한 줄 메모). 마찰이 0이거나 최소다.

무게(5장). 아이템의 중요도 신호. 열림 횟수, 별 표시, 노트 참조 횟수를 합쳐서 검색과 연결 제안의 근거로 쓴다.

네 원칙(6장). 끊기지 않게, 시키지 않게, 잊지 않게, 기다리지 않게. 충돌 시 이 순서로 판단한다.

Flux의 개념은 다섯 엔티티(아이템, 노트, 폴더, 세션, 아이템 임베드), 세 행위(수집, 검토, 메모), 아홉 기능, 네 상태, 여섯 설계 어휘로 구성된다.


## 8. 기능 범위

9개 기능(1장)이 각각 어디까지 하고 어디서 멈추는지를 정한다. "하는 것"은 v1에서 구현한다. "하지 않는 것"은 의식적으로 뺀 것이다 — 못 하는 게 아니라 안 하는 것이다.

9개 기능에는 레이어가 있다. 핵심(수집, 정리, 메모, 검색) → 강화(AI, 동기화, 창 관리) → 확장(협업, 공유). 1장의 중심 루프가 핵심이고, 나머지가 각 단계를 강화하거나 확장한다. 핵심 레이어가 완전해야 강화와 확장을 쌓을 수 있다.

구현도 이 순서를 따른다. 먼저 수집·정리·메모·검색이 한 플랫폼(데스크톱)에서 끊김 없이 돌아야 한다. 다음으로 AI 자동 요약과 동기화를 붙여서 모바일 수집→데스크톱 활용 흐름을 잇는다. 마지막으로 협업과 공유를 얹는다. 각 단계에서 3장의 가설을 검증하고, 통과하면 다음 레이어로 넘어간다.

개인 기능을 먼저 만드는 이유가 있다. 수집·검토·메모가 개인에게 먼저 가치를 증명해야 협업이 의미가 있다. 김성수 대표님이 "협업 기능을 만들면 쓰겠다"고 했지만, 개인 흐름이 안 되면 협업을 얹어도 쓸 이유가 없다. 협업이 부차적이라는 뜻이 아니다 — 수집+AI 정리+메모+협업이 한 앱에 있는 것이 Flux의 포지셔닝이다(9장). 다만 쌓는 순서가 핵심→확장이다.

v1에 9개 기능 전부와 세 플랫폼(데스크톱, 모바일, 웹)이 들어간다. 범위가 넓다. 이유가 있다 — 5장의 세 행위(수집, 검토, 메모)가 기기를 넘나들기 때문이다. 폰에서 수집하고 노트북에서 검토하고 메모하는 흐름이 끊기면 핵심 가치가 깨진다. 협업과 공유도 같은 이유다. 혼자 엮은 생각을 동료에게 넘길 때 앱 밖으로 나가면 흐름이 끊긴다. 다만 각 기능의 깊이를 조절해서 범위를 관리한다 — 협업은 "동시 편집+댓글"까지만, 공유는 "링크+내보내기"까지만.


### 수집

하는 것. 데스크톱에서는 브라우저 확장으로 Alt+우클릭, 드래그앤드롭 수집. 모바일에서는 공유 시트(Share Extension), 카메라, 클립보드 감지. 링크, 이미지, 텍스트 하이라이트, 스크린샷, 클립보드, 음성 메모. 메타데이터(제목, URL, 파비콘, 출처 앱, 타임스탬프) 자동 저장. AI가 자동으로 메타데이터를 보강한다(→AI 참조). 100ms 안에 끝나서 흐름이 안 끊긴다.

하지 않는 것. 웹페이지 전체 아카이빙(Pocket, Instapaper 영역). 동영상 파일 자체 저장(링크만 저장). RSS 피드 자동 수집. 이메일 연동.


### 정리

하는 것. 폴더 트리(중첩 가능). 세션(시간+주제 묶음, AI 자동 생성 가능). 정렬(최신순, 오래된순). 보기 옵션(그리드, 벽돌, 양쪽 정렬, 리스트). 무게 — 열림 횟수, 별 표시, 노트 참조 횟수를 합쳐서 검색과 연결 제안의 근거로 쓴다(7장). 수집 시점에 분류하지 않는다 — AI는 메타데이터(요약, 키워드)만 자동으로 붙이고, 폴더 배치는 활성 맥락이 있으면 거기, 없으면 inbox로 간다. 분류는 사용자가 검토하면서 자연스럽게 일어난다.

하지 않는 것. 명시적 태그 시스템. 자동 중복 제거(같은 URL이라도 다른 맥락에서 수집했을 수 있다). 복잡한 필터 조합(속성 A이고 B이면서 C가 아닌 것).


### 메모

하는 것. 리치텍스트 편집(loro CRDT 기반). 아이템을 노트로 드래그해서 임베드. 노트 안에서 다른 노트로 링크. 슬래시(/) 커맨드. 텍스트 서식(크기, 볼드, 이탤릭, 밑줄, 색상). 이미지 삽입. 하이퍼링크. 체크리스트.

하지 않는 것. 스프레드시트, 데이터베이스 뷰(Notion의 테이블/보드/캘린더). 코드 실행. 수식 계산. 위키 링크([[]])와 백링크 그래프(Obsidian 영역). 노트 간 연결은 명시적 링크와 AI 연관 제안으로 대체한다 — 자동 그래프 시각화는 하지 않는다.


### 검색

하는 것. 키워드 검색(제목, 본문, AI 요약, 키워드 대상). 의미 기반 검색(유의어 포함). 무게가 높은 항목을 우선 표시한다(7장). AI가 맥락을 고려해서 관련 아이템과 노트를 함께 제안.

하지 않는 것. 불리안 검색(AND/OR/NOT 연산자). 정규식 검색. 외부 웹 검색(앱 안의 데이터만 검색).


### AI

하는 것. 수집 시 자동 요약(1~3줄)과 키워드(3개) 생성 — 묻지 않고 자동 적용한다. 세션 자동 생성. 채팅 인터페이스로 수집한 정보 기반 대화(RAG). 모델 선택(Openrouter). 음성 대화(TTS/STT). 링크 수집 시 전체 페이지가 아니라 사용자의 활성 맥락에 맞는 요소만 추출해서 미리보기로 보여준다 — 옷 관련 폴더에 쇼핑몰 링크를 넣으면 상의 셔츠 이미지만 뽑아서 보여주는 식이다. 2장의 보편적 수집 흐름에서 3단계(포착)의 마찰을 줄이는 방향이다.

하지 않는 것. 자율 에이전트(사용자 대신 수집하거나 정리를 실행하는 것). 이미지 생성. 코드 생성/실행. AI의 모든 행위는 제안이다 — 실행은 사용자가 한다.


### 협업

하는 것. 초대 기반 동등 편집 — 노트 소유자가 초대한 사람은 모두 같은 편집 권한을 갖는다. 실시간 동시 편집(노트). loro CRDT로 충돌을 자동 해소한다. 커서 색상 구분. 프로필 표시. 인라인 채팅(슬래시로 호출). 댓글.

하지 않는 것. 역할 기반 권한 관리(읽기/쓰기/관리자 분리). 버전 히스토리 비교(diff 뷰). 워크플로우 자동화(승인 프로세스, 알림 규칙).


### 동기화

하는 것. 기기 간 자동 동기화(데스크톱, 모바일, 웹). 오프라인 작업 후 온라인 복귀 시 자동 병합. 로컬 전용 아이템(동기화 안 하는 바이너리 선택 가능).

일반 동기화는 배치로 처리한다 — 변경을 모아뒀다가 보낸다. 협업 모드에서는 별도 실시간 채널(WebSocket)을 열어서 즉시 반영한다. 두 경로가 공존한다.

하지 않는 것. 선택적 동기화(이 폴더만 이 기기에). P2P 동기화(서버 경유).


### 공유

하는 것. 노트 링크 공유(읽기 전용). 링크를 받은 사람을 편집자로 초대하면 협업으로 전환된다(→협업). PDF/Markdown 내보내기.

하지 않는 것. 퍼블리싱(블로그처럼 공개 페이지 생성). 소셜 피드. 템플릿 마켓플레이스.


### 창 관리

하는 것. 포스트잇 모드(투명 창, 항상 위). 분할 뷰(최대 4분할, 프리셋 제공). 사이드바 토글과 리사이즈. 탭 관리(재정렬, 핀 고정). 레이아웃 상태 자동 저장/복원.

하지 않는 것. 멀티 윈도우(독립 창 여러 개 — 포스트잇은 예외). 커스텀 테마 에디터. 플러그인/확장 시스템.


### 경계 원칙

"하지 않는 것"을 정할 때 6장의 네 원칙과 v1 우선순위로 판단했다.

명시적 태그를 뺀 이유 — 태그를 붙이는 행위가 사용자에게 뭔가를 시킨다. 세션이 사실상 태그의 역할을 한다(다대다 관계 — 하나의 아이템이 여러 세션에 속할 수 있다). 차이는 세 가지다. 세션에는 시간 맥락(시작/종료)이 있고, AI가 자동으로 만들 수 있고, 이름을 사용자가 안 붙여도 된다. "태그를 뺀 것"이 아니라 "태그를 시간 맥락이 있는 자동 생성 가능한 형태로 대체한 것"이다.

불리안 검색을 뺀 이유 — 의미 기반 검색이 있으면 AND/OR를 직접 조합할 필요가 줄어든다. 복잡한 쿼리 문법은 흐름을 끊는다.

자율 에이전트를 뺀 이유 — AI가 사용자 대신 수집하거나 정리를 실행하면 예측 불가능해진다. AI의 역할은 메타데이터 자동 부착(요약, 키워드)과 연결 제안에 한정한다. 보여주되 묻지 않고, 실행하지 않는다. 틀리면 사용자가 검토할 때 고친다.

플러그인 시스템을 뺀 이유 — 네 원칙이 아니라 v1 우선순위다. 확장성은 가치가 있지만 핵심 흐름의 완성도가 먼저다. 플러그인은 핵심이 단단해진 뒤에 열어도 늦지 않다.


## 9. 차별점

기존 도구들은 각자의 영역에서 잘 작동한다. 문제는 영역 사이에서 흐름이 끊긴다는 것이다. Flux의 차별점은 개별 기능의 우월이 아니라 흐름의 연결에 있다.


### 경쟁 지형

네 부류가 있다.

수집 특화 — Readwise, Eagle, mymind, Raindrop. 수집은 강하지만 수집한 뒤가 약하다. 모은 것을 엮어서 생각을 만드는 흐름이 없다. 사용자가 수집한 뒤 Notion이나 Obsidian으로 옮겨야 한다. 옮기는 순간 흐름이 끊긴다.

AI 통합 수집 — Fabric. 가장 직접적인 경쟁자다(2장). 수집도 강하고 AI 자동 정리, 시맨틱 검색, Explore 모드(관계 탐색), 실시간 협업까지 있다. 수집 특화 도구보다 범위가 넓다. Flux와의 차이: Fabric은 클라우드 기반이라 오프라인이 안 되고 속도가 서버에 의존한다. "이미 저장된 것 사이에서 관계를 보여주는" 수동적 발견이지, 메모를 쓰면서 자료를 끌어와 연결하는 능동적 엮기는 약하다(2장 6층).

올인원 — Notion, Obsidian, Evernote. 정리와 쓰기는 강하지만 수집이 약하다. 웹에서 뭔가를 가져오려면 복사-붙여넣기를 반복하거나 별도 클리퍼를 설치해야 한다. Notion은 느리고(사용자 피드백), Obsidian은 협업이 없다(사용자 피드백).

AI 검색 — Recall, Karakeep. 검색은 강하지만 수집과 쓰기가 빈약하다. AI가 찾아주는 건 좋은데 그걸로 뭘 할 수 있는 공간이 없다.


### Flux가 다른 점

다섯 가지다.

수집→정리→쓰기가 앱 안에서 끊기지 않는다. 5장의 세 행위(수집, 검토, 메모)가 한 공간에서 일어난다. 다른 도구에서는 수집→정리→쓰기가 최소 두 앱을 거친다. Flux에서는 한 앱 안에서 끝난다.

100ms 안에 끝나는 수집. 데스크톱에서 Alt+우클릭, 모바일에서 공유 시트. 수집하는 동안 지금 하던 일에서 눈을 뗄 필요가 없다. 대부분의 도구는 수집을 위해 앱을 전환하거나 복사-붙여넣기를 반복해야 한다. 0.5초의 전환이 23분의 몰입을 파괴한다(글로리아 마크 연구).

5장의 깊이 모델이 UI로 구현된다. 감시(앱을 안 쓰고 있어도 폴더 감시로 수집), 캡처(Alt+우클릭 1~2초), 포스트잇(옆에 띄워두고 작업), 몰입(풀 앱). 다른 도구는 "열거나 안 열거나" 두 상태뿐이다. 포스트잇 모드는 초기 사용자 피드백에서도 핵심 차별점으로 꼽혔다.

수집하면 AI가 요약과 키워드를 자동으로 붙인다. 묻지 않는다. 틀리면 나중에 검토할 때 고친다. mymind처럼 완전 자동이되, Obsidian처럼 사용자가 원하면 직접 고칠 수 있다. 7장의 걸러짐 3층(자동→암묵적→명시적)이 이 설계의 근거다.

Obsidian은 로컬이지만 협업이 없다. Notion은 협업이 있지만 느리다(클라우드 의존). Flux는 loro CRDT로 로컬에서 즉시 반응하면서 협업도 된다. 오프라인에서 작업하고 온라인 복귀 시 자동 병합한다.

수집+AI 정리+메모+협업이 한 앱에 있다. 수집+AI 정리를 하는 앱은 많다(mymind, Fabric, Raindrop). 메모+협업을 하는 앱도 많다(Notion, Obsidian). 하지만 수집한 자료를 AI가 정리하고, 그걸 메모로 엮고, 팀과 함께 쓰는 것까지 한 앱에서 끊기지 않게 되는 도구는 없다. 각 기능의 개별 품질이 아니라, 이 조합이 한 공간에서 끊기지 않는 것이 Flux의 포지셔닝이다.


### 차별점이 아닌 것

Flux는 Notion을 대체하지 않는다. 프로젝트 관리, 데이터베이스, 위키는 하지 않는다(8장). Obsidian의 지식 그래프도 하지 않는다. Eagle의 대용량 에셋 관리도 하지 않는다.

Flux는 "수집한 것을 엮어서 생각을 만드는 흐름"에만 집중한다. 이 흐름이 끊기지 않는 것이 유일한 약속이다.


## 10. 트레이드오프

모든 선택에는 포기가 따른다. 여기서 정리하는 건 기술 트레이드오프(스택, 아키텍처)가 아니라 제품 트레이드오프다 — 사용자가 경험하는 수준의 선택과 포기.


### 친숙함을 선택하고 독창성을 포기했다

VS Code 레이아웃과 Chrome 탭 패턴을 그대로 쓴다. 사용자가 첫날부터 쓸 수 있다. 대신 "Flux만의 혁신적 UI"는 없다. 코어는 익숙하게, 혁신은 가장자리에서 한다 — AI 자동 요약, 깊이별 인터페이스, 세션 같은 것들이 가장자리 혁신이다.

얻은 것 — 학습 곡선 제로, 즉각적 생산성, 근육 기억 활용.
포기한 것 — 독창적 UX, 브랜드 차별화를 UI로 하는 것.
근거 — 6장 "끊기지 않게". 새 UI를 배우는 것도 흐름을 끊는다.


### 단순함을 선택하고 깊이를 포기했다

각 기능의 깊이를 조절해서 v1 범위를 관리한다(8장). 메모는 리치텍스트까지만 — 스프레드시트, 데이터베이스 뷰는 없다. 정리는 폴더+세션까지만 — 태그, 복잡한 필터는 없다. 협업은 동시 편집+댓글까지만 — 권한 관리, 워크플로우 자동화는 없다.

얻은 것 — 핵심 흐름의 완성도, 빠른 출시, 낮은 복잡도.
포기한 것 — 파워 유저를 위한 고급 기능, Notion급 유연성.
근거 — 6장 "시키지 않게". 기능이 많으면 사용자에게 선택을 시킨다. 8장의 기능 레이어에서 핵심이 완전해야 강화와 확장을 쌓을 수 있다.


### 자동을 선택하고 통제를 포기했다

AI가 요약과 키워드를 자동으로 붙인다. 묻지 않는다. 사용자는 수집만 하면 나머지가 붙는다. 대신 "이 키워드 말고 저 키워드로 해줘"라는 세밀한 통제는 제한적이다. 틀리면 검토할 때 고칠 수 있지만, AI의 기준 자체를 사용자가 커스터마이징하는 건 하지 않는다.

얻은 것 — 수집 후 정리 부담 제거, 마찰 최소화.
포기한 것 — AI 동작의 세밀한 커스터마이징.
근거 — 6장 "시키지 않게" + "기다리지 않게". AI 설정을 만지는 것도 시키는 것이다.


### 흐름을 선택하고 완결성을 포기했다

수집→정리→쓰기 흐름에 집중한다. 그 흐름 바깥의 완결성은 포기한다. 완성된 노트를 PDF로 내보낼 수는 있지만, 퍼블리싱은 하지 않는다. 프로젝트 관리는 하지 않는다. 데이터 분석은 하지 않는다. Flux 안에서 모든 것을 끝내는 올인원이 아니라, Flux에서 생각을 만들고 다른 도구로 넘기는 구조다.

얻은 것 — 명확한 정체성, 핵심 흐름의 품질.
포기한 것 — 올인원의 편리함, "이 앱 하나면 다 된다"는 약속.
근거 — 9장 "차별점이 아닌 것". 모든 것을 하려다 아무것도 잘 못 하는 도구가 되지 않는다.


### 로컬을 선택하고 즉시 접근을 포기했다

핵심 기능은 로컬에서 작동한다. 네트워크 없이도 수집, 정리, 검색, 메모가 된다. 대신 새 기기에서 처음 열면 동기화가 끝날 때까지 전체 데이터에 접근할 수 없다. 클라우드 네이티브(Notion)는 아무 브라우저에서 바로 열리지만, Flux는 앱 설치와 초기 동기화가 필요하다.

얻은 것 — 즉시 반응(0ms), 오프라인 작업, 데이터 주권.
포기한 것 — 아무 기기에서 즉시 접근, 설치 없는 사용.
근거 — 6장 "기다리지 않게". 매번 쓸 때 100ms를 보장하려면 로컬이 필요하다. 초기 동기화는 한 번만 기다린다.


### 포기하지 않는 것

어떤 트레이드오프에서도 양보하지 않는 원칙이 있다.

흐름 연속성 — 하던 일을 멈추게 하는 기능은 넣지 않는다. 모달 다이얼로그, 필수 설정, 강제 업데이트 같은 것.

100ms 응답 — 사용자 행위에 대한 피드백이 100ms를 넘기면 설계를 다시 한다. 느린 기능보다 없는 기능이 낫다.

데이터 무결성 — 사용자의 데이터를 잃지 않는다. soft delete, 자동 백업, 충돌 시 양쪽 보존.

이 세 가지와 충돌하는 기능은 넣지 않는다. 8장의 "하지 않는 것"은 이 원칙을 지키기 위한 결과이기도 하다.
