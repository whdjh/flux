# 요구사항

## 배경

정보를 다루는 사람은 하루 평균 300회 작업을 전환한다. 작업 전환 후 원래 작업으로 복귀하는 데 평균 23분 15초가 걸리고(Gloria Mark 2008, CHI), 11.5초간 인지 저하가 지속된다(Task Switching 2025). 하루 300회 전환은 57.5분의 인지 저하 시간이다.

전환이 발생하는 이유는 정보 도구가 파편화돼 있기 때문이다. 북마크는 북마크 앱, 메모는 메모 앱, 스크린샷은 사진첩, 링크는 카톡 나에게 보내기. 수집하는 순간에 흐름이 끊기고, 나중에 활용하려고 열면 "왜 저장했지?"가 된다.

기존 도구의 한계는 한쪽만 강한 것이다. 북마크 앱은 메모가 안 되고, 메모 앱은 수집이 약하고, PKM 도구는 정리에 시간이 너무 든다. Notion은 "올인원"을 시도했지만 속도가 느려서 수집 흐름에 못 들어왔다.

Flux는 수집·정리·메모·검색·AI·협업·동기화·공유·창 관리 9개 기능을 한 흐름으로 엮는다. 도구 전환이 사라지면 몰입이 이어진다. 전체 맥락은 `essences/앱-재정의.md` 참고.

## 사용자

직군이 아니라 행동 패턴으로 정의한다. 다음 세 조건을 모두 충족하면 핵심 타겟이다.

1. 정보를 일상적으로 수집한다 (안테나가 켜져 있다)
2. 현재 여러 도구에 흩어져 있다
3. 수집한 것으로 결과물을 만들거나, 만들고 싶어한다 (활용 의도가 있다)

동기는 두 갈래가 한 사람 안에 공존한다. 업무 중에는 기획서를 쓰며 레퍼런스를 찾고(생산성), 일상에서는 간판·영화·음악에서 영감을 모은다(호기심). "일할 때만 쓰는 도구"가 아니라 "생각할 때마다 쓰는 도구"다.

수집은 모바일에서, 활용은 데스크톱에서 일어나는 패턴이 지배적이다. 멀티 디바이스가 전제다.

타겟이 **아닌** 사람: 이미 한 도구에 만족하는 사용자, 얕은 작업만 하는 사용자, 협업만을 위해 쓰는 사용자, 수집 습관 자체가 없는 사용자.

상세 페르소나와 감정 궤적은 `essences/앱-재정의.md` 4장, `essences/유저리서치/페르소나-메모.md` 참고.

## 핵심 요구사항

우선순위는 사용자 경험 순이 아니라 구현 순이다. 코어 루프(수집→정리→메모→검색)가 막히면 나머지가 무의미하다.

| 우선순위 | 요구사항 | 상세 |
|:---:|---|---|
| P0 | 수집 | 링크·이미지·텍스트·스크린샷·클립보드·음성을 흐름 끊김 없이 저장. 모바일 공유 시트, 웹 브라우저 확장, 데스크톱 클립보드/폴더 감시, 전역 단축키 팝업 |
| P0 | 자동 정리 | 수집 순간에 AI가 요약·키워드·출처를 자동 부착. 사용자는 저장만, 정리는 프로그램이 |
| P0 | 메모 | 리치텍스트 에디터로 아이템을 드래그 임베드, 노트 간 링크, 분할뷰. loro CRDT 기반 |
| P0 | 검색 | 키워드(FTS5) + 의미(AI) 혼합. 관련 아이템 자동 추천 |
| P0 | 동기화 | 모바일/데스크톱/웹 간 실시간 반영. 오프라인 작업 후 자동 병합 |
| P1 | AI 추천 | 수집한 항목 간 연결 제안, 분류 제안. 실행은 사용자 |
| P1 | 창 관리 | 포스트잇 모드(always on top), 분할뷰, 레이아웃 저장 |
| P1 | 협업 | 노트 공동 편집, 초대 기반, 동등 권한 |
| P2 | 공유 | 읽기 전용 링크, PDF/Markdown 내보내기 |

9개 기능은 중심 루프(수집→정리→메모→검색)를 나머지가 강화하는 구조다. 관계도는 `essences/앱-재정의.md` 1장 참조.

## 제약 조건

| 분류 | 내용 |
|------|------|
| 팀 | 2인 (이주훈·준영) |
| 일정 | MVP 2~3개월, 정식 베타 6개월 |
| 플랫폼 순서 | Web(Next.js) → Desktop(Tauri) → Chrome Extension → iOS(RN Expo) → Android(RN Expo) |
| 핵심 엔진 | loro CRDT (Rust 네이티브). 이것 때문에 서버도 Rust(Axum)로 고정 |
| 로컬 우선 | 모든 쓰기는 로컬 SQLite에 먼저. 서버 동기화는 백그라운드 |
| 예산 | 외부 서비스 비용 최소화 (Supabase Auth 제거, R2 이그레스 0) |

플랫폼 우선순위 근거는 `docs/스택.md` "플랫폼 우선순위" 섹션 참고. 초기 Rust 기반 개발 전략은 `docs/essences/아키텍처/구-전략-Rust.md`에 역사적 기록으로 보존 (현재는 TypeScript 모노레포로 전환).

## 비기능 요구사항

| 영역 | 기준 |
|------|------|
| 성능 — 수집 응답 | p95 < 100ms (가설 7의 핵심 베팅) |
| 성능 — AI 요약 | 2초 이내 |
| 성능 — 에디터 입력 | 60fps (16ms 이내) |
| 가용성 | 오프라인 완전 동작. 네트워크 복귀 시 자동 병합 |
| 보안 — 인증 | argon2 + JWT 자체 구현 |
| 보안 — 데이터 격리 | 쿼리 레벨 `WHERE user_id = $N` 강제 |
| 보안 — 외부 AI | 사용자 데이터는 OpenRouter 프록시를 통해서만 전송. 원문 저장 없음 |
| 확장성 — 동기화 | InMemoryBroadcaster → Redis pub/sub (단일 서버 → 수평 확장) |
| 확장성 — 저장 | R2 버킷 분리, 사용자별 용량 제한 (storage_used 추적) |
| 사용성 | 한국어 기본, 영어 확장 |
| 접근성 | 키보드 네비게이션 전체 지원, 스크린 리더 WCAG 2.1 AA |

## 메트릭

제품이 작동하는지 판별하는 지표. 개별 기능 KPI와 별개로 제품 전체 건강을 본다.

| 메트릭 | 목표 | 근거 |
|------|------|------|
| 일간 수집 건수 | 지속 증가 | 수집 없으면 나머지 무의미 |
| 주간 활성 사용자(WAU) | 베타 30일 리텐션 40% 이상 | "생각할 때마다 쓰는 도구"는 주 단위가 자연스러움 |
| 임계점 도달률 | 가입 후 60일 내 30% | 가설 6(200개 축적) 검증 |
| 검토 비율 | 수집 후 30일 내 재열람 50% 이상 | 수집만 하고 안 보면 카톡 나에게 보내기와 동일 |
| 30일 리텐션 | 임계점 도달 그룹 2배 이상 | 가설 6 전환점 검증 |

가설과 검증 계획 전체는 `essences/앱-재정의.md` 3장 참고.
