# 아키텍처

docs/essences/아키텍처/의 Electron 기반 구조는 초기 보일러플레이트 기준이다. 스택이 Rust(Axum) + Next.js + Tauri + RN Expo + loro + SQLite로 바뀌면서 아키텍처를 새로 설계한다.


## 전체 구조

```
┌─────────────────────────────────────────────────────┐
│  클라이언트                                          │
│                                                      │
│  Web (Next.js)      ←→ loro (WASM) ←→ SQLite (로컬) │
│  Desktop (Tauri)    ←→ loro (WASM) ←→ SQLite (로컬) │
│  Mobile (RN Expo)   ←→ loro (JSI)  ←→ SQLite (로컬) │
│                │                                     │
│                │ CRDT delta (binary)                  │
└────────────────┼─────────────────────────────────────┘
                 │ WebSocket
┌────────────────┼─────────────────────────────────────┐
│  서버 (Axum)   │                                      │
│                ▼                                      │
│  WebSocket ─→ 동기화 엔진 ─→ PostgreSQL (영구 저장)   │
│                │                                      │
│          Broadcaster (trait)                          │
│                │                                      │
│          다른 디바이스로 전파                          │
└──────────────────────────────────────────────────────┘
```

쓰기는 로컬에서 즉시 일어난다(0ms). 클라이언트가 loro 문서에 반영하고 SQLite에 저장한다. 백그라운드로 서버에 WebSocket 전송한다. 읽기도 SQLite에서 바로 읽는다. 네트워크 불필요. 웹/데스크톱은 WASM, 모바일은 JSI로 loro에 접근한다.

동기화는 서버가 CRDT delta를 받아서 PostgreSQL에 저장하고, Broadcaster를 통해 같은 유저의 다른 디바이스에 전파한다. 충돌 해소는 loro CRDT가 자동 처리한다. 서버는 merge만 하고 판단하지 않는다.

멀티 디바이스 전파는 trait으로 추상화한다. 초기에는 tokio::broadcast(인메모리)로 구현하고, 수평 확장이 필요할 때 Redis pub/sub으로 교체한다.

```
단일 서버 (초기):     InMemoryBroadcaster (tokio::broadcast, 비용 $0)
수평 확장 시:         RedisBroadcaster (Redis pub/sub)
```


## 인증

자체 구현. Axum 서버가 회원가입, 로그인, JWT 발급을 직접 처리한다. 비밀번호는 argon2로 해싱하고, 로그인 성공 시 JWT를 발급한다. 이후 요청에서 Authorization 헤더의 JWT를 검증하고 user_id를 추출한다. tower 미들웨어 하나로 처리한다.

```
클라이언트 → POST /auth/register (email, password) → argon2 해싱 → DB 저장
클라이언트 → POST /auth/login (email, password) → argon2 검증 → JWT 발급
클라이언트 → Axum (Authorization: Bearer <JWT>) → JWT 검증 → user_id 추출
```

오프라인 인증: 최초 로그인은 온라인 필수다. 이후 JWT를 안전한 저장소(iOS Keychain, Android Keystore)에 저장하고 오프라인에서도 로컬 데이터에 접근한다. JWT 만료 후 온라인 복귀 시 refresh token으로 갱신한다. 동기화는 유효한 JWT가 있을 때만 수행한다.


## 데이터 모델

하이브리드 모델. Item(수집물)과 Document(메모)를 분리하되, Document에서 Item을 참조(embed)한다. 수집은 가볍게(SQLite INSERT, < 100ms), 편집은 무겁게(loro CRDT).

```
Item (수집물)
  - id, user_id
  - type: text | image | link | video | screenshot | clipboard
  - content: 텍스트 본문 또는 파일 경로
  - metadata: { url, title, favicon, source_app }
  - ai: { summary, keywords[] }
  - created_at
  - sync_file: boolean (바이너리 파일 동기화 여부, 기본 false)
  - folder_id (nullable)

Document (메모)
  - id, user_id
  - title
  - crdt_doc: loro binary (리치텍스트 + 임베드 참조)
  - created_at, updated_at
  - folder_id (nullable)

Folder (정리)
  - id, user_id
  - name
  - parent_id (nullable, 트리 구조)

ItemEmbed (참조 관계)
  - document_id, item_id
  - position (문서 내 위치)
```

Item을 삭제해도 Document에서 참조가 깨지지 않도록 soft delete를 쓴다. 삭제된 Item은 "[삭제된 항목]"으로 표시한다.


## 동기화

하나의 WebSocket 연결 위에서 메시지 타입으로 구분한다. Document 동기화를 위해 WebSocket을 이미 유지하고 있으니, Item/Folder 변경도 같은 연결에 태운다.

```
WebSocket 메시지 타입:
  { type: "crdt_delta", doc_id, delta }       ← Document 실시간 동기화
  { type: "item_created", item }               ← Item 생성
  { type: "item_deleted", item_id }            ← Item 삭제
  { type: "folder_updated", folder }           ← Folder 변경
```

멀티 디바이스 전파가 자연스럽다. iPhone에서 Item을 수집하면 서버가 Broadcaster로 Mac에 즉시 전파한다. REST였으면 폴링이나 별도 push가 필요했다.

오프라인 큐도 하나로 통합된다. 오프라인에서 Item 생성, Document 편집, Folder 이동을 했으면 온라인 복귀 시 하나의 큐에서 순서대로 보낸다.

REST API는 초기 로드용이다. 앱 시작 시 Item 목록, Folder 트리, Document 메타데이터를 REST로 가져온다. 이후 실시간 변경은 WebSocket으로 동기화한다.

```
REST API: 초기 로드, 벌크 작업
WebSocket: 실시간 변경 동기화 (CRDT delta + Item/Folder 변경)
```


## 파일 저장소

Cloudflare R2를 쓴다. S3 호환 API라서 기존 SDK가 그대로 동작하고, 다운로드(이그레스) 비용이 0이다. 여러 기기에서 같은 파일을 자주 내려받는 flux에 유리하다.

```
로컬: App 로컬 저장소/{user_id}/{item_id}.{ext}
서버: Cloudflare R2 → bucket: items/{user_id}/{item_id}.{ext}
```

Item type별 저장 전략이 다르다.

```
항상 동기화 (텍스트, 용량 작음):  text, clipboard(텍스트), link
선택적 동기화 (바이너리):        image, screenshot, clipboard(이미지)
선택적 동기화 (대용량):          video(로컬 영상)
URL 참조만:                     video(외부 링크), link
```

텍스트와 메타데이터는 용량이 작으니 항상 동기화한다. 바이너리 파일은 Item의 `sync_file` 플래그로 사용자가 선택한다. 메타데이터는 항상 동기화되므로, 파일이 동기화되지 않은 항목은 다른 기기에서 "이 항목은 {기기명}에만 있음"으로 표시한다.

오프라인 큐에서 보내기 전에 `sync_file` 필터만 추가하면 된다. 아키텍처 변경 없이 정책 레이어로 처리한다.

사용자별 용량 제한을 둔다. 서버에서 `storage_used`를 추적하고 `storage_limit`을 초과하면 업로드를 거부한다. 구체적인 플랜별 용량은 추후 결정한다.


## 도메인 용어

프로젝트 전반에서 사용하는 용어를 정의한다. 코드의 네이밍, UI의 레이블, 문서의 서술이 여기서 통일된다.

### 엔티티

| 용어 | 정의 | 코드명 |
|------|------|--------|
| 아이템 | 저장된 모든 단위. 링크, 이미지, 텍스트, 스크린샷, 클립보드, 음성 메모. 출처와 무관하게 저장되면 아이템이다. | Item |
| 노트 | 사용자가 생각을 엮는 공간. 리치텍스트로 아이템을 끌어오고 자기 생각을 덧붙인다. UI에서는 "노트", "메모"는 행위 이름으로만 쓴다. | Document |
| 폴더 | 정리 단위. 트리 구조(parent_id)로 중첩 가능. | Folder |
| 세션 | 시간+주제로 묶인 수집 묶음. "지금부터 이 주제야"를 선언하면 앞으로 수집하는 것들이 자동으로 담긴다. 폴더와 다른 점이 세 가지다. 시작/종료 시각이 있고, AI가 자동으로 만들 수 있고, 하나의 아이템이 여러 세션에 속할 수 있다. 닫혀도 연결이 살아있다 — 닫힌 컨테이너가 아니라 열린 맥락 레이어다. | Session |
| 아이템 임베드 | 아이템이 노트 안에 참조되는 관계. 사용자에게는 "노트에 끌어온 아이템"으로 보인다. 아이템을 삭제해도 노트에서 참조가 깨지지 않도록 soft delete를 쓴다. | ItemEmbed |

### 행위

사용자가 하는 일과 앱이 제공하는 기능, 두 층위가 있다.

사용자 행위:

| 행위 | 정의 |
|------|------|
| 모으다 | 여러 경로로 정보를 한 곳에 모은다. 경로는 다르지만 행위는 하나다. |
| 다시 보다 | 쌓인 것을 훑고 판단한다. 수동(스크롤)에서 능동(별, 비교)까지 그래디언트. 나머지 두 행위의 촉발제. |
| 쓰다 | 아이템을 엮어 생각을 만든다. 완성된 글이 아니라 중간 결과물까지. |

세 행위는 단계가 아니다. 동시에 일어나되 비율이 달라진다.

앱 기능. 세 행위가 "왜 하는가"라면 9개 기능은 "뭘로 하는가"다. 매핑이 1:1이 아니다.

| 기능 | 정의 |
|------|------|
| 수집 | 사용자가 마주친 정보(링크, 이미지, 텍스트, 스크린샷, 음성 메모)를 흐름을 끊지 않고 저장한다. |
| 정리 | 저장된 아이템에 구조를 부여한다. 폴더(이미 수집한 것을 분류), 세션(앞으로 수집할 것의 대상 지정), AI 분류 제안. |
| 메모 | 노트를 만들고 편집한다. 아이템을 드래그해서 임베드하고, 노트 간 링크로 연결한다. |
| 검색 | 저장된 아이템과 노트를 키워드 또는 의미로 찾는다. AI가 관련 항목을 함께 제안한다. |
| AI | 수집된 정보를 자동으로 요약하고 분류를 제안한다. 모든 행위는 제안이며 실행은 사용자가 한다. |
| 협업 | 노트를 여러 사람이 동시에 편집한다. 초대 기반, 동등 권한. |
| 동기화 | 기기 간 데이터가 같은 상태를 유지한다. 오프라인 작업 후 자동 병합. |
| 공유 | 노트를 앱 밖으로 내보낸다. 읽기 전용 링크, 편집자 초대, PDF/Markdown 내보내기. |
| 창 관리 | 앱의 레이아웃과 창 형태를 조절한다. 포스트잇 모드, 분할 뷰, 레이아웃 저장. |

### 상태

| 용어 | 정의 |
|------|------|
| 동기화됨 | 서버와 로컬이 같다. |
| 로컬 전용 | sync_file이 꺼진 바이너리. 다른 기기에서 "이 아이템은 {기기명}에만 있음"으로 표시. |
| 오프라인 대기 | 변경됐는데 아직 서버에 못 올린 것. 온라인 복귀 시 큐에서 순서대로 전송. |
| 삭제됨 | soft delete. 노트에서 "[삭제된 아이템]"으로 표시. |

앱 상태는 런타임에만 존재한다.

| 용어 | 정의 |
|------|------|
| 활성 맥락 | 지금 수집 대상으로 지정된 폴더나 세션. |
| 깊이 | 배경/순간/떠있음/몰입. 사용자의 현재 몰입도. 데이터에 저장되지 않는다. |

### 설계 어휘

코드나 UI에 직접 쓰이지 않지만, 기능을 설계하고 판단할 때 쓰는 내부 언어다.

| 어휘 | 정의 |
|------|------|
| 풀 모델 | 정보의 생애주기. 들어옴→쌓임→걸러짐→엮임→나감. 순환한다. |
| 깊이 모델 | 사용자 몰입도의 네 단계. 배경→순간→떠있음→몰입. |
| 걸러짐 3층 | 자동(AI), 암묵적(사용 패턴), 명시적(사용자 판단). 자동과 암묵적이 명시적 없이도 충분해야 한다. |
| 의도 보존 3층 | 자동(URL, 타임스탬프), 추론(AI 요약, 키워드), 선택(한 줄 메모). 마찰이 0이거나 최소. |
| 무게 | 아이템의 중요도 신호. 열림 횟수 + 별 표시 + 노트 참조 횟수. 검색과 연결 제안의 근거. |
| 네 원칙 | 끊기지 않게 > 시키지 않게 > 잊지 않게 > 기다리지 않게. 충돌 시 이 순서. |



## 코드 컨벤션

서버(Rust/Axum) 코드 컨벤션은 `flux-be` 저장소의 `docs/아키텍처.md` 참고. 레이어(handlers → services → db), 에러 처리(AppError), SQL(sqlx::query_as), API 설계, 로깅(tracing) 등.

클라이언트(TypeScript) 코드 컨벤션은 모노레포 규칙으로 별도 정의한다. 현재는 packages/core의 엔티티 타입과 비즈니스 로직, packages/ai의 AI 파이프라인, apps/*의 플랫폼별 코드로 나뉜다. 깃 컨벤션은 루트 `.gitmessage.txt` 참고.
