# 개발 원칙

> "한 세션에 완성하고, 완벽하게 테스트하고, 자신있게 병합한다"

---

## 5가지 핵심 원칙

1. 데모 우선 개발 - demos/에서 실험, features/로 배포
2. 분해 가능한 설계 - 처음부터 쪼갤 수 있게
3. 리프 노드 아키텍처 - 2-4시간 단위로 완성
4. 익숙한 패턴 활용 - 이미 아는 것 사용
5. 사용자 중심 개발 - 데이터로 결정

---

## 1. 데모 우선 개발

실험은 demos/ 폴더에서 자유롭게 하고, 검증이 끝나면 features/로 옮겨 배포합니다.

이렇게 하면 프로덕션 코드를 망치지 않으면서도 아이디어를 빠르게 검증할 수 있습니다. demos/에서는 지저분해도 괜찮습니다. 빠르게 만들어서 실제로 써보고, 제대로 작동하는지 확인하는 게 목적입니다. 검증이 끝나면 깔끔하게 정리해서 features/로 이동합니다.

실전에서는 demos/ 폴더에서 빠르게 프로토타입을 만들고, 실제로 사용해보면서 검증합니다. 품질 기준을 통과하면 features/로 graduation합니다.

---

## 2. 분해 가능한 설계

큰 문제를 처음부터 작은 조각으로 쪼갤 수 있게 설계합니다.

쪼개진 조각들은 각각 독립적으로 의미가 있어야 합니다. 그래야 여러 명이 동시에 작업할 수 있고, 테스트하기도 쉽고, 이해하기도 쉽습니다. 설계할 때부터 "이걸 어떻게 나눌 수 있을까?"를 생각합니다.

경계를 찾으려면 몇 가지 신호에 주목하면 됩니다. UI와 Logic과 Data 이렇게 세 가지로 일단 나눠봅니다. 설명할 때 "그리고(and)"가 들어가면 분리 신호입니다. Mock을 만들 수 있으면 경계가 잘 잡힌 거고, README를 쓸 수 있으면 범위가 명확한 겁니다. 다른 곳에서도 쓸 수 있으면 재사용 가능한 좋은 조각입니다.

---

## 3. 리프 노드 아키텍처

하나의 리프 노드는 2-4시간 안에 완성하고, 테스트 커버리지 90% 이상으로 완벽하게 테스트한 뒤, 자신있게 병합합니다.

이 크기가 중요한 이유는 몰입 상태(flow state)를 유지할 수 있는 시간이기 때문입니다. 한 세션에 시작부터 끝까지 완성할 수 있으면 컨텍스트를 잃지 않고, 품질도 보장되고, 통합할 때 문제가 생기지 않습니다.

리프 노드는 다섯 가지 조건을 만족해야 합니다. 2-4시간 안에 완성할 수 있어야 하고, 다른 리프 노드에 의존하지 않아야 하며, 테스트 커버리지가 90% 이상이어야 합니다. null과 빈 값과 경계값과 에러 조건을 모두 테스트해야 하고, 독립적으로 실행하고 테스트할 수 있어야 합니다.

완성 기준은 명확합니다. "구현 완료했고, 모든 테스트 통과했고, 이제 깨뜨릴 방법이 생각 안 난다" 이 상태가 되면 완성입니다.

---

## 4. 익숙한 패턴 활용

새로운 패턴을 만들지 말고, 사용자가 이미 아는 것을 그대로 씁니다.

VS Code를 쓸 줄 아는 사람은 우리 앱도 바로 쓸 수 있어야 합니다. Chrome에서 탭을 다루던 방식 그대로 작동해야 합니다. Cmd+S를 누르면 저장되고, Cmd+F를 누르면 검색창이 열려야 합니다. 이미 널리 검증된 패턴을 버리고 새로 만들 이유가 없습니다.

구체적으로 보면 VS Code 스타일 3-패널 레이아웃(좌측 탐색, 중앙 콘텐츠, 우측 도구)을 사용하고, Chrome 스타일 탭 시스템(드래그로 순서 변경, 부드러운 애니메이션)을 적용합니다. 표준 키보드 단축키(Cmd+S 저장, Cmd+F 검색, Cmd+W 닫기)를 따르고, 일반적인 패턴(휴지통, 실행 취소, 자동 저장)을 활용합니다.

원칙은 간단합니다. 새로운 패턴 만들기 전에 익숙한 패턴이 있나 확인하고, 있으면 그걸 씁니다.

---

## 5. 사용자 중심 개발

추측으로 만들지 말고, 증거와 데이터로 결정합니다.

"사용자가 이걸 원할 것 같아"가 아니라 "사용자 10명이 테스트했을 때 80%가 이 기능을 썼다"로 말합니다. "이게 느린 것 같아"가 아니라 "평균 280ms인데 목표는 200ms"라고 측정합니다. 그래야 올바른 것을 만들고, 시간을 낭비하지 않습니다.

실천 방법은 네 가지입니다. 조기 테스트는 기능 만들고 6개월 기다리지 말고, 1주마다 사용자와 테스트하는 겁니다. 메트릭 측정은 핵심 여정의 성공률과 완료 시간과 에러율을 측정하는 겁니다. 데이터 결정은 "느린 것 같아"가 아니라 "평균 280ms, 목표 200ms"로 말하는 겁니다. 피드백 순환은 출시하고 피드백을 수집하고 분석하고 개선하고 측정한 뒤 다시 반복하는 겁니다.

## 원칙들이 함께 작동하는 방식

이 원칙들은 따로 떨어진 게 아니라 서로 연결되어 있습니다.

익숙한 패턴으로 demos/에서 빠르게 실험하고, 분해 가능하게 설계한 뒤 리프 노드 단위로 완성합니다. 사용자 중심으로 검증하면서 데모 우선으로 올바른 방향을 찾습니다. 이렇게 하면 빠르면서도 품질 높은 개발이 가능합니다.

실전 워크플로우는 이렇습니다:
```
사용자 조사 → 익숙한 패턴 찾기 → demos/에서 프로토타입
→ 리프 노드로 분해 → 각각 2-4시간에 완성
→ 통합 & 검증 → features/로 graduation
```

---

## 시작하기

실전 워크플로우:

```
1. 데모 생성
   demos/my-feature/ 폴더에 프로토타입 작성
   빠르게 작동하는 코드 우선, 타입이나 테스트는 나중

2. 리프 노드 분해
   DESIGN.md 작성으로 2-4시간 단위 작업 정의
   각 노드가 독립적으로 실행 가능하도록 설계

3. 리프 노드 구현
   각 노드를 완성하면서 테스트 커버리지 90% 이상 달성
   null, 빈 값, 경계값, 에러 조건 모두 검증

4. Graduation
   검증 완료된 데모를 features/ 폴더로 이동
   타입 정의, 에러 처리, 문서화 완성
```

상세 가이드는 [개발 워크플로우](./개발-워크플로우.md)를 참고한다.

---

## 핵심 요약

```
1. 데모 우선: 안전하게 실험하고 자신있게 배포
2. 분해 가능: 처음부터 작게 쪼개기
3. 리프 노드: 한 세션에 완성, 완벽한 테스트
4. 익숙한 패턴: 이미 아는 것 그대로 사용
5. 사용자 중심: 증거와 데이터로 결정
```

최종 목표는 빠르게 만들고, 높은 품질을 유지하며, 개발자는 몰입하고, 사용자는 익숙하게 쓰는 겁니다.
