  # Why VS Code and Chrome?

  ## VS Code 레이아웃을 선택한 이유

  ### 검증된 효율성
  - 4년 연속 Stack Overflow 개발자 선호도 1위
  - 수백만 사용자가 검증한 작업 패턴
  - 정보 계층화에 최적화된 구조

  ### 친숙한 메타포
  - 폴더/파일 구조는 보편적 정리 방식
  - 드래그 앤 드롭은 직관적 상호작용
  - 분할 화면은 비교 작업의 표준

  ## Chrome 탭 시스템을 선택한 이유

  ### 시각적 연속성
  - 200ms 애니메이션은 인지적 최적값
  - 탭 이동 시 시선 추적 가능
  - 컨텍스트 유지에 효과적

  ### 사용자 기대치
  - 65% 브라우저 점유율
  - 탭 인터랙션은 웹의 표준
  - 학습 비용 제로

  3. 아키텍처 결정 기록 (02-decisions/ADR-001-layout-system.md)

  # ADR-001: 3-Panel Layout System

  ## Status
  Accepted (2024-09-15)

  ## Context
  정보 관리 앱에서 사용자는:
  - 파일 트리를 탐색해야 함
  - 메인 콘텐츠를 봐야 함
  - 보조 정보(AI, 메모)가 필요함

  ## Decision
  VS Code 스타일 3-panel 레이아웃 채택:
  - Left: 파일 탐색기
  - Center: 메인 뷰어
  - Right: 보조 패널

  ## Consequences

  ### Positive
  - ✅ 개발자/파워유저에게 친숙
  - ✅ 효율적 공간 활용
  - ✅ 확장 가능한 구조

  ### Negative
  - ❌ 초기 구현 복잡도 높음
  - ❌ 모바일 대응 어려움
  - ❌ 성능 최적화 필요

  ### Risks
  - 너무 개발자 중심적일 수 있음
  - 일반 사용자에게 복잡해 보일 수 있음

  ## Links
  - [VS Code Architecture](https://github.com/microsoft/vscode/wiki/How-to-Contribute)
  - [Related: ADR-003-split-view.md]

  그리고 불필요한 문서가 있는지 봐줘.

  일단 가이드엔 '보일러 플레이트 READEME.md' 의 정보랑 VSCode의 파일 시스템, 분할 시스템, 탭 시스템 + Chrome 탭 재정렬
  애니메이션을 클론 코딩 한 정보까지의 것만 담겨있으면 되겠지? 왜냐면 문서까지도 보일러플레이트거든.

  그리고 문서를 싹 정리해서 README.md 랑 docs/README.md 랑 나머지 문서들도 정리하자. 그리고 COMPONENT_API.md 이런건
  필요하다면 새로 만드는게 나을것 같아서 지웠어, 근데 API를 만들기 시작하기 전까지 미리 만들고 가는건 나쁜것 같아. 기획이
  다 되지도 않았는데, 방향이 달라질지도 모르는데 만들고 가는거니까.

  그리고 Chrome 애니메이션 200ms가 아니라 167ms 아닌지 체크해줘.
