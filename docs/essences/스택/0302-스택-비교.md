# 클라이언트 스택 비교

0216-네이티브-vs-RN.md에서 Swift vs RN을 비교했다. 이주훈이 Next.js + Tauri를 제안하면서 선택지가 넓어졌다. 네 가지를 비교하고 결론을 낸다.


## 배경

이주훈의 판단: RN Web은 SSR이 안 되고, 나중에 Next.js로 전환하면 머리 아프다. 처음부터 Next.js로 웹을 잡고 Tauri로 데스크톱을 래핑하겠다. 모바일은 RN Expo로 나중에.

0216 문서의 우려: loro CRDT가 Rust라서 Swift FFI가 성능 최고다. RN은 매 키 입력마다 왕복이 생긴다.

0216 문서의 우려는 Old Architecture(Bridge) 기준이다. New Architecture(JSI)는 동기 함수 포인터 호출이라 오버헤드가 마이크로초 단위다. 구조가 근본적으로 다르다.

## 성능

60fps 기준 한 프레임이 16ms다. 이 안에 들어와야 타이핑이 매끄럽다.

| 항목 | A. Swift | B. RN 단일 | C. Next.js | D. Next.js + RN |
|---|---|---|---|---|
| 모바일 콜드 스타트 | 200ms | 400-500ms | 800ms+ (WebView) | 400-500ms |
| 모바일 에디터 (loro) | FFI 직결 ~1ms | JSI ~3-5ms | WASM+WebView ~8-15ms | JSI ~3-5ms |
| 모바일 스크롤 (60fps) | 네이티브 | FlashList로 60fps | 웹 스크롤 (떨어짐) | FlashList로 60fps |
| 웹 에디터 (loro) | WASM ~2-3ms | WASM ~2-3ms | WASM ~2-3ms | WASM ~2-3ms |
| 웹 SSR / SEO | React로 가능 | 없음 | Next.js 풀 지원 | Next.js 풀 지원 |
| 데스크톱 에디터 | SwiftUI ~1ms | WASM ~2-3ms | WASM ~2-3ms | WASM ~2-3ms |
| 메모리 (모바일) | 최소 | 중간 (Hermes) | 높음 (WebView) | 중간 (Hermes) |

셋 다 16ms 안에 충분히 들어온다. 사용자가 차이를 느끼기 어렵다. 진짜 병목은 loro 바인딩이 아니라 에디터 렌더링 컴포넌트다.

## 탈락 근거

A(Swift) — 성능 최고지만 2인 팀이 3개 코드베이스를 감당 못 한다. 이주훈이 Swift를 안 하니까 iOS를 준영이 혼자 해야 한다.

B(RN 단일) — 코드 공유 최대지만 웹 품질이 낮다. SSR 없음, SEO 없음, 공유 링크 미리보기 없음. 이주훈이 이 문제를 짚었다.

C(Next.js 단일) — 웹은 최고지만 모바일을 WebView로 래핑하면 치명적이다. 콜드 스타트 800ms+, 스크롤 떨어짐, Share Extension 불가, 오프라인 제한적. "수집 < 100ms"을 못 지킨다.


## 결론

D(Next.js + RN)가 유일한 현실적 선택이다.

- 웹/데스크톱: Next.js + Tauri — SSR, loro WASM, 최고 품질
- 모바일: RN Expo — JSI로 loro 성능 충분, 네이티브급 UX
- 비즈니스 로직: 모노레포(packages/core, packages/ai)로 공유
- 2인 팀이 둘 다 참여 가능

이주훈이랑 최종 확인 후 기준(정한것)/스택.md를 업데이트한다.


## 검증 필요

- loro + RN JSI 에디터 성능 → 프로토타입에서 실측
- Share Extension 등 iOS 네이티브 기능 → RN 네이티브 모듈로 구현 가능한지 검증
- RN 리치텍스트 에디터 선택지 조사 (ProseMirror WebView vs 네이티브 에디터)
