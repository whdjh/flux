# 개발 워크플로우

Demo-First 개발 10단계 실행 가이드다. 전략 배경은 [개발-전략.md](./개발-전략.md) 참고.

## 플로우

```
Step 1: Worktree 생성          (git worktree add)
Step 2: Demo 폴더 생성         (mkdir, DemoIndex 등록)
Step 3: Cursor 창 열기         (cursor)
Step 4: 코드 분석              (/feature-dev --explore)
Step 5: UI 설계                (/frontend-design)
Step 6: 구현                   (/feature-dev --implement)
  ├─ 6-1: 컴포넌트 구현        (개별 기능 단위)
  └─ 6-2: 통합                 (상태 관리, UI 연결)
Step 7: 사용자 검증            (npm start, 브라우저 테스트)
Step 8: 보안 검증              (/security-guidance)
Step 9: 코드 리뷰              (/code-review)
Step 10: 병합 및 정리          (git mv, /commit-commands:commit, git merge, git worktree remove)
```

독립된 작업 환경부터 만든다. git worktree로 demo/{기능} 브랜치를 새 디렉토리에 체크아웃한다. Cursor 창을 연다.

기존 패턴을 분석하고 UI를 설계한다. 뷰를 구현하고 통합한다. Worktree에서 검증한다. 보안과 코드 품질을 확인한다. features/로 이동하고 커밋해서 병합한다.

컨텍스트 사용량이 단계별로 최적화된다. Worktree로 격리하면 125K 코드베이스가 15K로 줄어든다. 환경 설정(Step 1-3)에서 15K를 쓴다. 분석과 설계(Step 4-5)에서 10K로 줄어든다. Docs 구조화로 필요한 문서만 로드하기 때문이다. 구현(Step 6)에서 5K만 쓴다. 하나의 컴포넌트에 집중하기 때문이다. 검증과 통합(Step 7-10)에서 15K로 늘어나지만 베이스라인 20K 안에 머문다. 전체적으로 125K에서 20K로 줄어든다. 84% 감소다.

## Step 1: Worktree 생성

독립된 작업 환경을 만든다.

```bash
git worktree add {workspace-dir}/inbox -b demo/inbox
```

Worktree는 demo/inbox 브랜치를 새 디렉토리에 체크아웃한다. 메인 프로젝트와 완전히 분리된 환경이다. 이 디렉토리에서 작업한 내용은 demo/inbox 브랜치에만 기록된다.

Worktree를 쓰면 컨텍스트가 격리된다. Git Worktree 전략에 따라 메인 프로젝트의 125K 코드베이스 대신 현재 작업(15K)만 로드한다. AI가 관련 없는 코드에 산만해지지 않는다.

## Step 2: Demo 폴더 생성

데모 디렉토리를 만들고 DemoIndex에 등록한다.

```bash
mkdir -p src/demos/inbox
```

Cursor에서 `src/demos/DemoIndex.tsx` 파일을 열어서 demos 배열에 추가한다:

```typescript
{
  title: 'Inbox',
  path: '/demos/inbox',
  status: 'wip'
}
```

DemoIndex.tsx는 데모 페이지 목록을 관리한다. 여기에 등록해야 /demos 페이지에서 새 데모로 이동할 수 있다. status는 'wip' (작업 중) 또는 'complete' (완료)다.

## Step 3: Cursor 창 열기

Worktree 디렉토리를 Cursor에서 연다.

```bash
cursor {workspace-dir}/inbox
```

새 Cursor 창이 열린다. 이 창의 Claude Code는 inbox worktree만 본다. 메인 프로젝트나 다른 worktree 코드는 컨텍스트에 없다. 완전히 격리된 환경이다.

단일 기능 개발이라도 worktree 격리를 추천한다. 컨텍스트가 깨끗하기 때문이다. 병렬 개발 시에는 여러 worktree를 만들고 각각 Cursor 창을 연다. 상세 내용은 [병렬 개발](#병렬-개발) 참고.

## Step 4: 코드 분석

기존 패턴을 찾아서 재사용 가능한 컴포넌트를 확인한다.

```bash
/feature-dev --explore "{재사용할 패턴}"
```

explore는 기존 코드에서 비슷한 구조를 찾는다. 이미 만든 컴포넌트가 있으면 참고한다.

컨텍스트는 10K다. Docs 구조화 전략에 따라 00-시작(5K) + 01-워크플로우(5K)만 읽는다.

## Step 5: UI 설계

UI 레이아웃을 설계한다.

```bash
/frontend-design "{기능} 레이아웃"
```

frontend-design은 UI 레이아웃을 정의한다. 그리드 구조, 간격, breakpoint를 설계한다. VS Code나 Chrome처럼 검증된 디자인 패턴을 활용한다.

## Step 6: 구현

컴포넌트를 구현하고 통합한다.

### Step 6-1: 컴포넌트 구현

각 컴포넌트를 독립적으로 만든다.

```bash
/feature-dev --implement "{컴포넌트A}"
/feature-dev --implement "{컴포넌트B}"
/feature-dev --implement "{컴포넌트C}"
```

하나씩 만들고 바로 확인한다. 문제가 있으면 즉시 수정하고 다음으로 넘어간다.

각 컴포넌트는 5K 컨텍스트만 쓴다. 하나의 컴포넌트에만 집중하기 때문이다.

복잡한 기능(인증, 결제, 보안 로직)을 만들 때는 AI가 자동으로 Codex-Claude Loop를 실행한다. 상세 내용은 [Codex-Claude Loop](#codex-claude-loop) 참고.

### Step 6-2: 통합

상태 관리와 UI 연결 로직을 추가한다.

```bash
/feature-dev --implement "{상태 관리 로직}"
/feature-dev --implement "{UI 연결}"
```

개별 컴포넌트가 완성되면 통합 로직을 만든다. useState나 Zustand로 상태를 관리하고 컴포넌트를 연결한다.

컨텍스트가 15K로 늘어난다. 여러 컴포넌트 코드를 읽어야 상태 관리를 통합할 수 있기 때문이다. Docs 구조화 전략으로 필요한 문서만 로드했기 때문에 작업 공간은 충분하다. 2-3시간이면 작동하는 데모가 완성된다.

## Step 7: 사용자 검증

Worktree에서 개발 서버를 실행한다.

```bash
# {workspace-dir}/{feature}에서 실행
npm start
```

서버가 시작되면 브라우저를 열어서 `http://localhost:3000/demos`로 이동한다. DemoIndex 페이지에서 해당 데모를 클릭한다.

실제로 사용해본다:
- 핵심 기능이 작동하는가?
- 사용자 인터랙션이 자연스러운가?
- 레이아웃이 깨지지 않는가?
- 반응 속도가 괜찮은가?
- 엣지 케이스가 처리되는가?

문제가 있으면 코드를 직접 수정한다. 빠른 수정은 직접 하고, 큰 변경은 다시 구현 단계로 돌아간다.

검증이 완료되면 다음 단계로 넘어간다. 모든 기능이 작동하고, UX가 괜찮고, 성능에 문제가 없어야 한다.

## Step 8: 보안 검증

Electron 앱 특화 보안을 체크한다.

```bash
/security-guidance demos/{feature} --focus electron,ipc
```

체크 항목:
- IPC 통신 (nodeIntegration, contextIsolation)
- XSS 방어 (Content Security Policy)
- 파일 시스템 접근 제어
- 외부 리소스 로딩

Critical/High 취약점이 없어야 통과한다.

## Step 9: 코드 리뷰

자동 리뷰로 품질을 검증한다.

```bash
/code-review demos/{feature}
```

여러 agent가 분석한다:
- 아키텍처 검토
- 성능 분석
- 보안 취약점
- 코드 품질

Confidence 점수 85% 이상이면 통과한다.

## Step 10: 병합 및 정리

features/로 이동하고 커밋해서 병합한다.

### Step 10-1: features 이동

```bash
git mv demos/{feature} features/{feature}
```

### Step 10-2: 커밋

일관된 커밋 메시지로 기록한다.

```bash
# 자동 커밋 메시지 생성 (둘 중 하나)
/commit-commands:commit

# 또는 옵션 지정
/commit --scope {feature} --type feat
```

생성 예시:
```
feat({feature}): Add {feature} demo with {핵심 기능}

- Implement {컴포넌트A, 컴포넌트B, 컴포넌트C}
- Add {통합 로직} component
- Configure {상태 관리} logic

Reviewed-by: code-review (confidence: 92%)
Security-check: PASS (0 critical, 0 high)
```

### Step 10-3: 병합

메인 프로젝트로 병합한다.

```bash
git checkout main
git merge demo/{feature}
```

### Step 10-4: 정리

worktree를 제거한다.

```bash
git worktree remove {workspace-dir}/{feature}
git branch -d demo/{feature}
```

다음 데모로 넘어간다.

## 병렬 개발

2-3개 기능을 동시에 개발할 때는 worktree를 여러 개 만든다. 각 창에서 Step 1-10을 독립적으로 실행한다.

```bash
# 3개 worktree 생성
git worktree add {workspace-dir}/feature-a -b demo/feature-a
git worktree add {workspace-dir}/feature-b -b demo/feature-b
git worktree add {workspace-dir}/feature-c -b demo/feature-c

# 각각 Cursor 창 열기
cursor {workspace-dir}/feature-a
cursor {workspace-dir}/feature-b
cursor {workspace-dir}/feature-c
```

각 Cursor 창의 Claude Code가 독립된 코드베이스 컨텍스트를 로드한다. feature-a 데모를 작업하는 Claude는 feature-a 코드만 본다. 각 창의 컨텍스트가 격리되어 3.6배 효율이다.

상세 내용은 [코딩-가이드.md - 병렬 개발](./코딩-가이드.md#병렬-개발) 참고.

## 도구 상세

### Codex-Claude Loop

품질 검증 루프다. Claude가 계획하고 구현하면 Codex가 검증해서 피드백한다. 반복해서 코드 품질을 올린다.

6단계로 진행된다. Claude가 계획을 세우면 Codex가 로직 오류, 빠진 엣지 케이스, 보안 문제를 찾는다. 문제가 있으면 Claude가 수정하고 다시 검증받는다. 계획이 통과하면 Claude가 구현한다. 구현이 끝나면 Codex가 코드를 리뷰한다. 버그나 성능 이슈가 있으면 Claude가 고치고 재검증받는다. 품질 기준을 만족할 때까지 반복한다.

구현 단계에서 AI가 복잡도를 판단해서 자동으로 사용한다. 인증(OAuth, JWT), 결제, 보안 로직처럼 품질이 중요한 기능에서 자동으로 품질 검증 루프가 돌아간다. 사용자가 선택하는 게 아니라 AI가 코드 복잡도를 보고 자동으로 판단한다.

### generate_code MCP

복잡한 알고리즘 생성 도구다. Codex를 호출해서 코드를 생성한다.

보안 관련(OAuth, JWT, 암호화), 성능 critical(정렬 알고리즘, 데이터 처리), 수학 연산(통계, 인코딩)이 해당한다. Claude가 구현 중에 PKCE 같은 복잡한 알고리즘을 만나면 generate_code로 Codex를 호출해서 생성하고 프로젝트에 통합한다. 나머지는 Claude가 직접 구현한다.

결과적으로 코드 품질이 올라간다. 복잡한 알고리즘은 검증된 코드를 쓰고, 전체 일관성은 Claude가 유지한다.

### /feature-dev

7단계 프로세스로 기능을 개발한다. code-explorer가 기존 코드를 분석하고, code-architect가 설계하고, code-reviewer가 품질을 체크한다.

옵션:
- `--explore`: 기존 코드 패턴 분석
- `--implement`: 기능 구현
- `--review`: 품질 검토

### /frontend-design

UI 레이아웃을 설계한다. VS Code나 Chrome처럼 검증된 디자인 패턴을 활용한다. 그리드 구조와 breakpoint를 정의한다.

### /security-guidance

Electron 앱 보안을 체크한다. IPC 통신, XSS 방어, 파일 시스템 접근을 검증한다.

옵션:
- `--focus electron,ipc`: 특정 영역에 집중

### /code-review

다중 agent로 코드를 분석한다. Confidence 점수 85% 이상만 리포트해서 false positive를 줄인다. 아키텍처, 성능, 보안, 품질을 모두 체크한다.

### /commit-commands:commit

Git 작업을 자동화한다. 변경 사항을 분석해서 일관된 커밋 메시지를 생성한다. code-review 점수와 security-check 결과를 커밋 메시지에 포함한다.

별칭: `/commit --scope {scope} --type {type}`

## 목표

베이스라인 컨텍스트를 125K에서 20K로 줄인다. 84% 감소다. Demo는 28K, Integration은 50K, Security는 27K를 유지한다. 컨텍스트가 작을수록 AI가 관련 정보에 집중한다. 개발 속도를 유지하거나 향상한다. 몰입 상태를 지키면서 도구 전환을 최소화한다.

이 전략으로 최소 컨텍스트를 유지하면서 최고의 바이브 코딩이 가능하다.
