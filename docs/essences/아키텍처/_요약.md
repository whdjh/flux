# 아키텍처

## Electron 프로세스 구조

애플리케이션은 Electron의 3-프로세스 모델을 따른다.

```
┌─────────────────────────────────────────┐
│         Main Process (Node.js)          │
│  - 윈도우 관리                           │
│  - 파일 시스템 접근                      │
│  - IPC 핸들러                            │
│  - 네이티브 기능                         │
└──────────────┬──────────────────────────┘
               │ IPC 통신
┌──────────────┴──────────────────────────┐
│       Preload Script (Bridge)           │
│  - contextBridge API                    │
│  - 보안 경계                            │
└──────────────┬──────────────────────────┘
               │ 안전한 API
┌──────────────┴──────────────────────────┐
│    Renderer Process (Chromium)          │
│  - React 앱                             │
│  - UI 렌더링                            │
│  - 사용자 상호작용                      │
└─────────────────────────────────────────┘
```

Main Process는 Node.js 환경에서 실행된다. 윈도우 생성/관리, 네이티브 API 접근, IPC 핸들링, 파일 시스템 접근을 담당한다.

Preload Script는 contextBridge로 안전한 API만 Renderer에 노출한다. Main과 Renderer 사이의 보안 경계 역할을 한다.

Renderer Process는 Chromium 환경에서 React 앱을 실행한다. UI 렌더링과 사용자 상호작용만 담당하고 비즈니스 로직은 없다.


## Backend-Centric 설계

"Frontend는 UI만, Backend는 모든 로직"이 핵심 원칙이다.

Renderer는 비즈니스 로직이 없다. path 계산, 캐싱, 재귀 알고리즘 모두 Backend에 있다. Renderer는 IPC 호출과 UI 렌더링만 하고, path.join()조차 사용하지 않는다.

```
Renderer (Dumb UI) → IPC 호출 → Main (Smart Backend)
                                  - 모든 path 계산
                                  - 파일 시스템 로직
                                  - 데이터 검증 (Zod)
                                  - 보안 검증 (PathValidator)
                                  - 캐싱, 배치 처리
```

API는 Result Objects 패턴을 따른다. Backend가 계산한 결과를 풍부한 객체로 반환한다.

```typescript
interface RenameResult {
  success: boolean;
  oldPath: string;
  newPath: string;  // Backend가 계산
}

// Renderer: 이름만 전달
await renameItem('/home/file.txt', 'newName.txt');
// Backend가 newPath 계산해서 반환
```

이점은 보안(PathValidator가 모든 path 검증), 크로스 플랫폼(Backend가 Windows/Unix path 처리), 성능(병렬 처리, 단일 캐싱), 유지보수(명확한 책임 분리, 테스트 용이)다.


## IPC 통신

Electron의 Main과 Renderer 프로세스는 서로 격리되어 있다. IPC(Inter-Process Communication)로 통신한다.

### 통신 흐름

Renderer → Preload → Main → Preload → Renderer 순서로 요청/응답이 이동한다.

```typescript
// 1. Renderer에서 요청
const content = await window.electron.readFile(path);

// 2. Preload에서 브릿지
contextBridge.exposeInMainWorld('electron', {
  readFile: (path: string) => ipcRenderer.invoke('read-file', path)
});

// 3. Main에서 처리
ipcMain.handle('read-file', async (event, path: string) => {
  const validated = validatePath(path);
  const content = await fs.readFile(validated, 'utf-8');
  return content;
});
```

### IPC 채널 목록

파일 시스템:
- `read-file`, `write-file`, `list-directory`, `create-file`, `delete-file`

윈도우 관리:
- `minimize-window`, `maximize-window`, `close-window`, `fullscreen-toggle`

애플리케이션:
- `get-app-version`, `get-user-data-path`, `open-external`

### 에러 처리

에러는 객체로 감싸서 전달한다. `{success, data/error}` 패턴을 사용한다.

```typescript
// Main
ipcMain.handle('read-file', async (event, path: string) => {
  try {
    return { success: true, data: content };
  } catch (error) {
    return { success: false, error: error.message };
  }
});

// Renderer
const result = await window.electron.readFile(path);
if (result.success) {
  setContent(result.data);
} else {
  toast.error(result.error);
}
```

### 이벤트 기반 통신 (Main → Renderer)

Main에서 Renderer로 이벤트를 보낼 수 있다.

```typescript
// Main
webContents.send('file-changed', { path, content });

// Renderer
window.electron.onFileChanged((data) => {
  console.log('File changed:', data);
});
```

### TypeScript 타입 안전성

Preload에서 ElectronAPI 인터페이스를 정의하면 Renderer에서 자동완성이 된다.

```typescript
interface ElectronAPI {
  readFile: (path: string) => Promise<string>;
  writeFile: (path: string, content: string) => Promise<void>;
}

declare global {
  interface Window {
    electron: ElectronAPI;
  }
}
```


## 보안 아키텍처

> 충돌 주의: 문서마다 보안 레이어 수가 다르다. 초기 문서는 3-Layer, 중간 문서는 5-Layer, README는 7-Layer(Crypto + Logging 추가)를 명시한다. 아래는 가장 최신인 7-Layer 구조를 기준으로, 핵심 5-Layer를 상세히 기술한다.

Defense in Depth 전략으로 각 레이어가 독립적으로 동작한다. 한 레이어가 뚫려도 다른 레이어가 막는다.

```
사용자 입력 → [L1] CSP → [L2] Headers → [L3] Zod → [L4] Rate Limit → [L5] Path → [L6] Crypto → [L7] Logging → 안전한 처리
```

### Layer 1: CSP (Content Security Policy)

브라우저 레벨에서 허용된 소스만 로드하게 제한한다. 외부 스크립트, eval(), 신뢰되지 않은 소스를 차단한다.

```typescript
session.defaultSession.webRequest.onHeadersReceived((details, callback) => {
  callback({
    responseHeaders: {
      ...details.responseHeaders,
      'Content-Security-Policy': [
        "default-src 'self'",
        "script-src 'self'",
        "style-src 'self' 'unsafe-inline'",
        "img-src 'self' data: https:",
      ].join('; ')
    }
  });
});
```

### Layer 2: Security Headers

HTTP 헤더로 추가 보호막을 친다.

```typescript
'X-Content-Type-Options': 'nosniff',      // MIME 타입 변조 차단
'X-Frame-Options': 'DENY',                // iframe 삽입 차단
'X-XSS-Protection': '1; mode=block',      // XSS 필터 활성화
'Referrer-Policy': 'no-referrer',          // 정보 누출 차단
'Permissions-Policy': 'geolocation=(), microphone=(), camera=()'
```

### Layer 3: Zod 입력 검증

모든 IPC 입력은 Zod로 런타임 타입 체크한다.

```typescript
const FilePathSchema = z.object({
  path: z.string().min(1).max(1024),
  encoding: z.enum(['utf-8', 'base64']).optional()
});

ipcMain.handle('read-file', async (event, input: unknown) => {
  const validated = FilePathSchema.parse(input);
});
```

### Layer 4: Rate Limiting

IPC 요청 빈도를 제한한다. 100ms 안에 같은 채널을 두 번 호출하면 거부한다.

```typescript
const rateLimiter = new Map<string, number>();

function checkRateLimit(channel: string): boolean {
  const now = Date.now();
  const lastCall = rateLimiter.get(channel) || 0;
  if (now - lastCall < 100) return false;
  rateLimiter.set(channel, now);
  return true;
}
```

### Layer 5: Path Validation

파일 경로를 4단계로 검증한다. Path Traversal 공격을 막는 마지막 방어선이다.

```typescript
function validatePath(inputPath: string, basePath: string): string {
  // 1. 정규화
  const normalized = path.normalize(inputPath);
  // 2. 절대 경로 변환
  const resolved = path.resolve(basePath, normalized);
  // 3. Path Traversal 체크
  if (!resolved.startsWith(basePath)) {
    throw new Error('Invalid path: traversal detected');
  }
  // 4. 금지된 문자 체크
  if (/[<>:"|?*]/.test(inputPath)) {
    throw new Error('Invalid path: forbidden characters');
  }
  return resolved;
}
```

### Layer 6-7: Crypto + Logging

Layer 6은 OS-level 암호화(Keychain/DPAPI/Secret Service)로 민감 정보를 보호한다. Layer 7은 보안 이벤트를 JSON Lines 형식으로 기록한다(30일 보관, 자격 증명 절대 기록 안 함).

### 보안 테스트

6개 카테고리로 나뉜다. CSP 우회 시도, XSS 공격 패턴, Path Traversal, SQL Injection, Rate Limit 초과, 입력 검증 우회를 검증한다. 모든 보안 테스트는 100% 통과 필수다.

보안 스코어: 9.8/10. OWASP Top 10 커버리지: Access Control, Cryptographic Failures, Injection, Security Misconfiguration, Vulnerable Components, Logging Failures.


## Frontend 아키텍처

```
React Router v7 (/explorer, /settings, /editor/:fileId)
    ↓
App Layout (Titlebar, Sidebar, EditorArea, StatusBar)
    ↓
State Management - Zustand
  (useLayoutStore, useEditorGroupStore, useFileSystemStore, useTabStore)
```

### 라우팅 (React Router v7)

```
/ (Root)
├── /explorer          # 파일 탐색기 뷰
├── /settings          # 설정 페이지
│   ├── /appearance    # 외관 설정
│   └── /security      # 보안 설정
├── /editor/:fileId    # 에디터 뷰 (동적)
└── /404               # Not Found
```

라우트 로더로 데이터를 미리 로드한다. 라우트 가드로 인증을 체크한다. 중첩 라우팅으로 Layout 구조를 구성한다. NavLink로 활성 링크를 스타일링한다.

### 상태 관리 (Zustand)

전역 상태는 Zustand로 관리한다. Feature별로 독립적인 Store를 만든다.

```
src/features/file-explorer/store/fileSystemStore.ts    # 파일 탐색 상태
src/features/editor-groups/store/editorGroupStore.ts   # 에디터 그룹
src/features/editor-groups/store/tabStore.ts           # 탭 관리
src/app/layout/store/layoutStore.ts                    # 레이아웃 상태
```

주요 Store:
- layoutStore: sidebarOpen, sidebarWidth, statusBarVisible
- editorGroupStore: groups(탭 배열), activeGroupId, addTab/removeTab/setActiveTab/updateTabContent
- fileSystemStore: tree, expandedFolders, selectedFile, loadTree/toggleFolder/selectFile

IPC와 상태 동기화: 파일 클릭 → FileSystemStore 업데이트 → IPC로 파일 읽기 → EditorGroupStore에 탭 추가. 자동 저장은 isDirty 상태 변경 후 2초 debounce로 IPC writeFile을 호출한다.

영속화: layoutStore는 localStorage(persist 미들웨어)로 사이드바 폭 등을 저장한다. tabStore는 sessionStorage로 세션 동안만 유지한다.

최적화:
- Selector로 필요한 부분만 구독 (불필요한 리렌더 방지)
- shallow 비교로 객체 구조 비교
- Immer 미들웨어로 불변성 자동 처리
- DevTools 연동 (개발 환경)


## Backend 아키텍처 (Clean Architecture)

```
┌─────────────────────────────────────────┐
│         Domain Layer                     │
│  - 비즈니스 로직, Entity, Value Object   │
│  - 프레임워크 독립                       │
├─────────────────────────────────────────┤
│      Application Layer                   │
│  - Use Cases, Service Layer              │
│  - DTO, Mapper                           │
├─────────────────────────────────────────┤
│     Infrastructure Layer                 │
│  - DB (Drizzle ORM), External API        │
│  - File System, Supabase                 │
└─────────────────────────────────────────┘
```

의존성 방향: UI Components → Zustand Store → IPC API (Preload) → Main IPC Handler → Application Use Case → Domain Logic → Infrastructure (DB). 위에서 아래로만 의존한다. 역방향은 금지다.


## 데이터베이스

DB 스택은 Drizzle ORM + Supabase + PostgreSQL이다. Main 프로세스에서 Drizzle로 접근하고, Renderer는 Supabase Client를 사용한다.

### 스키마 정의

`src/backend/infrastructure/db/schema.ts`에 pgTable로 정의한다.

```typescript
export const files = pgTable('files', {
  id: uuid('id').primaryKey().defaultRandom(),
  path: text('path').notNull().unique(),
  content: text('content'),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow()
});
```

### 마이그레이션 흐름

schema.ts 수정 → `npm run db:generate` → `npm run db:push` → `npm run db:studio`로 확인.

### Clean Architecture 통합

Domain Layer에 Repository 인터페이스를 정의하고, Infrastructure Layer에 DrizzleFileRepository로 구현한다. toDomain()/toPersistence() 변환 메서드로 레이어 간 데이터를 매핑한다.

### Renderer용 Supabase Client

```typescript
const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
);
```

### 성능 최적화

Connection Pooling(max: 10, idle_timeout: 20s), 인덱스(path_idx, created_at_idx), 배치 삽입, 트랜잭션으로 원자적 작업을 보장한다.


## 폴더 구조

```
src/
├── demos/             # 실험적 프로토타입 (빠른 실험, 삭제 가능)
├── features/          # 검증된 기능 모듈 (프로덕션, 테스트 필수)
├── app/               # 코어 인프라 (통합 레이어, VS Code/Chrome 통합)
├── shared/            # 공통 리소스 (UI 컴포넌트, 훅, 유틸리티)
├── main/              # Main Process (윈도우 관리, IPC 핸들러)
├── backend/           # 백엔드 로직 (DB, API, 서비스)
├── routes/            # React Router 라우팅
├── __tests__/         # 통합/E2E 테스트
├── main.ts            # Main process 진입점
├── preload.ts         # Preload script
└── renderer.tsx       # Renderer 진입점
```

### demos/ vs features/

demos/는 실험 공간이다. 코드 품질보다 속도를 우선한다. 사용자 피드백이 긍정적이고, 기술적 실현 가능성이 확인되고, 성능 요구사항을 충족하면 features/로 이동한다.

features/는 프로덕션 기능이다. 높은 코드 품질, 완전한 테스트 커버리지(80%+), 문서화, 접근성(WCAG AA)이 필수다.

### 파일 명명 규칙

- 컴포넌트: PascalCase.tsx (Button.tsx, FileExplorer.tsx)
- 훅: camelCase + use prefix + .ts (useEditor.ts, useTheme.ts)
- 유틸리티: camelCase.ts (format.ts, validation.ts)
- 타입: camelCase.types.ts (editor.types.ts)
- 테스트: 같은 이름.test.ts(x)

### Import 규칙

절대 경로 `@/`를 사용한다. 상대 경로는 같은 feature 내부에서만.

순서: React/외부 → @/shared → @/features → 로컬 → 스타일


## 애플리케이션 흐름

### 실행 흐름

1. `npm run dev` 실행
2. Vite가 3개 번들 동시 빌드 (Main, Preload, Renderer)
3. Electron Forge가 Main 프로세스 실행
4. Main이 BrowserWindow 생성
5. Preload 스크립트 로드 (contextBridge 설정)
6. Renderer 프로세스 (React 앱) 시작
7. React Router가 라우팅 처리

### 빌드 흐름

1. `npm run make` 실행
2. TypeScript 타입 체크
3. Vite 프로덕션 빌드 (3개 번들)
4. Electron Forge Maker 실행 (macOS: ZIP, Windows: Squirrel, Linux: Deb/Rpm)
5. `out/` 디렉토리에 배포 파일 생성

### 데이터 흐름

UI 상호작용 → Zustand Store 액션 → IPC 호출 → Backend Use Case → Infrastructure (DB) → 결과 반환 → Store 업데이트 → 리렌더링

### 보안 검증 흐름

사용자 입력 → L1 CSP → L2 Security Headers → L3 Zod → L4 Rate Limiting → L5 Path Validation → 안전한 처리
