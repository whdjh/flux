# 스택

docs/memory/essences/스택/의 Electron + Drizzle 구성은 초기 보일러플레이트 기준이다. 브레인스토밍(2/15), 스택 논의(2/17), 프론트엔드 스택 재검토(3/2)를 거쳐 아래로 확정했다.

flux는 여러 기기에서 메모를 실시간으로 편집하고, 오프라인에서도 동작하는 앱이다. 이 요구사항이 스택 전체를 결정했다. 실시간 편집 엔진(loro)이 Rust라서 서버도 Rust가 됐고, 오프라인 동작이 필요해서 로컬 DB(SQLite)가 필수가 됐고, 기기 간 즉시 반영이 필요해서 WebSocket을 쓴다. 나머지 선택도 이 흐름 위에 있다.


## 서버: Rust (Axum)

API 서버, 실시간 동기화, 인증을 처리한다. loro가 Rust로 만들어져 있어서, 서버도 Rust면 데이터를 변환 없이 그대로 다룬다. 다른 언어로 서버를 짜면 매번 데이터를 변환해야 해서 느려지고 복잡해진다. Rust 웹 프레임워크 중 Axum을 고른 건 tokio 팀이 직접 만들어서 비동기 처리가 안정적이고, 미들웨어 생태계(tower)가 넓기 때문이다. 바이너리 하나로 배포할 수 있어서 인프라가 단순하다.

WebSocket 처리는 tokio-tungstenite. DB 접근은 SQLx로 컴파일타임에 쿼리를 검증한다.


## 서버 DB: PostgreSQL

사용자 데이터를 영구 저장한다. 여러 사용자가 동시에 데이터를 쓰고 읽어야 하는데, 로컬 DB(SQLite)로는 이걸 처리할 수 없다. MySQL도 되긴 하지만, PostgreSQL이 JSON 처리와 동시성 제어에서 더 성숙하다. 수집한 항목마다 출처 URL, 제목, AI 요약, 키워드 같은 부가 정보를 JSON으로 저장하는데, 이런 비정형 데이터를 다루는 데 PostgreSQL 생태계가 더 두텁다. Rust 쪽 DB 도구(SQLx, SeaORM)도 PostgreSQL 지원이 가장 먼저, 가장 안정적으로 나온다.


## 인증: 자체 구현 (argon2 + JWT)

회원가입, 로그인, 세션 관리를 서버에서 직접 처리한다. 처음에는 Supabase Auth를 쓰려고 했는데, 두 가지 이유로 빼기로 했다. 하나는 외부 서비스를 줄이자는 거다. Supabase를 빼면 외부 의존이 하나 줄어들고, 기술이 분산되는 문제가 줄어든다. 다른 하나는 로그인 같은 핵심 흐름을 외부에 맡기면 장애가 나도 우리가 대응할 수 없다는 거다. 서버가 이미 있으니까 거기서 같이 처리하면 구조도 단순해진다.


## 클라이언트: Next.js (웹/데스크톱) + React Native (모바일)

처음에는 RN 하나로 세 플랫폼을 커버하려고 했다. 하지만 RN Web은 SSR이 안 되고, SEO와 공유 링크 미리보기도 불가능하다. 공유 기능(읽기 전용 링크)에 SSR이 필요한데 RN Web으로는 풀기 어렵다. 나중에 Next.js로 전환하면 공수가 더 크다.

그래서 웹은 Next.js로 잡고, Tauri로 래핑해서 데스크톱 앱을 만든다. 모바일은 RN Expo로 별도 작업한다. 비즈니스 로직(타입, AI 파이프라인 등)은 pnpm 모노레포에서 공유한다.

```
apps/
  web/        — Next.js (웹 + API Routes)
  desktop/    — Tauri (Next.js 래핑)
  mobile/     — React Native (Expo)
  extension/  — Chrome Extension MV3

packages/
  core/       — 엔티티 타입, 비즈니스 로직 (순수 TS)
  ai/         — OpenRouter 클라이언트, 요약/키워드 파이프라인 (순수 TS)
```

loro 바인딩은 플랫폼별로 다르다. 웹/데스크톱은 WASM으로 브라우저에서 직접 실행하고, 모바일은 JSI로 네이티브급 성능을 낸다. 둘 다 에디터 키 입력 기준 16ms(60fps) 안에 충분히 들어온다. 상세 비교는 `essences/스택/0302-스택-비교.md` 참조.

스택 변경 이력: Swift 네이티브 검토(`essences/스택/0216-네이티브-vs-RN.md`) → RN 단일 선택(팀 효율) → Next.js + RN 분할(웹 품질, 3/2)


## 클라이언트 (Chrome Extension)

JS/TS. 브라우저에서 바로 캡처하는 접점. 웹 클리핑, 링크 저장 등.


## 실시간 편집 엔진: loro

여러 기기에서 같은 문서를 동시에 편집해도 충돌 없이 합쳐주는 엔진이다. iPhone에서 쓴 메모를 Mac에서 이어 쓸 수 있어야 하고, 인터넷이 끊겨도 작동해야 한다. 리치텍스트(볼드, 리스트 등) + 버전 관리(실행 취소/되돌리기)가 내장되어 있다.

비슷한 걸로 Yjs(JS), Automerge(Rust/JS), diamond-types(Rust)가 있다. Yjs는 JS 기반이라 서버(Rust)에서 네이티브로 다룰 수 없고, Automerge는 리치텍스트와 트리 구조 지원이 loro보다 약하다. diamond-types는 텍스트만 된다. loro는 Rust 네이티브이면서 리치텍스트 + 트리 + 타임트래블을 전부 지원하는 조합이 맞는 선택지다.

서버에서는 Rust 네이티브, 웹/데스크톱에서는 WASM, 모바일에서는 JSI 네이티브 바인딩으로 연결한다.


## 로컬 DB: SQLite

사용자 기기에 데이터를 저장한다. 저장할 때 서버 응답을 기다리면 느려지는데, 로컬에 먼저 저장하면 0ms다. 인터넷 없이도 앱이 완전히 동작해야 하기 때문에 로컬 DB가 필수다. 모든 쓰기는 SQLite에 먼저 하고, 백그라운드에서 서버와 동기화한다.

웹/데스크톱에서는 wa-sqlite(WASM), 모바일에서는 op-sqlite(네이티브 모듈)를 쓴다.


## 실시간 동기화: WebSocket

기기 간 데이터를 실시간으로 주고받는다. SSE(Server-Sent Events)는 서버→클라이언트 한 방향만 된다. flux는 클라이언트도 서버에 편집 내용을 보내야 하고, 서버도 다른 기기의 변경을 클라이언트에 보내야 한다. 양방향이 필요하다. SSE로 하면 받는 건 SSE, 보내는 건 별도 REST 요청으로 두 채널을 관리해야 한다. WebSocket은 하나의 연결로 양방향 통신이 되니까 구조가 단순하다.


## 파일 저장소: Cloudflare R2

이미지, 스크린샷 같은 바이너리 파일을 저장한다. flux는 여러 기기에서 같은 파일을 내려받는데, S3는 다운로드마다 $0.09/GB가 나간다. R2는 다운로드 비용이 0이다. S3 호환 API라서 나중에 S3로 옮기기도 쉽다.


## 모노레포: pnpm workspace

웹, 데스크톱, 모바일, 익스텐션이 같은 저장소에서 비즈니스 로직을 공유한다. packages/core에 엔티티 타입과 순수 TS 로직을, packages/ai에 OpenRouter 파이프라인을 둔다. 앱별 코드는 apps/ 아래에 분리한다.


## 검증

서버: serde + validator (Rust). 클라이언트: Zod.


## 플랫폼 우선순위

"수집 < 100ms", "인지 부하 최소화", "로컬 우선" 원칙에서 플랫폼 우선순위를 정했다. 3/2 스택 재검토에서 RN 단일에서 Next.js + RN 분할로 바뀌면서 우선순위도 조정했다.

```
Web (Next.js) → Desktop (Tauri) → Chrome Extension (JS/TS) → iOS (RN Expo) → Android (RN Expo)
```

웹을 먼저 만들고 Tauri로 데스크톱을 래핑한다. 모바일은 RN Expo로 나중에 한다. 기존 순서는 iOS가 첫 번째였지만, 2인 팀에서 웹+모바일을 동시에 개발하기 어렵다는 현실적 판단으로 웹/데스크톱에서 핵심 루프(수집→정리→메모→검색)를 먼저 검증하고 모바일로 수집 경로를 확장하는 흐름으로 바꿨다.

**1순위 Web** — Next.js (App Router). SSR로 공유 링크 미리보기(OG 태그) 지원, API Routes로 AI 프록시·인증 처리. loro는 WASM, SQLite는 wa-sqlite(WASM)로 로컬 저장.

**2순위 Desktop** — Tauri v2. Next.js 웹 앱을 WebView로 래핑. OS 네이티브 기능(포스트잇 창, 폴더·클립보드 감시, 전역 단축키, 시스템 트레이)은 Tauri 공식 플러그인으로 커버하고 커스텀 Rust는 최소화. 콜드 스타트가 아닌 핫 스타트(백그라운드 상주)라서 Tauri로 충분. 프론트엔드는 Web과 동일한 코드.

**3순위 Chrome Extension** — JS/TS, MV3. 브라우저 수집 접점. 우클릭 컨텍스트 메뉴, 텍스트 선택 저장, 페이지 클리핑, 탭 URL 저장.

**4순위 iOS** — React Native (Expo, New Architecture). Share Extension이 핵심 진입점(브라우저·SNS·유튜브 어디서든 공유 버튼으로 수집). 카메라, 클립보드 URL 감지, 음성 메모. loro는 JSI, SQLite는 op-sqlite.

**5순위 Android** — iOS와 같은 RN 코드베이스. 플랫폼별 분기는 OS 통합 기능(Share Extension → Intent Filter, 위젯 → App Widget)에서만 발생.

### 플랫폼별 수집 진입점

사용자가 "Flux에 저장한다"는 행위 없이 기존 습관 그대로 하면 알아서 모이는 구조다.

- Web/Desktop: 브라우저 확장으로 Alt+우클릭 수집, 드래그앤드롭. Tauri에서 폴더 감시, 클립보드 감시, 전역 단축키 팝업
- iOS/Android: Share Sheet가 핵심. 카메라 촬영, 갤러리 선택, 클립보드 URL 감지, 음성 메모
- Chrome Extension: 우클릭 컨텍스트 메뉴, 텍스트 선택 저장, 페이지 클리핑, 탭 URL 저장

### 왜 Next.js + RN인가

처음에는 Swift/SwiftUI로 시작하려고 했다. cold start가 빠르고 OS 통합이 자연스럽기 때문. 하지만 2인 팀에서 Swift+Kotlin+React를 각각 감당할 수 없어서 RN 단일로 갔다.

RN 단일로 가니까 웹 품질이 문제였다. SSR이 안 되고, 공유 링크 미리보기가 불가능하고, 프론트엔드 생태계를 제대로 못 쓴다. "나중에 Next.js로 바꾸면 더 힘들다"는 판단으로 처음부터 Next.js로 웹을 잡기로 했다. 결과적으로 웹/데스크톱(Next.js + Tauri)과 모바일(RN Expo)을 분리하되, 모노레포(pnpm workspace)로 비즈니스 로직을 공유한다. 코드베이스가 2개로 늘지만 각 플랫폼의 품질이 올라간다.
